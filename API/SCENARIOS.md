# Примеры реализации сценариев

Краткие ориентиры для реализации согласованных сценариев TripFlow. Форматы запросов, ответов и обязательные правила взаимодействия описаны в [CONTRACT.md](CONTRACT.md). Здесь показано, как эти правила могут применяться в работе сервисов. Числа в примерах условные.

## 1. Полная генерация

| Шаг | Пример действий |
|---|---|
| Подготовка запроса | Backend берёт выбранное направление из общего справочника, формирует параметры поездки, создаёт `taskId` и передаёт `callbackUrl` |
| Получение данных | Python получает реальные отели, достопримечательности и сведения для оценок расходов; недостающие данные дополняет из предусмотренных резервных источников |
| Подготовка кандидатов | Проверяет соответствие направлению, убирает повторы и неподходящие объекты, приводит денежные значения к рублям и единицам контракта |
| Подбор | Нейросеть помогает интерпретировать предпочтения, ранжировать реальные кандидаты и оценивать повседневные расходы; обычный код проверяет допустимость результата |
| Передача результата | Python отправляет итоговый callback. Backend сопоставляет его с задачей и сохраняет результат для карточки |

Отсутствие рекомендаций само по себе не мешает успешной генерации: карточка может содержать метаданные и пригодные общие оценки бюджета. Если необходимую бюджетную основу получить невозможно, задача завершается ошибкой.

## 2. Продолжение поиска и резервные источники

При временном сбое запрос повторяется с паузой. Число попыток и общее время поиска ограничены настройками. При исчерпании попыток используются предусмотренные резервные источники. Повтор одинакового запроса применяется к временным сбоям, а не к заведомо неисправимым этим повтором причинам.

Следующую страницу можно запросить независимо от пропущенной, если это позволяет внешний источник. При пагинации через указатель из предыдущего ответа продолжение может оказаться недоступным. Пропуски учитываются при определении полноты поиска.

Пример: запрошено пять вариантов, поиск ведётся до получения хотя бы одного дополнительного подходящего уникального кандидата либо до завершения доступного поиска.

| Результат | Ответ |
|---|---|
| Найдено шесть подходящих кандидатов | Возвращаются пять, `hasMore: true` |
| Найдено два, поиск завершён | Возвращаются два, `hasMore: false` |
| Найдено два, часть поиска недоступна после предусмотренных попыток | Возвращаются два, `hasMore: null` |

Наличие дополнительных кандидатов проверяется после исключения повторов и непригодных объектов. Отдельный вызов нейросети только ради флага `hasMore` не требуется.

## 3. Расчётная стоимость кандидата

В MVP используется фиксированный локальный справочник реальных статистических ставок. Для оценки подбираются сопоставимые категория, территория и единицы стоимости. Общая ставка поездки и оценка конкретного кандидата имеют разные назначения.

Для общей ставки сначала используется пригодный городской ориентир, затем региональный, затем общестрановой как последний резерв. В `scope` сохраняется фактический уровень исходных данных: например, региональная ставка для карточки Суздаля возвращается с `scope: "region"`.

| Данные кандидата | Пример обработки |
|---|---|
| У отеля есть собственная цена и подходящая справочная ставка | Возвращаются `amountRub` и рассчитанный `estimatedRub` |
| У отеля есть цена, категория неизвестна | Возвращаются собственная цена и `stars: null`; при отсутствии обоснованной оценки `estimatedRub: null` |
| Цена отеля отсутствует, категория известна | При наличии подходящей ставки рассчитывается `estimatedRub` |
| Нет собственной цены отеля и обоснованной оценки | Отель не включается в рекомендации |
| Источник явно обозначает категорию «без звёзд» | Для оценки может использоваться соответствующая ставка; наружу передаётся `stars: null` |
| У достопримечательности известна категория и есть подходящая ставка | Категория возвращается в `category`, оценка — в `estimatedRub` |
| Стоимость достопримечательности определить невозможно | Кандидат может возвращаться с обеими суммами `null` как рекомендация с неизвестной стоимостью |

Внешнее значение `0` звёзд трактуется с учётом смысла поля конкретного источника. Неизвестная категория не превращается автоматически в самую дешёвую. Звёздность берётся из данных источника; характеристики объекта не служат основанием выдать предположение за установленную категорию.

При расчёте и отображении используется `amountRub`, если он не `null`, иначе — `estimatedRub`. Собственная нулевая цена сохраняет значение бесплатности. Статистическая оценка показывается с соответствующей подписью.

## 4. Бюджетный отбор и приоритет

Пример догенерации отеля: лимит — 60 000 ₽, три путешественника, пять ночей. Удельный предел составляет `60 000 / 3 / 5 = 4 000 ₽` на человека за ночь.

| Используемая сумма кандидата | Решение |
|---|---|
| Собственная цена 3 500 ₽ | Проходит бюджетный отбор |
| Собственной цены нет, оценка 3 200 ₽ | Проходит бюджетный отбор |
| Собственная цена 4 500 ₽ | Не проходит; меньшая статистическая оценка не заменяет известную цену |

Для достопримечательности предел делится на число путешественников: проверяется одно посещение всей группой. При обеих неизвестных суммах рекомендация допускается без подтверждения соответствия лимиту.

После отбора варианты ранжируются по предпочтениям и доступным характеристикам. При сопоставимом соответствии пожеланиям собственная цена даёт более определённую основу для выбора, чем статистическая оценка. Близость стоимости к верхнему пределу сама по себе не означает преимущества кандидата.

При полной генерации целевой бюджет допускает согласованный диапазон отклонений. Подходящий более дешёвый вариант сохраняется; при невозможности уложиться в верхний допуск возвращаются наиболее доступные подходящие варианты с реалистичными оценками расходов. Backend показывает разницу с целевым бюджетом.

## 5. Предварительный бюджет и выбор пользователя

Пример для трёх путешественников и пяти ночей:

| Состояние | Пример расчёта |
|---|---|
| Отель не выбран | Общая ставка 3 000 ₽ даёт предварительное проживание `3 000 × 3 × 5 = 45 000 ₽` |
| Выбран отель с используемой суммой 3 500 ₽ | Проживание становится `52 500 ₽`, заменяя предварительные `45 000 ₽` |
| Посещения не выбраны | Общая ставка 300 ₽ и четыре посещения на человека дают `300 × 4 × 3 = 3 600 ₽` |
| Выбрано посещение с используемой суммой 500 ₽ | Расчёт выбранных посещений составляет `500 × 3 = 1 500 ₽` и заменяет предварительную оценку посещений |
| Дополнительно выбрано место с обеими суммами `null` | Оно сохраняется в выборе, но стоимость не включается в итог; пользователю показывается предупреждение о неполной сумме |

Backend добавляет питание, городской транспорт, прочие расходы и резерв. Неизвестное посещение не становится бесплатным; неполный итог не подтверждает соответствие всей поездки бюджету. Общие ставки и заменившие их стоимости выбранных объектов одновременно не суммируются.

## 6. Догенерация с уточнением и исключениями

Пользователь отклонил предложенные отели и уточнил: «Можно дальше от центра, главное — тише».

1. Backend формирует новый `taskId`, `target: "hotels"`, актуальный контекст и `optionBudgetRub` с учётом остальных расходов. Стоимость заменяемого отеля не удерживается в остальных расходах.
2. В `excluded` передаются названия и координаты уже показанных, выбранных и отклонённых отелей, которые требуется исключить. `refinement` содержит итоговое уточнение для текущего запроса.
3. Python исключает уверенно сопоставленные объекты до ранжирования, подбирает новые альтернативы по бюджетному пределу и пожеланиям. Новое уточнение имеет приоритет при противоречии старому пожеланию к отелям.
4. Backend сохраняет результат как альтернативы. Выбранный отель меняется после действия пользователя; общие оценки расходов и метаданные направления сохраняются.

При `refinement: null` используются предпочтения карточки. При пустом `excluded` прежние варианты могут встретиться снова: необходимые исключения передаются в каждом запросе. Неоднозначное сопоставление объекта не является основанием для автоматического исключения.

## 7. Очередь вариантов на backend

Backend хранит связь кандидата с карточкой и задачей, а также состояние выбора или отклонения. `position` задаёт порядок только внутри соответствующей выдачи.

| Ситуация | Пример работы очереди |
|---|---|
| В прежней очереди последняя позиция — 5 | Новая выдача приходит с `position: 1, 2, 3` |
| Backend добавляет выдачу в конец | Новые элементы получают места очереди `6, 7, 8` с сохранением порядка ответа |
| Пользователь отклоняет вариант | Backend сохраняет отклонение и переходит к следующему доступному элементу |

Внутренний ID записи используется для идентификации, а не для определения приоритета рекомендации. В примере общая позиция получается прибавлением локального `position` к последней позиции очереди.

## 8. Исчерпание выдачи и повторный поиск

| Ситуация после просмотра полученных вариантов | Пример поведения |
|---|---|
| `hasMore: true` | Пользователь запрашивает дополнительные варианты целевого типа |
| `hasMore: false` | После исчерпания или отклонения выдачи показывается отсутствие дополнительных вариантов; новый поиск предлагается после изменения условий |
| `hasMore: null` | Пользователь может нажать «Повторить поиск»; backend создаёт новую задачу догенерации с актуальными исключениями |
| Поиск завершён без новых вариантов | Сохраняется успешный ответ с пустым `items` и `hasMore: false` |
| Догенерация завершилась ошибкой | Предыдущие варианты, выбор и прежний `hasMore` сохраняются; отображается ошибка и возможность повторить запрос |

Ранее полученные результаты остаются доступны во время повторного поиска. Ошибка задачи не обозначает исчерпание вариантов.

## 9. Приведение цены проживания

Для оценки используются цены, позволяющие определить ориентировочные расходы одного путешественника за ночь. В первую очередь рассматривается цена размещения одного человека, затем — минимальная пригодная цена другого варианта размещения, допускающего проживание одного человека.

| Исходные данные | Пример использования |
|---|---|
| Есть пригодный тариф на одного человека за ночь | Используется как основа `amountRub` |
| Есть цена за ночь номера с двуспальной кроватью, допускающего проживание одного человека | Может использоваться полная цена такого размещения; число спальных мест само по себе не является основанием делить цену |
| Валюта или единица стоимости не позволяют обоснованно получить цену на человека за ночь | Возвращается `amountRub: null`; при наличии подходящих справочных данных рассчитывается `estimatedRub` |

Подбор исходной цены служит оценке расходов; конкретный номер и состав услуг пользователь определяет при самостоятельном бронировании.

## 10. Дни, ночи и денежные значения

| Условие | Пример расчёта или результата |
|---|---|
| Поездка с 10 по 15 июня | Проживание учитывает пять ночей, питание и прочие ежедневные расходы — шесть полных дней |
| Питание оценивается в 800 ₽ на человека в день, путешественников трое | За шесть дней получается `800 × 3 × 6 = 14 400 ₽` |
| Цена после приведения к рублям — 333 ₽ | Возвращается `333` |
| Цена после приведения к рублям — 333,01 ₽ | Возвращается `334` |
| Подтверждено бесплатное посещение | Возвращается `amountRub: 0`; запасная оценка не подставляется |
| Цены посещения неизвестны | Обе суммы могут оставаться `null`; при выборе места его стоимость не включается в итог, что отдельно обозначается пользователю |
| Не удалось получить обязательную оценку питания | Получение пригодной оценки продолжается предусмотренными способами; при невозможности задача завершается ошибкой, без успешного результата с нулём или `null` вместо расходов |

Обычная оговорка об ориентировочности относится ко всему бюджету. Наличие выбранных посещений с неизвестной стоимостью дополнительно выделяется как неполнота расчёта.
