# TripFlow · Python API

FastAPI-сервис принимает задачи подбора и расчёта сметы. Локальная сборка Stage 2 ищет реальные отели в выбранном городе. Места берутся из московского тестового набора для всех городов, четыре статьи сметы рассчитываются по тестовым ставкам. Два маршрута создают задачи, а `GET /v1/tasks/{taskId}` возвращает статус и сохранённый результат по одному `X-API-Key`. [Контракт локальной сборки](docs/BACKEND-HANDOFF.md)

## Локальный запуск

Для первого запуска из пустой базы скопируйте `.env.example` в `.env` внутри `API/` и задайте email и пароль владельца. При существующей базе оставьте её прежние параметры подключения. Из каталога `API` запустите:

~~~powershell
docker compose up -d --build
docker compose ps
~~~

По умолчанию сервис доступен на порту 8000, а SQLite сохраняется в томе `api-state`. Порт хоста задаётся через `TRIPFLOW_API_PORT`. При указанном `DATABASE_URL` используется PostgreSQL. После первого входа владельца переменные его email и пароля для запуска можно убрать. [Локальный кабинет](http://127.0.0.1:8000/portal) · [Локальный Swagger](http://127.0.0.1:8000/docs)

Задайте `GEOAPIFY_API_KEY` в `API/.env` для подсказок городов и `DEEPSEEK_API_KEY` для разбора пожеланий, Search, Fetch и извлечения данных. После изменения ключей выполните из `API`:

~~~powershell
docker compose up -d --force-recreate api
Invoke-RestMethod http://127.0.0.1:8000/health
~~~

Конструктор и публичный API используют общий обработчик. При отсутствии ключа Geoapify подсказки показывают состояние настройки. Публичный POST с валидным направлением работает без Geoapify. Гостиничная задача может закончиться результатом из сохранённого каталога при недоступном DeepSeek, если есть применимые тарифы и доказательства условий. Для разбора нового текста требуется Flash. Успешные шаги сохраняются, а перезапуск сервиса подхватывает незавершённые задачи по истечении захвата. Повтор того же POST и чтение результата используют исходный снимок. В Swagger используется ключ TripFlow из кабинета. [Инструкция и метрики](docs/PORTAL.md#разбор-пожеланий-локально)

### Исполнение гостиничной задачи

В конструкторе можно задать желаемую групповую сумму проживания. `targetHotelTotalRub` ранжирует варианты по близости к цели с учётом качества основания, доступности и предпочтений. Явный `maxTotalRub` остаётся жёстким пределом. Если готовые варианты отличаются от цели более чем на 30%, поиск может выполнить один дополнительный запрос по ценовому уровню. Конструктор показывает отклонение, категорию номера, подтверждённые фото, адрес и отдельные ссылки на цену и сайт гостиницы.

Финализация прикладывает сохранённые метаданные и проверяет до двух первых вариантов в пределах общего дедлайна. На задачу предусмотрено до двух поисковых запросов, шести чтений страниц и 18 секунд на финализацию. Результаты сохраняются в каталоге. После неполной попытки следующая проверка этого объекта возможна через сутки. Для локальной диагностики можно отключить этап с `HOTEL_ENRICHMENT=off`.

При неполном каталоге Geoapify находит жильё в выбранной локации. Russhotels добавляет посуточные ставки для России по одноимённым объектам с проверенными адресами или координатами. Веб-поиск закрывает пробелы и добавляет варианты, включая гостевые дома и хостелы с отдельными комнатами. [Geoapify Places](https://apidocs.geoapify.com/docs/places/index.html) · [Russhotels hotel/index](https://wiki.russhotels.ru/doku.php?id=site:api#поиск_отелейпредложений_index)

Одновременно в БД захватываются до трёх гостиничных задач. Захват действует 18 секунд и продлевается каждые 6 секунд. Лимит исполнения с момента первого захвата составляет 210 секунд и включает Stage 1 и повторы. Конструктор опрашивает каждую задачу до 300 секунд. Профиль `HOTEL_SEARCH_PROFILE=A` ограничивает гостиничный поиск 7 Search, 5 Fetch и 6 Flash, 150 000 байтами входа и резервом 18 000 выходных токенов. Профиль B по умолчанию применяет те же начальные пределы и разрешает до 10 Search, 8 Fetch и 10 Flash, 240 000 байт и 30 000 выходных токенов для конкретного объекта или локальной страницы с тарифом, пока пакет неполон. Учитываются физические попытки, включая прерванные. Для геокодирования и Places доступно по одному обращению, для Russhotels и ЦБ — до двух. При аномально низкой ставке Russhotels по сравнению с другими гостиницами города нужен второй источник. Разбор Stage 1 учитывается отдельно с его лимитами и переиспользованием.

Планировщик проверяет вместимость следующего пакета до Search и Fetch и сокращает пакет до одного номера или предложения при малом остатке. Точный повтор с новым `taskId` может использовать успешные ответы предыдущей задачи того же аккаунта в течение 30 минут. Физические вызовы и фактические токены в журнале относятся к текущей задаче. При неполной выдаче журнал показывает использованный и доступный объём, этап остановки и число объектов с подтверждённой ценой.

Цена формируется по трём уровням. Сначала используется применимый тариф предложения. Если известна ночная цена всего частного номера другой вместимости, она служит ориентиром за одну комнату без деления на число мест. Если своей цены нет, берётся медиана ставок минимум двух разных местных объектов того же типа. Подбор предпочитает близкий район и сопоставимый класс, а при неполной звёздности может использовать подходящие ставки по городу. Диагностика хранит источники, курс, доноров и разброс оценок. Для иностранной валюты сохраняются номинал, значение и дата курса Банка России. Документ используется до шести часов. При сбое обновления подходит подтверждённый снимок, полученный в последние трое суток. Итог округляется вверх после расчёта на всю группу. Цена «от» и цена по аналогам служат ориентирами. Покрытие зависит от опубликованных страниц и доступности поискового сервиса. [DeepSeek Search и Fetch](https://api-docs.deepseek.com/guides/search/) · [Методика Stage 2](docs/STAGE-2-HOTELS.md)

Блок тарифа сохраняет исходную запись суммы, дословные строки номера, условия и период действия. Даты поездки определяют число ночей. Ставка за номер за ночь с другого периода может служить ориентиром. Неприменимые цены за пакет или всё проживание исключаются из расчёта. Доступность проверяется отдельно по явному подтверждению дат и числа одноместных номеров. При прочих равных подтверждённые варианты показываются раньше неизвестных, а варианты с явным отсутствием мест — после них. Старые ставки перепроверяются перед новой выдачей, а завершённые задачи остаются историческими снимками.

## Размещение на Render

Действующий сервис развёрнут на Render. Его контракт соответствует последнему выпуску `deploy/api`. Для нового размещения создайте Web Service и PostgreSQL в одном регионе. Для первого размещения используйте пустую базу. Бесплатная Render Postgres истекает через 30 дней. [Условия тарифа](https://render.com/docs/free#30-day-limit) · [Кабинет на Render](https://tripflow-api-x1p5.onrender.com/portal) · [Swagger на Render](https://tripflow-api-x1p5.onrender.com/docs)

| Поле Web Service | Значение |
|---|---|
| Branch | `deploy/api` |
| Language | Docker |
| Root Directory | Оставить пустым |
| Dockerfile Path | `API/Dockerfile` |
| Docker Build Context Directory | Корень репозитория (`.`) |
| Health Check Path | `/health` |
| Auto-Deploy | On Commit |

Dockerfile читает `shared/data/destinations.json` из общего каталога, поэтому контекст сборки должен включать весь репозиторий. Контейнер слушает выданный Render порт `PORT`. [Docker на Render](https://render.com/docs/docker) · [Автоматический деплой](https://render.com/docs/deploys#auto-deploys)

В Environment веб-сервиса укажите `DATABASE_URL` со значением **Internal Database URL**. Для создания владельца в пустой базе временно задайте `TRIPFLOW_PORTAL_ADMIN_EMAIL` и новый `TRIPFLOW_PORTAL_ADMIN_PASSWORD`. После первого успешного входа на `/portal` удалите эти две переменные и примените изменения. Аккаунт и его роль сохранятся в PostgreSQL. [Подключение PostgreSQL](https://render.com/docs/postgresql-creating-connecting)

После успешного деплоя откройте `/health` и `/portal` по адресу веб-сервиса. Когда одобрите заявку и выпустите ключ, проверьте полный цикл создания и чтения задачи через `/docs`.

## Выпуск новой версии

Рабочие изменения команды продолжают попадать в `main`. Render следит за `deploy/api`. После проверки версии из чистого рабочего дерева обновите ветку размещения выбранным коммитом из `main`.

~~~powershell
git fetch origin
git switch deploy/api
git merge --ff-only origin/deploy/api
git merge --ff-only origin/main
git push origin deploy/api
git switch main
~~~

Этот вариант выпускает текущую версию `origin/main`. Чтобы выпустить более ранний проверенный коммит, укажите его SHA вместо `origin/main` во второй команде merge. Если ветка размещения ещё не создана локально, используйте `git switch --track origin/deploy/api` при первом выпуске.

## Кабинет разработчика

Пошаговые действия для разработчика и владельца описаны в гайде. [Гайд по порталу на Render](docs/PORTAL.md)

1. Разработчик открывает кабинет, выбирает «Запросить доступ» и задаёт email и пароль. Если заявка ещё рассматривается или отклонена, статус отображается при входе. После одобрения можно войти с теми же данными.
2. Владелец и администраторы рассматривают обычные заявки. Владелец назначает администратора из одобренных разработчиков и может снять эту роль. Администратор видит только аккаунты разработчиков.
3. При отключении сессии и ключ отзываются, роль администратора снимается. Для восстановления пользователь заново подаёт заявку с прежними email и паролем. Её рассматривает владелец. История задач и метрики остаются в аккаунте.
4. Одобренный разработчик выпускает один ключ. Он передаёт ключ в `X-API-Key` при создании задачи и чтении результата. Полное значение показывается при выпуске. Перевыпуск и отзыв сразу отключают прежний ключ.
5. Журнал разработчика показывает последние 30 задач и общие счётчики. В карточке аккаунта откройте «Активность API». Видны число запросов за 24 часовых интервала, запуски, опросы, HTTP-ошибки и максимальное число запросов за час за семь дней. Учитываются запросы к трём маршрутам задач с действующим ключом. Расчёт задач и чтение их результатов видны раздельно. Счётчики измеряют нагрузку, квот на запросы задач нет. Попытки входа и подачи заявки ограничиваются отдельно.

Проверить подбор и смету можно через [конструктор карточки](docs/PORTAL.md#конструктор-карточки) в кабинете. Он работает по сессии кабинета и сохраняет задачи в общий журнал аккаунта.

## Проверка в Swagger

Откройте Swagger на том адресе, который проверяете. Примеры в нём соответствуют запущенной сборке. [Проверка на Render](docs/PORTAL.md#проверка-api-через-render)

Откройте Swagger UI по пути `/docs`, нажмите **Authorize** и вставьте выпущенный ключ. В `POST /v1/recommendations` выберите пример «Отели» или «Достопримечательности», затем **Try it out → Execute**. В `POST /v1/budget` есть пример сметы. У каждого примера свой `taskId`. В рекомендациях `targets` содержит одну категорию. Обязательные `refinement` и `excludedObjectIds` можно передать как `null`, а для исключений подходит и `[]`.

POST отвечает `202`. Выполните `GET /v1/tasks/{taskId}` с тем же ключом. При `pending` повторите через указанное в `Retry-After` число секунд. При `completed` читайте `result`. Сохраните пригодные варианты при `partial`. Новый набор входных данных требует нового ID. C# достаточно исходящего HTTPS к Python API. [Контракт и примеры](docs/BACKEND-HANDOFF.md)

## Тесты

Из каталога `API` установите зависимости для тестов и запустите проверки.

~~~powershell
python -m pip install -r requirements-test.txt
python -m unittest discover -s tests -v
~~~

По умолчанию тесты работают с временной SQLite. Для отдельной тестовой PostgreSQL задайте `TRIPFLOW_TEST_DATABASE_URL` с правом создания схем. Тесты подменяют Geoapify, DeepSeek и Банк России на границе HTTP и не расходуют баланс поставщиков.
