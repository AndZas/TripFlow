## Текущий результат

LM Studio отвечает на `127.0.0.1:1234`. Установлена и загружена Qwen3-4B-Instruct-2507, GGUF `Q4_K_M`, с идентификатором API `tripflow-qwen3-4b`. Ускоренная загрузка по частям завершилась, SHA-256 совпал с опубликованным. Файл импортирован в настроенный каталог `F:\Files\LanguageModels`. Приложение сообщило об успешной загрузке модели за 9,71 с. Контекст выставлен на 4096 токенов, при загрузке использован `--gpu max`. В отдельном замере сразу после загрузки `nvidia-smi` показал 4107 МиБ занятой видеопамяти на RTX 5060 Ti из 8151 МиБ. Это общая занятость GPU, включая другие процессы, без измерения пика при генерации.

**Финальная версия харнеса прошла 21 из 21 живого прогона.** Это семь сценариев по три повтора на сохранённых данных по Москве. Также прошли все девять проверок Python с имитацией успешных и ошибочных ответов LM Studio.

## Как устроен эксперимент

- [harness.py](harness.py) хранит системные промпты, JSON Schema, разрешённые функции и правила проверки. LM Studio принимает массив `tools` через `POST /v1/chat/completions`. Python читает `message.tool_calls`, проверяет аргументы и выполняет функцию. В текущем варианте на шаге доступна ровно одна функция с `tool_choice: "required"`. Результаты всех функций передаются модели компактным блоком данных в отдельном запросе. В исходном варианте проверялась и передача результата через `role: "tool"` с `tool_call_id` при многошаговом поиске.
- [providers.py](providers.py) читает сохранённые ответы поставщиков для Москвы. `search_hotels` возвращает отели Russhotels, `search_attractions` принимает категории `museums`, `nature` и `historic` и читает выборки Geoapify, `get_budget_rates` возвращает московскую ставку Росстата по билетам в музеи и на выставки. Снимки в репозитории позволяют прогонять одни и те же данные без ключей и зависимости от внешней сети.
- [experiment.py](experiment.py) отправляет семь контрольных сценариев. JSONL содержит входные данные, проверенные вызовы, результаты функций, ответы LM Studio, проверки по сценарию и длительность. Каждый запуск получает отдельный файл в `runs/`.
- [test_harness.py](test_harness.py) проверяет харнес с имитацией HTTP-ответов. В частности, текст с тегом `<tool_call>` отклоняется. При штатном вызове LM Studio сам разбирает служебный формат модели, а Python разбирает только JSON аргументов и решения. [LM Studio Tool Use](https://lmstudio.ai/docs/developer/openai-compat/tools)

Для полной генерации доступны все три инструмента. При догенерации доступен поиск одного целевого типа. Город, число путешественников, ночи, исключения и лимит берутся из сценария Python. Модель выбирает категории, порядок кандидатов и число платных посещений, когда оно следует из текста. Для решения используется отдельный запрос с `response_format: json_schema`. Python проверяет, что порядок содержит ровно ID полученной выдачи и что число посещений в допустимом диапазоне. Этот диапазон — ограничение эксперимента, максимум два посещения на день. Ошибки протоколируются. Запасная сортировка в эксперименте отключена, чтобы было видно каждый сбой.

### Контрольные сценарии

| Сценарий | Критерий |
|---|---|
| `two-museums` и `four-museums` | Одинаковый поиск музеев и парков, но две разные оценки на одну группу. Ставка 500,37 ₽ округляется до 501 ₽ на человека за посещение. Для троих ожидаются 3 006 ₽ и 6 012 ₽ соответственно |
| `unclear-visit-count` | Поиск музеев, число посещений остаётся `null`, если пользователь оставил решение на потом |
| `parks-refinement` | Уточнение «только парки» побеждает исходное «только музеи». Единственный именованный парк исключён, поэтому выдача должна быть пустой |
| `budget-hotel` | Python убирает выбранное исключение и варианты дороже 65 000 ₽ на группу за пять ночей. Остаётся «Славянка» с ориентиром 50 850 ₽ |
| `rank-hotels` | По запросу «от самого дешёвого» модель возвращает порядок «Гостиный дом», «Славянка», «Золотое кольцо» |
| `empty-hotel` | При лимите 10 000 ₽ все кандидаты отфильтрованы. Модель возвращает пустой список ID |

Проверка формата и проверка смысла различаются. Например, вызов поиска музеев при уточнении «только парки» технически валиден, но сценарий отмечает его как ошибку подбора. Аналогично, валидное число посещений может оказаться неверным. В тестах смысл сравнивается с ожидаемыми значениями, заданными для каждого контрольного запроса.

### Результаты живых прогонов

Во всех сериях использованы одни и те же семь запросов по три раза, температура 0, контекст 4096 токенов, максимум 320 токенов на ответ. Время ниже включает вызовы LM Studio и обработку Python от входа сценария до результата. Загрузка модели, скачивание весов и внешняя сеть в замер не входят. Первые две серии запускались с четырьмя слотами инференса, текущая серия после перезагрузки модели использует один слот. Скрипт во всех случаях отправляет запросы последовательно.

- **[Исходный харнес](runs/baseline.jsonl) — 12/21, медиана 1,15 с.** Все 12 догенераций прошли. Из девяти полных генераций пять раз модель вернула только часть ID, трижды ответила обычным текстом до выполнения всех инструментов и один раз исчерпала лимит ответа на фазе поиска.
- **[`tool_choice: "required"` и длина массивов в схеме](runs/bounded.jsonl) — 9/21, медиана 8,69 с.** Для пяти полных генераций, дошедших до итогового JSON, модель вернула все ID и правильное число посещений, но перепутала два соседних отеля по стоимости. Сортировка по цене также ошиблась во всех трёх отдельных сценариях сортировки. Три запроса с неясным числом посещений по-прежнему не дошли до решения. Ещё в одном запросе сервер вернул HTTP 400 с `Engine protocol predict request failed: fetch failed`. Причину сбоя не установили. Отдельный пробный вызов показал, что сервер принимает строку `"required"` и отклоняет объект с именем принудительно выбранной функции.
- **[Фиксированные шаги поиска и исходная сортировка в Python](runs/stepwise.jsonl) — 21/21, медиана 2,75 с.** Получены 39 валидных `tool_calls` и 21 итоговое решение. Полная генерация заняла от 2,72 до 29,01 с, медиана 3,06 с. Догенерация заняла от 0,98 до 4,27 с, медиана 1,28 с. Три самые долгие полные генерации пришлись на первый повтор после перезагрузки модели. Серии проверяют работу конфигураций целиком. Из них нельзя выделить влияние каждого изменения на скорость.

В итоговом прогоне на «два платных музея и парки» Qwen запросила `search_attractions({"categories":["museums","nature"]})` и вернула `paidMuseumVisitsPerPerson: 2`. Для «четыре платных музея» она вернула `4` при тех же категориях. Python подставил городскую ставку и получил 3 006 ₽ и 6 012 ₽ на троих. Для «решим на месте» модель оставила число `null`. Все три случая повторились без расхождений. В итоговом прогоне правильный порядок отелей показывает, что модель сохранила переданный порядок по цене. Самостоятельное числовое ранжирование оказалось нестабильным в предыдущей серии.

## Запуск

В PowerShell из корня TripFlow:

```powershell
Set-Location API/experiments/lmstudio-tripflow
python -m venv .venv
.\.venv\Scripts\python.exe -X utf8 -m unittest -v
```

Зависимости эксперимента входят в стандартную библиотеку Python. Если модель выгружена, а сервер LM Studio работает, её можно загрузить так:

```powershell
& ~/.lmstudio/bin/lms.exe load qwen3-4b-instruct-2507-tripflow --gpu max --context-length 4096 --parallel 1 --identifier tripflow-qwen3-4b
```

Живой прогон:

```powershell
.\.venv\Scripts\python.exe -X utf8 experiment.py --case two-museums
.\.venv\Scripts\python.exe -X utf8 experiment.py --repeat 3
```

По умолчанию порт `1234`. При необходимости он задаётся через `--port`, модель через `--model`. Если включена авторизация LM Studio, скрипт читает токен из переменной `TRIPFLOW_LMSTUDIO_TOKEN`. Токен не включается в журнал.

## Границы и выводы для TripFlow

Сценарии используют Москву и короткие сохранённые выборки. Тарифы отелей взяты из снимка опубликованных цен Russhotels для одноместного размещения. На даты поездки наличие и цены не проверялись. Билеты с неизвестной ценой остаются `null`. Общая ставка Росстата используется только для оценки группы, без записи в цену конкретного места. Живых обращений к Geoapify или Russhotels в этом этапе не было.

Qwen3-4B в LM Studio подходит для следующего прототипа с управляемым сценарием. Стоит использовать модель для извлечения пожеланий из текста и выбора категорий. Сортировка по известной цене, фильтры и денежные формулы однозначно выполняются Python. Для оценки содержательного ранжирования понадобится более широкий набор запросов и проверяемые характеристики вариантов.

Текущий контракт даёт нужные входные поля и `admission.suggestedVisitsPerPerson`. Для опыта использованы внутренние ID кандидатов и исключений. В рабочем API исключения нужно сопоставлять по имени и координатам, как описано в контракте. Прототип считает только музейную часть оценки. Полный бюджет, `hasMore` по поиску поставщика и отправка callback в C# требуют отдельной реализации. Если модель возвращает `null` для неясного числа посещений, команде ещё нужно определить правило по умолчанию или ошибку задачи. [Контракт](../../CONTRACT.md)

Модель установлена из [репозитория LM Studio Community](https://huggingface.co/lmstudio-community/Qwen3-4B-Instruct-2507-GGUF), ревизия `4edb920b6f14e3b9284d4502a6485103d72cde05`, SHA-256 `8cdb57cbb880d313736a9bc4e3d3d2485f145b5e19cf33783746e753e82641fc`. Прямой запуск GGUF через Python и облачные модели в этот этап сравнения не входили.
