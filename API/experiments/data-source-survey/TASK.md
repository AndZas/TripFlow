# Задание для Codex: разведочный эксперимент по API данных для TripFlow

## Цель

Исследовать доступные источники данных, необходимые Python API проекта TripFlow, и подготовить воспроизводимый Python-скрипт, который делает безопасные пробные запросы к доступным источникам и показывает:

- какие параметры можно передать;
- какие фильтры и способы поиска поддерживаются;
- какие данные фактически приходят в ответе;
- какие поля отсутствуют или нестабильны;
- каковы ограничения доступа, бесплатного использования, лицензии и стоимость.

Это разведочный эксперимент, а не реализация production API TripFlow. Не подключать результат к основному приложению и не принимать за команду уже утверждённую архитектуру или поставщика.

## Контекст продукта

TripFlow — курсовой веб-сервис для совместного планирования путешествий. Python API — предполагаемый сервис, который будет помогать C# backend получать реальные данные о направлении, жилье и интересных местах. В перспективе данные могут использоваться при оценке бюджета.

На этом этапе AI не исследуется. Требуется понять, какие реальные данные возможно получить обычными запросами к источникам. AI не должен использоваться для генерации или подстановки отсутствующих объектов, цен и фактов.

Итоги эксперимента должны помочь команде определить границы будущего Python API и понять, какие данные нужно будет получать из внешних источников, а какие можно хранить или рассчитывать отдельно.

## Ограничения и правила

1. **Не тратить деньги.** Не выполнять платные запросы, не переходить в платный production-тариф и не запускать операции, которые могут повлечь оплату. Для тарифа с неясной ценой остановиться на изучении официальной документации и пометить его как требующий ручной проверки. Условный предел команды — 100 рублей; в рамках этого задания безопаснее считать бюджет платных запросов равным нулю.
2. **Не создавать аккаунты от имени пользователя и не принимать условия поставщиков.** Если API требует регистрации, партнёрского статуса, ключа или ручного одобрения, записать это как требование. Можно использовать уже доступные локальные ключи, если они присутствуют.
3. Не просить пользователя вставлять секреты в чат. Ключи читать только из локального `.env`, переменных окружения или другого явно локального файла конфигурации. Не печатать их, не сохранять в примерах ответов и не коммитить.
4. Не публиковать реальные токены, персональные данные или необработанные ответы, если правила источника запрещают их хранение. Сохранять только небольшие примеры, необходимые для сравнения, с очисткой секретных полей.
5. Использовать официальную документацию и условия поставщика как источник сведений о квотах, цене, атрибуции и правах использования. Фиксировать дату проверки и ссылки.
6. Не парсить сайты и не обходить ограничения API. Для парсинга достаточно изучить условия использования кандидатов и описать вывод; реализацию парсера не начинать.
7. Не делать параллельные или массовые запросы. Использовать небольшое количество последовательных запросов с ограничением частоты и таймаутом.
8. Если доступ к API невозможен, скрипт должен корректно пропустить источник и указать причину. Не подменять живые данные фиктивными и не выдавать документационный пример за результат реального запроса.

## Объём исследования

Рассмотреть кандидатов ниже. Это целевой обзор подходящих источников, а не обещание перечислить абсолютно все существующие API. При обнаружении релевантной альтернативы можно добавить её с кратким обоснованием.

### 1. Интересные места (POI)

Проверить в первую очередь:

- OpenStreetMap через публичный Overpass API — музеи, исторические места, парки/природные места, смотровые площадки и рестораны;
- Geoapify Places — те же категории через единый API;
- OpenTripMap — туристические POI и подробности об объекте, если удастся проверить доступ и актуальную квоту.

Дополнительно исследовать по документации, не подключая платный тариф:

- Foursquare Places;
- Google Places;
- Tripadvisor Content API;
- Yelp Places — особенно для ресторанов.

Проверить, какие категории и атрибуты реально доступны (например, кухня/тип заведения, координаты, адрес, сайт, описание, изображение, рейтинг, плата за вход, часы работы). Не предполагать, что любой источник содержит всё это. Отдельно отметить, что «местная кухня» обычно определяется данными конкретного ресторана, а не универсальным полем для города.

### 2. Жильё

Проверить:

- Amadeus Self-Service Hotel List и Hotel Search: отдельно каталог отелей и наличие ценовых предложений;
- Geoapify Places и/или OSM как бесплатный справочник объектов размещения, не предполагая наличия тарифов и доступности;
- Booking.com Demand API и Expedia Rapid — по официальной документации и требованиям к партнёрскому доступу.

Для каждого источника явно разделить:

- сведения об объекте размещения;
- цену на конкретные даты;
- доступность номера;
- число гостей/номеров;
- валюту и состав цены (налоги/сборы, цена за ночь или за всё проживание).

Наличие отеля в каталоге не считать доказательством наличия свободного номера или цены.

### 3. Городские и справочные данные

Проверить варианты получения:

- названия и координат города, страны и кода страны;
- часового пояса в формате IANA;
- валюты страны и её ISO 4217 кода;
- обменного курса и даты курса, если такую конвертацию поддерживает источник.

Кандидаты: GeoNames и Open-Meteo Geocoding для геокодирования/часового пояса; ISO 4217/CLDR или иной поддерживаемый справочник для валюты; Frankfurter для обменных курсов. Отдельно оценить, можно ли получать часовой пояс локально по координатам без отдельного сетевого API.

Погода не является обязательной частью текущего эксперимента. Open-Meteo можно кратко описать как возможный источник, отдельно указав ограничения бесплатного использования и лицензию.

### 4. Визы и документы для въезда

Изучить Sherpa Requirements API, Visafar API и доступные официальные государственные источники. На этом этапе определить только:

- какие входные данные нужны (гражданство/тип паспорта, страна назначения, резидентство, цель, даты, транзит, уже имеющиеся визы/ВНЖ);
- какие типы требований возвращаются (виза, электронное разрешение, паспортные правила, иные документы);
- доступность документации, тестового доступа, ключа и тарифов;
- можно ли использовать результат в приложении и требуется ли подтверждать его ссылкой на официальный источник.

Не запрашивать реальные визовые требования для пользователя и не делать вывод о его гражданстве. Визовые правила зависят от профиля путешественника и должны быть помечены как потенциально изменчивые; не представлять экспериментальный результат как официальную консультацию.

## Единый сценарий пробных запросов

Использовать **Париж, Франция** как фиксированный демонстрационный город, если API поддерживает этот поиск. Для API, которым нужны координаты, сначала получить координаты через проверяемый источник или указать явно приведённые в отчёте координаты с источником.

Для поиска POI выполнить небольшие последовательные запросы по категориям:

1. музеи;
2. исторические/культурные объекты;
3. парки, природные места или смотровые точки;
4. рестораны/кафе.

Ограничить выдачу примерно 10–20 объектами на запрос, если API это позволяет. Для 2–3 результатов запросить дополнительные детали, только если это отдельный недорогой или бесплатный endpoint и его использование допустимо.

Для жилья проверить каталог по городу. Для API с гостиничными предложениями задать один номер, двух взрослых и проживание на две ночи в будущем: check-in = дата запуска + 30 дней, check-out = check-in + 2 дня. Убедиться, что даты вычисляются в коде и параметры передаются в формате, который требует API. Цель — проверить схему и фактическое наличие/цену, не бронировать жильё.

Для городских данных запросить Париж и записать координаты, ISO-код страны, IANA timezone и валюту/код валюты, если источник их возвращает. Для курса запросить EUR к RUB, только если это разрешено источником и бесплатно; сохранить дату курса.

Для визовых API выполнить только безопасную проверку документации/схемы и доступности тестового endpoint. Если для реального запроса необходим профиль паспорта, не подбирать гражданство самостоятельно: ограничиться схемой запроса либо использовать только публичный пример поставщика и пометить его как пример.

## Что должен делать скрипт

Создать простой запускаемый Python-скрипт или небольшую CLI-команду, которая:

- последовательно вызывает только настроенные и доступные бесплатные endpoints;
- читает ключи из окружения; отсутствие ключа не прерывает весь запуск;
- задаёт короткий таймаут, аккуратно обрабатывает ошибки сети, HTTP 401/403/404/429/5xx и пустые ответы;
- измеряет время ответа и записывает HTTP-статус;
- показывает сводку по каждому endpoint: имя провайдера, endpoint, параметры запроса (без секретов), фильтры, статус, длительность, количество объектов и список фактических полей;
- позволяет увидеть небольшой очищенный пример JSON-ответа;
- показывает, какие поля отсутствуют, в частности цена/валюта/изображение/рейтинг/сайт и цена/наличие отеля;
- различает реальные ответы и выводы только по документации;
- не выполняет бронирование, регистрацию или платные операции.

Для нормализованного представления можно использовать поля:

```text
provider
external_id
name
category
latitude
longitude
address
description
website_url
image_url
rating
price_amount
price_currency
price_period_or_total
availability
source_url
retrieved_at
raw_fields
```

Поля, которых нет в ответе, оставлять пустыми/`null`. Не вычислять выдуманные значения и не смешивать рейтинг с оценкой AI.

## Изоляция эксперимента

Этот эксперимент должен быть автономным и не менять существующие корневые документы или будущие папки frontend/backend. Рекомендуемая структура:

```text
API/
  experiments/
    data-source-survey/
      TASK.md
      README.md
      pyproject.toml                 # или requirements.txt, выбрать один способ
      .env.example
      .gitignore
      src/
        ...                          # код запросов и формирования отчёта
      data/
        samples/                     # только маленькие очищенные JSON-примеры
      reports/
        comparison.md
```

Использовать отдельное виртуальное окружение внутри этого эксперимента. Не ставить зависимости глобально. Реальные `.env` и секреты исключить через `.gitignore`. Не добавлять тяжёлые сырые выгрузки. Если создание virtualenv или установка зависимости невозможны из-за ограничений среды, описать это и не обходить ограничения.

## Ожидаемые результаты

1. Запускаемый скрипт, который показывает сводку и примеры ответов доступных API.
2. `README.md` с командами установки/запуска в Windows PowerShell и описанием переменных окружения.
3. `reports/comparison.md` с таблицей по каждому кандидату:
   - назначение и категории;
   - query-параметры и поддерживаемые фильтры;
   - поля ответа и доля заполнения ключевых полей в небольшой выборке;
   - цена, валюта и доступность для отелей;
   - время ответа и ошибки при пробных запросах;
   - регистрация/ключ/партнёрство;
   - бесплатная квота, цена сверх неё, лимиты, атрибуция и лицензия;
   - ограничения покрытия, свежести и использования данных;
   - рекомендация: подходит, частично подходит или не подходит для TripFlow и почему.
4. Краткий вывод о возможном разделении интеграций: POI, отели с ценами, справочные данные, визовые сведения.
5. Список открытых вопросов для команды и конкретный перечень API-ключей, которые потребуется получить вручную для дальнейшей проверки.

## Критерии завершения

- Скрипт запускается без ключей и всё равно выдаёт полезный отчёт о keyless API и недоступных источниках.
- Если ключи доступны, сделаны только небольшие бесплатные пробные запросы и результат явно помечен как живой ответ.
- Сводка показывает параметры запроса и реальные поля ответа, чтобы разработчик мог понять, что принимает и возвращает каждый API.
- Все сведения о тарифах и ограничениях снабжены ссылками на официальные страницы и датой проверки.
- Никаких платежей, бронирований, скрытого скрейпинга или секретов в Git.
- Описаны ограничения исследования; не заявляется, что API были реально проверены, если был изучен только их документационный контракт.

## Рекомендуемый порядок работы

1. Проверить актуальность официальной документации кандидатов и заполнить таблицу доступа/тарифов до вызова API.
2. Реализовать и запустить сначала бесплатные запросы без ключа и те endpoints, для которых локально уже есть ключ.
3. Сохранить малые очищенные примеры, подготовить сводку по фактическим полям и ограничениям.
4. Запустить скрипт повторно без ключей, чтобы проверить, что он корректно пропускает защищённые API.
5. В конце показать пользователю, что удалось проверить живыми запросами, что осталось только на уровне документации и какие ключи/API решения нужны дальше.
