# Задание: эксперимент по бесплатным API для недостающих данных TripFlow

- **Тип работы:** отдельный воспроизводимый исследовательский эксперимент; не production-интеграция.
- **Дата подготовки:** 27.10.2026.
- **Область:** только официальные API и публичные машинные API. Парсинг HTML, браузерная автоматизация, скрейпинг, обход ограничений и неофициальные endpoint'ы запрещены.
- **Цель по стоимости:** никаких платежей, подписок, платных тарифов, платных пробных периодов или запросов с риском списания. Не привязывать платёжную карту и не активировать биллинг.

## 1. Цель эксперимента

Проверить, могут ли доступные бесплатно API закрыть поля TripFlow, которые остались редкими или отсутствующими после предыдущих тестов:

1. Цены/тарифы на вход в реальные достопримечательности и туристические активности.
2. Фотографии, краткие описания и официальные ссылки к достопримечательностям, если их можно сопоставить с существующими кандидатами.
3. Каталог жилья, статические сведения о нём и ориентировочная/минимальная цена проживания, если API действительно возвращает цену.
4. Другие полезные метаданные, только если их даёт один из проверяемых API и они не дублируют надёжно закрытые поля.

Нужно установить не только факт успешного HTTP-ответа, но и **полезность ответа для контракта TripFlow**: заполненность полей, точность сопоставления объектов, ценовую семантику, ограничения бесплатного плана, лицензию/атрибуцию и практическую готовность использовать источник.

Не искать и не тестировать парсеры в этом эксперименте. Если API для поля не найден или его бесплатный доступ не подтверждается, зафиксировать пробел и остановиться на выводе «API-кандидат не подтверждён».

## 3. Кандидаты для этого эксперимента

Сначала перепроверить в официальной документации цену, доступность и условия каждого кандидата **на дату эксперимента**. В живом режиме разрешены только API, для которых бесплатность конкретного тестового сценария установлена и запросы не могут превысить бесплатную квоту.

### 3.1 DATAtourisme API — обязательный кандидат для Франции

- Официальная документация: <https://api.datatourisme.fr/v1/docs>
- Получение ключа и правила: <https://www.datatourisme.fr/faq/> и <https://www.datatourisme.fr/utiliser-les-donnees>
- API бесплатен по опубликованным условиям, но для ключа нужна регистрация/заявка. Пользователь получает ключ самостоятельно. Код должен быть готов к `DATATOURISME_API_KEY`.
- Это каталог туристических POI Франции, агрегирующий территориальные базы. Проверить, какие сущности/типы реально возвращаются для достопримечательностей, музеев, мероприятий, туристических предложений и жилья.
- Особо проверить, есть ли у найденных POI `offers`, `priceSpecification`, числовой `minPrice`/иные тарифные поля, обозначение бесплатного посещения, валюту/период/единицу тарифа, даты актуальности, ссылку на первоисточник, описание, часы, географию и изображение.
- Наличие поля в схеме **не означает**, что оно заполнено у конкретной записи. Не превращать цену «от», диапазон или тариф иной единицы в цену билета на человека без достаточных данных.
- Запрашивать несколько французских городов (минимум Париж и ещё два города с туристическими POI), выборочно музеи/достопримечательности и жильё. Ограничить объём запросов и страниц.
- Задокументировать квоту, атрибуцию данных и фотографий. Если источник требует указать автора/обновление, предложить, как выполнить атрибуцию в проекте; не терять эти данные из сырых/нормализованных samples.

### 3.2 Amadeus Self-Service Test API — обязательный кандидат только в sandbox

- Официальные материалы: <https://amadeus4dev.github.io/developer-guides/> и <https://amadeus4dev.github.io/developer-guides/test-data/>
- На момент подготовки документа официальные материалы описывают бесплатное ограниченное тестовое окружение с кешированными/ограниченными данными и API для Hotels и Destination Experiences. Повторно подтвердить это перед вызовами.
- Зарегистрировать пользователя должен владелец проекта сам. Код подготовить для переменных `AMADEUS_CLIENT_ID` и `AMADEUS_CLIENT_SECRET`.
- Использовать **только** test host и sandbox-данные. Production host, переключение в Production, платные вызовы, бронирование, prebook, заказ активности, создание заказа и любые операции оплаты запрещены.
- Проверить безопасные read-only сценарии:
  - Hotel List / поиск каталога отелей для поддерживаемых тестовой документацией городов (например, LON/NYC, если эти коды остаются официально валидными). Измерить название, координаты, адрес/категорию/официальный сайт/описание/изображение, если поля действительно присутствуют.
  - Hotel Search/Offers в пределах документированных sandbox-данных — только если запрос без бронирования и API не может инициировать платную операцию. Проверить даты/размещение, цену/валюту/налоги/период, доступность и ограничения. Помечать результат как sandbox fixture, не как рыночную актуальную цену.
  - Tours and Activities / Destination Experiences для нескольких поддерживаемых тестом городов. Определить, возвращаются ли конкретные экскурсии/активности с ценой и чем такие предложения отличаются от цены входного билета в выбранную достопримечательность.
- Если API или интерфейс кабинета просит активировать биллинг, добавить карту, перейти на Production или принять условия с платными вызовами — остановиться, ничего не активировать; отметить этот endpoint как пропущенный по ограничению стоимости.
- Нельзя считать старые примеры/документацию доказательством доступности текущего тарифа. Зафиксировать разницу между sandbox и production.

### 3.3 Wikimedia Wikidata + Commons — условный кандидат для обогащения POI

- Официальные материалы: <https://www.wikidata.org/wiki/Wikidata:Data_access>, <https://commons.wikimedia.org/wiki/Help:Machine-readable_data>, <https://www.mediawiki.org/wiki/API:Imageinfo>, <https://www.mediawiki.org/wiki/Wikimedia_APIs/Access_policy>.
- Публичные read-only API не требуют ключа. Задать собственный `WIKIMEDIA_USER_AGENT` с реальным контактом владельца проекта. Не выдумывать email/URL.
- Предыдущее исследование отложило этот источник, так как не нашло надёжных связей с сохранёнными Geoapify samples. Поэтому проверить его только на небольшом заранее фиксированном наборе объектов с точными/однозначными названиями и географией, включая несколько объектов, для которых у базового источника не было фото или описания.
- Проверить точность entity/Commons-file match, описание/языки, прямые URL изображений, имя автора, лицензию, attribution/credit и размеры. Не считать найденное фото разрешённым к показу без проверки лицензии и требований атрибуции. Для неуверенного совпадения не прикреплять результат к объекту.
- Цены билетов и жильё от Wikimedia не ожидать; этот кандидат только про метаданные и изображения.
- При низком match rate сразу остановить дальнейшие запросы и описать ограничение, не расширять поиск до больших объёмов.

### 3.4 Кандидаты только для документальной оценки, без вызовов по умолчанию

- **Foursquare Places API:** текущая модель pay-as-you-go. Официальные материалы сообщают бесплатные ограниченные Pro-вызовы, а некоторые поля/endpoint'ы (включая фото) относятся к Premium. В рамках требования «без риска списания» по умолчанию не включать в live-run. Можно отметить как исключённый кандидат; включить только если на дату запуска доступен отдельный бесплатный sandbox с жёсткой квотой, который не требует биллинга и не может тарифицировать дальнейшие запросы.
- **Booking.com Demand API, Ostrovok API, Expedia Rapid, Viator/GetYourGuide/Tiqets и подобные:** только проверить официальные prerequisities/условия доступа и отметить, являются ли они публичными бесплатными API или требуют партнёрства/контракта. Не регистрироваться вместо пользователя и не запрашивать доступ от его имени. Не делать live-запрос, если нет явно подтверждённого бесплатного sandbox без биллинга и соответствующих ключей.
- **Google Places API:** не активировать и не вызывать в этом эксперименте, поскольку API требует включённого billing account и использует pay-as-you-go; бесплатный кредит/триал не удовлетворяет запрету на риск платежа.
- Не добавлять другие провайдеры автоматически. Любого нового кандидата сначала обосновать официальной документацией: какое конкретно недостающее поле он даёт, почему бесплатность гарантирована и что запрос не ведёт к оплате.

## 4. Целевые данные и определения

### Достопримечательность / активность

Проверить отдельно, не смешивая разные понятия:

- `admission_price_amount`: цена именно входного билета на место;
- `activity_price_amount`: цена экскурсии/тура/активности;
- `price_currency`;
- `price_basis`: за человека, за группу, за билет, за тур, за ночь, за номер, за посещение или неизвестно;
- `price_period_or_validity`: даты действия тарифа, если API их даёт;
- `is_free`: только если источник явно сообщает бесплатный вход; отсутствие цены не означает бесплатно;
- `price_source_url` и `price_updated_at`, если API отдаёт эти значения;
- название, краткое описание, категория, координаты, адрес, часы, сайт, изображение и сведения об авторе/лицензии фото.

Платная экскурсия вокруг объекта — не цена входного билета в сам музей/достопримечательность. Оценивать отдельно.

### Жильё

Проверить:

- реальный объект проживания и надёжный поставщицкий ID;
- название, категория, координаты/адрес, описание, фото, официальный URL;
- числовую цену и валюту;
- ценовую базу: за ночь или весь период; за номер/койко-место/человека; число гостей/номеров; включены ли налоги/сборы;
- даты пребывания, доступность тарифа, условия и timestamp, если API возвращает;
- можно ли аккуратно нормализовать цену в рубли и в согласованную для проекта базу «за ночь за одного путешественника».

Цена из sandbox, статический «от»-тариф и точная цена на даты — разные классы наблюдений. Сохранить это различие в отчёте/сыром результате для оценки качества теста, даже если будущий пользовательский контракт его не показывает. Если невозможно установить базу цены, не выдавать её как нормализованную цену за человека за ночь.

### Метаданные и изображение

Для фото сохранить лицензию/автора/credit/source page/период прав, если они доступны. Если лицензия или право использования неясны — пометить поле как «не пригодно для показа без проверки», но не присваивать изображение себе и не делать его основным результатом.

## 5. Эталонная выборка и сопоставление

- Не менять и не перезаписывать результаты прошлых экспериментов.
- Сначала использовать сохранённые POI samples из `../../free-api-gap-test/data/` и отчётов предыдущего запуска. Проверить фактическую структуру папок; не предполагать, что путь/образцы существуют, пока не проверено.
- В текущих предыдущих результатах малое число samples, поэтому кросс-провайдерную заполненность считать только на фиксированном наборе записей, для которых действительно возможен match. В отчёте отдельно указать размер набора и правила сопоставления.
- Для новых API использовать ограниченный сценарий по городам: минимум Париж для DATAtourisme и документированные тестовые города Amadeus; можно добавить Москву/Стамбул/Суздаль только там, где у источника есть данные/поддержка. Для мировой выборки не обобщать результат по Франции или sandbox-каталогам.
- Сопоставлять по точному внешнему ID, если он общий; иначе по нормализованному названию + расстоянию координат + типу объекта. Уверенное/возможное/неуверенное совпадение — отдельные категории. Нечёткие совпадения не должны повышать coverage.
- Не запускать массовое скачивание полного каталога или bulk dump, если оно не нужно и не подтверждено как доступное без оплаты.

## 6. Реализация тестового стенда

Создать в этой папке изолированный CLI, например `enrichment_test.py`, с простыми стандартными библиотеками Python, если нет существенной причины добавить зависимость. Не менять API приложения и код за пределами этой новой папки.

Обязательные режимы:

1. `--offline`: проверяет конфигурацию, структуру и отчётность, не делает HTTP-запросов.
2. `--live`: вызывает только источники, для которых доступны необходимые env-переменные и выполнена проверка официального бесплатного режима. Источник без ключа/разрешения получает явный `skipped_missing_config`, а не фиктивный ответ.
3. Выбор источников, например `--providers datatourisme amadeus wikimedia`; лимит запросов, лимит результатов, пауза между запросами и timeout настраиваемы, но есть безопасные верхние пределы в коде.

Требования к безопасности:

- Никаких ключей в исходниках, Markdown-отчётах, логах, JSON, traceback или командной строке. Секреты только из environment процесса.
- Не читать `.env` автоматически; добавить `.env.example` только с именами переменных и комментариями, без секретов. В README объяснить настройку env в PowerShell и то, что переменные должны быть доступны именно процессу Python/Codex.
- Проверять наличие переменных до сети. Не показывать значение или частичный префикс секрета даже при ошибке.
- Не выполнять бронирование, prebook, заказ/checkout, авторизацию пользователя, запись или модификацию данных у поставщика.
- При HTTP 401/403/429 прекратить вызовы к этому поставщику в текущем запуске; не делать автоматических повторов. На timeout/5xx записывать ошибку без цикла ретраев. Не логировать сырые тела ошибок, если там могут быть секреты.
- Применять строгие caps на количество запросов и результатов. Для Amadeus обращаться только к sandbox host, с проверкой host перед каждым запросом; production host блокировать программно.
- Если провайдер требует перейти на платный тариф/включить billing, CLI не продолжает этот маршрут. Любая неясность стоимости трактуется как `skipped_cost_not_verified`.
- Использовать в HTTP-запросах корректный `User-Agent`/контакт, если этого требует источник.
- Не выводить в HTML/Markdown пользовательские секреты или неочищенные error payload.

Рекомендуемые env имена:

```text
DATATOURISME_API_KEY=
AMADEUS_CLIENT_ID=
AMADEUS_CLIENT_SECRET=
WIKIMEDIA_USER_AGENT=
```

Не требовать Foursquare/Booking/Ostrovok/Google credentials для этого эксперимента. Они не входят в safe live-run по умолчанию.

## 7. Схема результатов и отчёты

Каждый запуск должен создавать новую папку `reports/runs/<UTC-id>/`, не перезаписывая прошлый результат. Сохранить:

- `results.json`: версии/endpoint'ы, город и категория, число запросов, HTTP status (без токенов), задержка, статус `ok/error/skipped_*`, количество результатов, заполненность каждого поля, match confidence, price basis/currency, ссылки и licensing metadata. Сырые ответы сохранять только если они безопасны; убрать секреты и персональные данные.
- `live-results.md`: таблицы и небольшая читабельная сводка по каждому источнику и городу.
- `samples/`: ограниченные очищенные примеры объектов с исходными полями для аудита маппинга.
- `reports/sources.md`: официальная документация, условия, тариф/квота, дата проверки, требование ключа, данные/ограничения/атрибуция.
- `reports/assessment.md`: общий вывод, обновляемый только явным итоговым шагом и с ссылкой на конкретный run.
- `README.md`: установка/запуск в PowerShell, где вручную зарегистрироваться и получить ключи, точные env имена, примеры безопасного запуска, лимиты и что отправить/передать в отдельный чат для live запуска. Не просить пользователя прислать ключ в чат.
- `.gitignore`: исключить виртуальное окружение, реальные `.env`, кэши, сырые чувствительные данные и локальные файлы запусков, если это принято в структуре экспериментов.

Отчёт должен показать для каждого provider/города:

- число записей и HTTP ошибки/пропуски;
- coverage и denominator для каждого поля (не считать пустое поле или страницу без кандидатов успешной записью);
- точность/уверенность match и число исключённых неоднозначных совпадений;
- у цен — число вариантов с ценой, с валютой, с известной базой цены и тех, что можно корректно привести к рублям / базису TripFlow;
- отдельный счёт для «входной билет» против «экскурсия/активность»;
- фотополя, которые реально пригодны к показу с точки зрения лицензии/атрибуции;
- задержки, лимиты и актуальность ответа;
- чёткое решение `use / optional / reject / not tested` для каждого поля.

Никакие проценты не представлять без знаменателя и границ тестовой выборки. Сравнивать кандидатов по одному и тому же набору мест только если match подтверждён.

## 8. Критерии завершения

Эксперимент завершён, когда:

1. Утверждён список кандидатов, каждый относится к конкретному пробелу; платные/партнёрские варианты отделены от бесплатных.
2. Есть работающий стенд с offline режимом и ограниченным live режимом, который не может отправить платный/booking-запрос.
3. Для доступных credentials сделан минимальный воспроизводимый live-run; отсутствующие ключи/поставщики ясно помечены, и пользователь получил точные инструкции, какие аккаунты/ключи завести самостоятельно.
4. Отчёты показывают фактическое качество/покрытие и ограничения, а не только перечисляют поля в документации.
5. Для недоступных API проведена документальная проверка официальной цены и требований доступа; причина неприменимости явно записана.
6. Ключи/секреты не попали ни в один артефакт. Вызовы не превышали бесплатные безопасные caps.
7. Не изменялись файлы API продукта, Frontend, backend и результаты предыдущих экспериментов.

Отдельно ответить:
