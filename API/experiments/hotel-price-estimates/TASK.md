# Задание: эксперимент по бесплатным ориентировочным ценам проживания

> **Статус: завершён 28.10.2026 по решению владельца проекта.** Кандидаты отклонены для текущего MVP по стоимости, доступу и неподтверждённым условиям использования. Живые запросы цен не выполнялись; предусмотренная ниже программа live-тестов прекращена, её критерии не объявляются выполненными. Исходное задание сохранено как исследовательский план. Итог и границы выводов — в [reports/assessment.md](reports/assessment.md). Выбор альтернативного способа оценки проживания отложен.

- **Тип работы:** изолированный исследовательский эксперимент, не production-интеграция.
- **Дата подготовки:** 27.10.2026.
- **Область:** только официальные API и документированные машинные интерфейсы. Не писать парсеры HTML, не автоматизировать браузер, не обращаться к скрытым/неофициальным endpoint'ам.
- **Стоимость:** не платить, не активировать платный тариф или trial с риском списания, не привязывать карту, не делать бронирование, предбронирование или оплату.

## 1. Цель

Проверить, можно ли получать пригодную для TripFlow **ориентировочную цену проживания**, при этом точная цена для будущего бронирования не требуется.

Порядок гипотез:

1. **Сначала** попробовать получить ориентировочную цену, привязанную к конкретному отелю из выдачи TripFlow.
2. Если подходящей цены на конкретный отель бесплатно получить нельзя, проверить **цену проживания по городу/направлению**. Такая цена не должна выглядеть как цена выбранного отеля: это отдельная оценка расходов на проживание для всей поездки.
3. Зафиксировать, что именно означает каждая найденная сумма: за ночь или весь период, за номер или за человека, средняя/медиана/минимальная, валюта, период/даты и сколько свежести/покрытия подтверждается источником.

В продукте пользователь не бронирует отель. Цена используется как примерный ориентир, а для актуальной информации пользователь переходит к самому отелю или поставщику. Нельзя представлять ориентировочную или устаревшую сумму как гарантированную цену бронирования.

## 3. Кандидаты и очередность

Перед запросами повторно проверить официальную документацию, актуальные лимиты, стоимость и условия использования. Если в бесплатности или праве использовать ответ есть сомнение, API можно исследовать документально, но live-запрос не выполнять.

### 3.1 Makcorps — первый кандидат для цены конкретного отеля

- Документация: <https://www.makcorps.com/documentation/>
- Бесплатный городской endpoint и его ограничения: <https://docs.hotelapi.co/free-hotel-api>
- Страница регистрации/текущий бесплатный лимит: <https://api.makcorps.com/register>
- Вендорская документация конкретных hotel/city endpoints: <https://www.makcorps.com/documentation/hotel-price-apis/> и <https://www.makcorps.com/documentation/hotel-api-search-by-hotel-id/>.

Проверить безопасные сценарии в таком порядке:

1. Получить информацию об остатке тестовых credits, если это не списывает credit.
2. Проверить бесплатный endpoint по городу: понять формат выдачи, число отелей, имена, поставщицкие цены, валюту и налоги. В документации для free endpoint указано, что дату/гостей задать нельзя, выбираются случайные будущие даты, число отелей ограничено. Эти условия перепроверить в актуальном аккаунте и документации.
3. Проверить, можно ли сопоставить 2–5 возвращённых отелей с небольшим набором существующих Geoapify гостиничных примеров по точному названию и географии. Нечёткое совпадение не считать успешной привязкой.
4. Только если в кабинете явно виден безрисковый бесплатный остаток и документация подтверждает бесплатность вызова, сделать небольшое число запросов на hotel-specific endpoint. Он может требовать hotel ID Makcorps и даты/число гостей; не вводить случайные даты как реальные данные пользователя. Зафиксировать, можно ли получить именно недатированный ориентир без перехода на платный план.
5. После каждого ограниченного запроса сверять остаток credits. Остановиться до исчерпания бесплатного лимита. **Не вызывать endpoint при неясном учёте credits, автоматически не повторять запросы и не включать overage/автопродление.**

На публичных страницах Makcorps в момент подготовки документа найдено несоответствие размера бесплатного пакета: регистрационная страница показывает 15 credits, главная страница может показывать другой размер. Фактическую квоту брать только из кабинета пользователя и не закладывать тест, превышающий минимально заявленный бесплатный лимит. Карта/оплата не вводятся.

Не предполагать, что Makcorps API разрешает любое хранение/показ цен третьим лицам. Найти официальные условия использования и записать, разрешён ли учебный некоммерческий проект, хранение/кэширование и показ цены с переходом на источник. Если правила неясны — итог `access_or_display_rights_unclear`, не подключать в MVP до уточнения.

### 3.2 Skyscanner Stays Indicative Prices — fallback для городской оценки

- Официальный overview: <https://developers.skyscanner.net/docs/hotels-indicative-prices/overview>
- Аутентификация/заявка на ключ: <https://developers.skyscanner.net/docs/getting-started/authentication>
- Локализация и поддерживаемые `market`, `locale`, `currency`: <https://developers.skyscanner.net/docs/getting-started/culture-service> и <https://developers.skyscanner.net/docs/getting-started/localisation>
- FAQ по распространению цен: <https://developers.skyscanner.net/docs/faqs>

API по документации возвращает агрегированные indicative prices по месту и диапазону дат, например cheapest/average/median и фильтры типа/категории размещения. Это **не цена конкретного отеля**. Источник описывает цены как кэшированные значения, построенные по поискам и обновляемые; сравнить данный факт с возвращёнными timestamps/ответом API, если они доступны.

Доступ требует заявки и одобрения Skyscanner. Нельзя создавать заявку от имени пользователя. Подготовить код и инструкции для `SKYSCANNER_API_KEY`, но выполнять live-запрос только если владелец проекта сам получил доступ и подтвердил, что:

- доступ и выбранный объём вызовов не создают оплаты или включённого биллинга;
- условия разрешают использование в учебном проекте;
- Skyscanner разрешает отображать indicative price в TripFlow при отсутствии перехода к бронированию непосредственно из TripFlow. Официальный FAQ указывает на ограничения распространения supplier prices; если для price-only use нужен отдельный контакт/согласование, зафиксировать это и не считать доступ разрешённым.

Условия запросов:

- Найти документированный способ получить Skyscanner destination entity ID через API. Не использовать скрейпинг сайта или угадывание ID.
- API требует `market`, `locale`, `currency`, город/`destinationEntityId`, диапазон дат. Не считать, что можно запросить абстрактную «среднюю за всю историю» без дат.
- Проверить варианты: широкий допустимый диапазон с aggregated grouping; при наличии уже заданных дат поездки — отдельный сценарий на период карточки. Не передавать состав путешественников, если API его не требует.
- Проверить поддержку RUB через Culture API/официальную документацию. Если RUB не поддерживается конкретным endpoint, сохранить исходную валюту и конвертировать через уже имеющийся Frankfurter только если курс доступен; записать дату курса и не выдумывать курс.
- Результат привязывать к городу/карточке поездки, не к конкретному отелю.

### 3.3 Dataestur — условный региональный источник для Испании

- Каталог официальных туристических данных: <https://www.dataestur.es/en/apidata/>.
- Документально оценить endpoint'ы индексов и средних цен гостиничного проживания, включая данные по туристическим точкам/регионам.
- Включать live-вызов только если на дату запуска официально подтверждены бесплатный доступ без биллинга и понятный способ загрузки. Источник ограничен Испанией и региональной/статистической агрегацией; он не даёт автоматически цену конкретного отеля.
- Рассматривать только как дополнительный benchmark по городу/региону, не смешивать с ценой конкретного отеля и не использовать как глобальное покрытие.

### 3.4 Поиск дополнительных бесплатных API

Можно добавить максимум 2 кандидата, найденных в официальных источниках, только если они напрямую дают цену отдельного отеля или ориентир по городу и удовлетворяют требованиям:

- конкретный бесплатный тест без карты и без риска списания подтверждён официальными условиями;
- понятна правомерность показа/кэширования цен в учебном приложении;
- можно получить JSON/другой документированный машинный ответ, а не парсить HTML.

Все прочие источники (Booking.com Demand, Expedia Rapid, Ostrovok, LiteAPI, платные Google Places/Foursquare-поля и т.п.) допускается описать в `reports/sources.md`, если они требуют партнёрства/оплаты/активации биллинга. Не регистрироваться от имени пользователя, не запрашивать партнёрство, не вызывать платный endpoint.

## 4. Что измерить

Для каждого ответа/отеля сохранить в обезличенном нормализованном виде:

- поставщик и ID поставщика;
- название, город/страна и результат сопоставления с Geoapify (`exact`, `high_confidence`, `ambiguous`, `no_match`);
- цену и исходную валюту;
- ценовую базу и смысл: за ночь/за весь срок/за номер/за человека/неизвестно;
- тип показателя: cheapest / average / median / конкретное предложение / городская агрегация;
- даты или диапазон дат, если они относятся к цене;
- налоги/сборы: включены, отдельно указаны, неизвестно;
- количество поставщицких предложений и разброс min/median/max, если ответ содержит несколько цен;
- timestamp ответа/источника и freshness, если API отдаёт;
- URL/deeplink на источник/поставщика, если API отдаёт, и ограничения использования;
- цену в RUB только если исходная величина, база и валюта установлены; сохранить исходную сумму и дату курса для проверки.

**Не делить сумму на число путешественников**, если источник не подтверждает, что цена дана за человека. Для проекта рабочая гипотеза: одна базовая комната на одного путешественника, поэтому цена за комнату/ночь может использоваться как стоимость размещения на путешественника/ночь при таком допущении. Явно записать, где это допущение сделано.

Городскую среднюю нельзя копировать в запись отдельного отеля. Для будущего контракта оценить отдельные семантические варианты:

```json
{
  "accommodationEstimate": {
    "amountRub": 0,
    "period": "per_night",
    "scope": "city",
    "aggregation": "average",
    "sourceUpdatedAt": "2026-10-27T00:00:00Z"
  }
}
```

Это пример обсуждения, не утверждённый контракт. При `scope=hotel` сумма привязана к объекту, при `scope=city` — только к направлению/поездке. Если источник не позволяет честно определить сумму, `amountRub` не подставлять (в рабочем JSON использовать `null`, не ноль).

## 5. Тестовая выборка

- Использовать уже проверенные города (Париж, Москва, Стамбул, Суздаль) там, где API их поддерживает, плюс минимум ещё 1–2 города по необходимости источника. Указать географические ограничения каждого API.
- Для Makcorps при наличии бесплатной квоты ограничиться несколькими городскими запросами и максимум несколькими hotel-specific запросами. Перед live вызовами составить бюджет credits; никогда не исчерпывать лимит полностью.
- Для Skyscanner достаточно минимального числа запросов, чтобы проверить поддержку city price, даты/группировки, фильтров размещения и RUB. Не делать серию вариантов без исследовательской необходимости.
- Для каждого API проверять и пустой/неподдерживаемый город, и один успешный сценарий, если это не превышает безопасный лимит.
- Сопоставление с Geoapify считать только при точном ID или надёжном совпадении имени и расстояния. Не прикреплять цену к неоднозначному объекту.

## 6. Реализация стенда

Создать изолированный CLI в этой папке, например `hotel_price_test.py`, не меняя код TripFlow API, Frontend, backend и прошлые эксперименты. Использовать стандартную библиотеку Python, если сторонняя зависимость не нужна.

Режимы:

- `--offline`: проверка конфигурации/отчётности без HTTP.
- `--live`: живые запросы только к включённым и безопасным источникам.
- `--providers makcorps skyscanner dataestur`: выбор провайдеров.
- `--max-requests` / credit budget: жёсткий верхний предел; значение должно быть меньше доступной бесплатной квоты.
- запросы последовательные, с timeout и минимальной паузой; автоматических повторов нет.

Env-переменные:

```text
MAKCORPS_API_KEY=
SKYSCANNER_API_KEY=
DATAESTUR_API_KEY=  # только если официально потребуется
```

Не создавать аккаунты, не вводить данные оплаты, не запрашивать секреты в чате. Владелец проекта регистрируется сам и устанавливает ключи в environment того процесса, который запускает Python. Добавить `.env.example` только с именами переменных и README с инструкцией PowerShell. Реальный `.env` не читать автоматически и игнорировать Git.

Безопасность:

- не записывать ключи в исходники, URL/логи, отчёты, JSON и traceback; если поставщик требует ключ в query string, редактировать URL до логирования;
- при 401/403/429 прекращать запросы к провайдеру без повтора;
- блокировать production/base URL, если разрешён только sandbox;
- для Makcorps перед запросом проверить remaining credits; не вызывать, если невозможно убедиться, что запрос не приведёт к оплате;
- Skyscanner не вызывать до ручной проверки одобрения доступа, стоимости и разрешённого использования цены;
- никогда не бронировать, не вызывать prebook/checkout и не создавать заказы.

## 7. Отчёты и результат

Каждый live-run сохранять в новой папке `reports/runs/<UTC-id>/`:

- `results.json` — все запросы и очищенные нормализованные наблюдения, HTTP status, latency, price basis, валюты, период, matching confidence, квоты/credits до и после. Секреты не сохранять.
- `live-results.md` — читаемая сводка по городам, отелям и endpoint'ам.
- `samples/` — небольшие очищенные примеры JSON ответов, если в них нет секретов/персональных данных и условия API позволяют хранение.
- `reports/sources.md` — официальные страницы, текущая дата проверки, доступ, квота, требования к ключу, право отображения/хранения, ограничения.
- `reports/assessment.md` — общий итог с ссылкой на последний валидный run. Не включать неудачные/неполные запуски как успешные данные.
- `README.md` — установка и повторный запуск, точные инструкции по получению ключей, условия ручной проверки перед live.

Для каждого источника итоговая строка должна иметь решение:

- `use_hotel_level` — цену можно корректно привязать к конкретному отелю;
- `use_city_level` — только общая оценка проживания в городе;
- `optional` — данные полезны лишь в части стран/объектов;
- `reject` — неподходящая семантика/покрытие/стоимость/условия;
- `not_tested` — не было безопасного доступа или credentials.

Не указывать только число успешных HTTP ответов: считать долю отелей с пригодной ценой, надёжно сопоставленных отелей, известной базой, валютой и корректной нормализацией в RUB. Отдельно показать долю пустых, просроченных, неоднозначных или непригодных цен. Не делать вывод о глобальном покрытии по нескольким городам.

## 8. Критерии завершения

1. Проверены безопасным live запросом все доступные бесплатные источники, которые владелец проекта сам подключил; остальные имеют явный `skipped_missing_config`, `skipped_cost_not_verified`, `skipped_terms_unclear` либо `not_available`.
2. Для Makcorps документированы фактическая квота, стоимость каждого использованного сценария и качество hotel match; credits не израсходованы сверх безопасного лимита.
3. Для Skyscanner чётко установлено, доступна ли заявка, нужна ли партнёрская модель, можно ли показывать цены без бронирования и получаются ли городские оценки для тестовой выборки. Без одобрения/подтверждения условий вывод — `not_tested`, не «API не работает».
