# Задание: проверка бесплатных API для TripFlow

- **Тип работы:** самостоятельный исследовательский эксперимент, не production-интеграция.
- **Дата подготовки:** 26.10.2026.
**Главный критерий:** не использовать платные API, платные тарифы, платные пробные периоды или операции, которые могут создать списание.

## 1. Цель

Проверить только новые бесплатные источники, которые могут дополнить уже проведённое исследование TripFlow, и понять:

1. Может ли Geoapify Geocoding закрыть поиск города так, чтобы сократить количество поставщиков.
2. Добавляет ли OpenTripMap полезные сведения к уже проверенным объектам Geoapify: описание, изображение, сайт и другие фактические поля.
3. Можно ли получить бесплатный справочный курс валют в RUB для валют, кроме уже проверенной пары EUR/RUB.
4. Если OpenTripMap оставляет значимые пробелы в описаниях/фотографиях, можно ли ограниченно дополнить соответствующие объекты через Wikidata/Wikimedia Commons без нарушения атрибуции и лимитов.

Результатом должен стать воспроизводимый небольшой запуск и отчёт с фактической заполненностью полей, сопоставлением объектов, ошибками, лимитами/условиями и решением: использовать, оставить резервом или не подключать.

В той небольшой выборке координаты и ID были у всех, адресная строка — у всех, имя — у 91%, сайты — у 27%, фото — у 3%, описания — у 3%, часы — у 14%, рейтинг, числовая цена и наличие номера — у 0%. Эти проценты относятся только к исследованной выборке.

- Frankfurter v2: живьём проверен EUR/RUB. **Не повторять EUR/RUB** в этом эксперименте; новый обязательный тест валюты — TRY/RUB.
- Overpass/OSM: проверен ранее; оставался нестабильным по времени и HTTP-ошибкам, числовых цен не дал. Не добавлять новые вызовы.

Для сравнения использовать существующие очищенные Geoapify-примеры, прежде всего `../data-source-survey/data/samples/20261015T150210175612Z/`, а также агрегированные проценты из отчётов выше. В samples сохранено не более двух объектов на endpoint, поэтому оценку межисточникового совпадения по ним обязательно помечать как ограниченную; не выдавать её за сравнение полного каталога.

## 3. Ограничения и безопасность

- **Никаких платных вызовов и подписок.** Не привязывать карту, не запускать платный тариф, платный пробный период, бронирование или заказ.
- Использовать только бесплатный план/публичный endpoint. Перед первым запросом к ключевому API проверить в официальной документации, что выбранный сценарий остаётся бесплатным, и записать дату проверки, квоту, ограничения использования и обязательную атрибуцию.
- Не создавать аккаунты от имени пользователя и не проходить регистрацию. Если для API требуется ключ, подготовить код и `.env.example`, объяснить пользователю, где получить бесплатный ключ, и ждать, пока он добавит его в environment.
- Читать секреты только из переменных окружения процесса. Не печатать ключи, URL с ключами, заголовки авторизации или тела ошибок, если они могут включать секрет. Не читать/копировать старые `.env` проекта.
- Не сохранять секреты в Git, JSON-отчётах, Markdown, логах, traceback или samples. `.env` должен быть в `.gitignore`.
- Не обходить CAPTCHA, авторизацию, ограничения тарифа, robots.txt или блокировки. **Парсинг сайтов в этом эксперименте не выполнять.**
- Не создавать лживые данные: отсутствующее поле остаётся `null`; неизвестная цена не равна нулю; `fee=yes` не превращать в денежную сумму.
- Один запрос за раз, с паузами и без автоматических повторов. При 401/403/429 или явном исчерпании бесплатного лимита прекратить запросы к провайдеру и записать причину.
- Сырые ответы хранить только при необходимости, очищенными и небольшими: максимум 1–2 образца на endpoint/тип. Не сохранять персональные данные.

## 4. Источники в области теста

### A. Geoapify Geocoding — обязательный новый сетевой тест

Это новый endpoint того же уже проверенного поставщика; проверяется только возможность использовать его для разрешения города и тем самым потенциально объединить геокодер с Geoapify Places.

- Использовать актуальную официальную документацию и текущую схему endpoint; не копировать устаревший URL из случайного примера.
- Официальные документы для начала: `https://apidocs.geoapify.com/docs/geocoding/forward-geocoding/` и `https://www.geoapify.com/pricing/`.
- Переменные окружения: `GEOAPIFY_API_KEY`; перед вызовом требовать `GEOAPIFY_FREE_PLAN=1` как явное подтверждение, что пользователь использует бесплатный план.
- Проверить небольшим числом запросов: Paris, Moscow (включая вариант кириллицей), Istanbul, Suzdal; неоднозначное название `Springfield` без страны и с фильтром страны; искусственное несуществующее название.
- Снять фактическую заполненность полей: исходное/локализованное название, страна и ISO-код, координаты, населённый пункт/административный район, timezone, feature type, Geoapify ID. Для валюты не предполагать наличие поля: проверить реально. Сопоставить города с сохранёнными GeoNames/Open-Meteo примерами по коду страны и координатам.
- Отдельно записать, поддерживает ли ответ надёжное разрешение неоднозначности без выбора первого результата и какие поля отсутствуют.
- Не вызывать Geoapify Places повторно.

### B. OpenTripMap — обязательный тест POI-обогащения, если пользователь передал бесплатный ключ

- Официальные документы: `https://dev.opentripmap.org/product`, `https://dev.opentripmap.org/docs`, `https://dev.opentripmap.org/price`.
- Бесплатный план в изученной документации указан как non-commercial, до 5 000 запросов в день и 10 запросов в секунду. Для курсового исследовательского запуска не переходить на платный план. Уточнить актуальность условий на дату теста.
- Переменные окружения: `OPENTRIPMAP_API_KEY`; требовать `OPENTRIPMAP_FREE_NONCOMMERCIAL=1`. Не запрашивать/использовать ключ, если его нет.
- Без ключа всё равно подготовить адаптер, `.env.example`, инструкции получения ключа и режим `--offline`; в отчёте отметить provider как `skipped_missing_key`, а не считать это нулевой заполненностью.
- Использовать города и координаты из предыдущих отчётов и каталог `../data-source-survey/data/samples/20261015T150210175612Z/`. Сделать маленькую последовательную выборку: до 3 категорий туристических объектов на город (например, музеи/культура, история, природа), максимум 5–10 результатов на запрос; запросить Details максимум для двух объектов на категорию/город. Итого держать до 50 HTTP-запросов на запуск, не превышать 1 запрос/сек.
- Сначала сверить допустимые category/kind values в актуальной официальной схеме. Не придумывать категории, поля или версию endpoint. Если категория недоступна в официальном API, записать это и пропустить.
- Фактически измерить: ID/XID, имя, тип/категории, координаты, адрес, описание, изображение/preview, Wikipedia/Wikidata/website URL, язык, рейтинг API (если поле есть — не трактовать как отзывы, пока это не подтверждено документацией), цена и доступность (ожидать их отсутствие, не выдумывать).
- Сопоставить новые записи с очищенными Geoapify samples: сперва по подтверждённому общему OSM/Wikidata ID, если он присутствует в обеих записях; иначе по нормализованному названию и малому расстоянию между координатами. Зафиксировать отдельно точные ID-совпадения, вероятные совпадения, новые объекты и неуверенные случаи. Не сливать неуверенные пары автоматически.
- Посчитать, сколько **уже сопоставленных** объектов получили новые непустые значения описания/фото/сайта. Это главный критерий полезности OpenTripMap, не только общее число найденных записей.
- Учитывать ODbL/атрибуцию и источники изображения; наличие URL изображения не означает автоматически, что его можно показывать без нужной атрибуции.

### C. Frankfurter — обязательная проверка новой валютной пары

- EUR/RUB уже проверен; повторный запрос пары не нужен.
- Выполнить один запрос TRY/RUB через документированный актуальный v2 endpoint. API key не требуется. Официальная документация: `https://frankfurter.dev/`.
- Сохранить пару, дату ответа, курс, HTTP-статус и длительность. Проверить обратное направление только если оно требуется выбранной реализацией конвертации; не делать лишних валютных комбинаций.
- В отчёте указать, что это справочный дневной курс, а не цена покупки/оплаты конкретного объекта.
- Если источник не поддерживает нужную валюту или вернул ошибку, не подставлять фиксированный курс и не вычислять через неизвестную промежуточную пару.

### D. Wikidata / Wikimedia Commons — только условный ограниченный этап

Не добавлять их безусловно в runtime-пайплайн. Рассматривать только если OpenTripMap не закрыл важный пробел по описаниям/изображениям и в фактических результатах есть общий QID или Commons/Wikipedia-ссылка, по которой запись можно сопоставить.

- Официальные точки входа: `https://www.wikidata.org/wiki/Wikidata:Data_access`, `https://commons.wikimedia.org/wiki/Help:Machine-readable_data`, `https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits`.
- Ключ обычно не требуется. Для теста задать осмысленный `User-Agent` из `WIKIMEDIA_USER_AGENT`, содержащий название эксперимента и контакт, предоставленный пользователем; не подставлять вымышленный email.
- Выполнить не более 10 последовательных запросов для уже сопоставленных объектов. Проверить description, image title/URL, author, license name/URL, attribution и язык.
- Соблюдать актуальные лимиты и `Retry-After`; использовать кэш и прекращать вызовы при 429. Для каждой картинки записать её собственные условия лицензии.
- Если нет устойчивого идентификатора связи или прирост мал, этап пропустить и рекомендовать не подключать источник.

## 5. Проверяемая архитектура/поток данных

Эксперимент не строит production API и не меняет согласованный продуктовый контракт. Он оценивает следующий кандидатный порядок:

1. Вход: город строкой или уже подготовленные данные.
2. Для строки города — один выбранный геокодер. Новый тест Geoapify Geocoding сравнить с уже проверенным GeoNames; решить, достаточно ли Geoapify для города/координат/timezone или GeoNames остаётся отдельным сервисом. Не вызывать оба автоматически для каждого запроса.
3. Валюту страны получать из проверенного CLDR/GeoNames; не считать её валютой конкретной цены.
4. Список жилья и POI получать из проверенного Geoapify Places (в этом эксперименте повторно не вызывать).
5. Если результаты OpenTripMap проходят порог полезности и сопоставимости, обогатить ими только совпавшие записи; не дублировать весь каталог.
6. Денежные оценки из внешних источников нормализовать в RUB с проверенным курсом Frankfurter только для поддерживаемой пары. Не выдумывать цену отеля/билета из отсутствующих полей каталога.
7. AI использует проверенные реальные кандидаты для фильтрации/ранжирования; эксперимент не должен просить модель генерировать название/цену/описание реального объекта, отсутствующие в данных.

Парсеры сайтов, платные API и погодный API в этой задаче вне области работ.

## 6. Как считать покрытие и делать выводы

Для каждого провайдера, города, категории и поля считать:

- `N_requested` — количество объектов, для которых поле применимо;
- `N_present` — объектов с фактически непустым и валидным значением;
- `coverage = N_present / N_requested * 100%`;
- отдельное число `unknown/not_applicable`, если поле по смыслу к объекту неприменимо.

Не смешивать успешный HTTP 200 с заполненностью или качеством. Отдельно классифицировать `ok`, `empty`, `missing_key`, `skipped`, `http_error`, `provider_error`, `schema_error`, `timeout`, `rate_limited`.

В отчёте:

- обозначить малую выборку и не называть долю гарантией или математической вероятностью будущей выдачи;
- показывать абсолютные числа вместе с процентами, например `3/20 (15%)`;
- сравнивать только одинаковые города/категории/радиусы, где это возможно;
- для cross-match давать denominator сохранённых Geoapify samples (максимум два объекта на endpoint), отдельно от покрытия API;
- приводить по одному очищенному примеру ответа каждого реально вызванного endpoint;
- описывать стоимость как `0` только после проверки бесплатного плана, квоты и ограничений; не путать бесплатный прототип с разрешением для будущего коммерческого сервиса.

## 7. Ожидаемые артефакты эксперимента

В этой папке создать:

- `.env.example` — только пустые/примерные переменные без секретов;
- `.gitignore` — игнорировать `.env`, ключи, временные ответы и кэш;
- `README.md` — создание окружения, установка, запуск в Windows PowerShell, перечень бесплатных ключей и что включать в environment;
- небольшой CLI с режимами `--offline`, `--providers`, лимитами запросов и последовательным исполнением;
- локальные проверки на искусственных фикстурах для нормализации/подсчёта полей, без сетевого доступа в этих проверках;
- `reports/assessment.md` — итоговая сводка и решение по каждому провайдеру;
- `reports/sources.md` — официальные ссылки, условия/квоты и дата проверки;
- `reports/runs/<UTC-id>/results.json`, `live-results.md` и максимум по одному-двум очищенным примерам на endpoint.

Не переписывать предыдущие результаты и не переносить в новую папку старые секреты или большие сырые ответы.

## 8. Что должно получиться в конце

В `reports/assessment.md` дать однозначный вывод:

1. Какие результаты можно считать уже подтверждёнными по прежнему исследованию, не повторяя запросы.
2. Закрывает ли Geoapify Geocoding поиск города настолько, чтобы не держать два геокодера.
3. Сколько полезных описаний/изображений OpenTripMap добавил к тем же объектам, насколько надёжен cross-match и стоит ли его подключать.
4. Подтверждён ли TRY/RUB у Frankfurter; какие ограничения остаются для валютной конвертации.
5. Нужен ли ограниченный Wikidata/Commons этап или он не даёт достаточной выгоды.
6. Предложенный минимальный бесплатный набор сервисов и порядок их вызова.
7. Чёткий список неизвестных данных, которые бесплатные проверенные API всё ещё не закрывают: в частности, цены/доступность отелей на даты и числовые цены входных билетов.
8. Для каждого требующего ключа — точное имя environment-переменной, бесплатная страница регистрации, тариф/ограничения и инструкция пользователю, как безопасно передать значение. Не просить присылать ключ в чат.

Не писать код в `API/` production-проекта и не редактировать документы вне `API/experiments/free-api-gap-test/`. Не создавать Git-коммиты.
