# TripFlow. Интеграция C# backend с Python

**Для агента C#, реализующего интеграцию:** начните с [плана миграции клиента](BACKEND-MIGRATION.md). Там указаны точки изменения в Backend, различия форматов и сценарии приёмки. Таблицы и примеры ниже относятся к действующему Python API с моком Москвы.

Публичный Python API на Render доступен через кабинет с выдачей ключей. Версия из этой документации использует одно строковое поле `targets` и одну категорию на задачу. Для проверки опубликованной версии используйте её Swagger. [Гайд по порталу на Render](PORTAL.md) · [Текущий контракт Python](CONTRACT.md)

Диаграмма описывает подключение C# к polling Python. Маршруты карточек в C# уже существуют. Для сквозной работы с текущим Python API требуется обновить клиент C#, который сейчас ожидает callback. [Состояние интеграции C#](../../Backend/README.md#связь-с-python)

## Сценарий от черновика до сметы

~~~mermaid
sequenceDiagram
    participant R as React
    participant C as C# backend
    participant P as Python API
    R->>C: POST {card}/generation с сохранёнными параметрами
    C->>C: Сохранить taskId и версию карточки
    loop Одна задача на категорию
        C->>P: POST /v1/recommendations с отдельным taskId
        P-->>C: 202 Accepted
    end
    C-->>R: 202 Accepted с текущим статусом запрошенных типов
    par Опрос задачи
        C->>P: GET /v1/tasks/{taskId} до completed
        P-->>C: result с recommendations.finished
        C->>C: Применить результат один раз
    and Получение статуса в React
        loop Пока экран открыт и запрошенный подбор pending
            R->>C: GET {card}
            C-->>R: Сохранённый статус и пакет после завершения
        end
    end
    opt Пользователю нужны дополнительные варианты
        R->>C: POST {card}/generation для нужного типа
        Note over R,P: Та же схема с новым taskId и актуальными исключениями
    end
    R->>C: Сохранить выбранный отель и места
    R->>C: POST {card}/budget
    C->>C: Сохранить taskId, версию карточки и выбор
    C->>P: POST /v1/budget с актуальным выбором
    P-->>C: 202 Accepted
    C-->>R: 202 Accepted с текущим статусом сметы
    par Опрос задачи
        C->>P: GET /v1/tasks/{taskId} до completed
        P-->>C: result с budget.finished
        C->>C: Сохранить смету или ошибку
    and Получение статуса в React
        loop Пока экран открыт и последний статус pending
            R->>C: GET {card}
            C-->>R: Сохранённый статус и результат или ошибка, если есть
        end
    end
~~~

Python проверяет входные данные и сохраняет результат задачи. Текущая сборка вычисляет его по тестовым данным. C# хранит карточку, её версию, выбор автора, исключения, полученные списки вариантов и итоговый бюджет. React получает всё состояние карточки через C#.

## Три маршрута межсервисного обмена

| Метод и рабочий путь | Направление | Назначение |
|---|---|---|
| `POST /v1/recommendations` | C# → Python | Первый подбор и догенерация. Один запрос на отели или места. |
| `POST /v1/budget` | C# → Python | Оценка питания, городского транспорта, прочих расходов и резерва по актуальному выбору. |
| `GET /v1/tasks/{taskId}` | C# → Python | Статус и сохранённый результат своей задачи. |

Все три маршрута используют один заголовок `X-API-Key` из кабинета. Оба POST принимают JSON и возвращают `202 Accepted`, например `{"taskId":"rec-001","status":"accepted"}`. Заголовок `Location` указывает относительный путь для опроса, `Retry-After` задаёт рекомендуемую задержку в секундах.

GET возвращает `200`. Пока задача выполняется, тело имеет вид `{"taskId":"rec-001","status":"pending","result":null}`. После завершения `status` равен `completed`, а `result` содержит объект `recommendations.finished` или `budget.finished` по схемам ниже. `completed` означает готовность к чтению, включая результат с прикладной ошибкой. Повторный GET возвращает тот же итог. Чужой или неизвестный ID даёт `404`, неверный или отозванный ключ — `401`.

Для первичной генерации C# отправляет две независимые задачи с разными ID, по одной на `hotels` и `attractions`. Смета получает третий ID после выбора. Сохраняйте ID до POST. При потере ответа повторяйте тот же POST. Тот же ID с изменённым содержимым или операцией даёт `409`. При временном сетевом сбое продолжайте GET с увеличенной паузой. Сохраняйте незавершённые ID для возобновления после перезапуска C#. Локальному backend достаточно исходящего HTTPS к Python.

### Общие правила типов

Далее используются типы JSON Schema. **Обязательное** поле должно присутствовать. `null` допустим там, где он явно указан в столбце типа. Пустой список передаётся как `[]`. Python приводит пустые и пробельные входные nullable-строки к `null`. Для необязательных полей смысл отсутствия указан в описании. Имена полей в новых структурах приведены в `camelCase`. Тела запросов в этом разделе соответствуют OpenAPI этой сборки.

#### TripContext

Общий объект `trip` в запросах к Python.

| Поле | Тип | Присутствие | Смысл и ограничения |
|---|---|---|---|
| `destinationId` | `string` | Обязательно | ID из общего справочника направлений, например `ru-moscow`. |
| `startDate` | `string` | Обязательно | Календарная дата в формате `YYYY-MM-DD`. |
| `endDate` | `string` | Обязательно | Календарная дата в том же формате, не раньше `startDate`. Ночи — разница дат. |
| `travelers` | `integer` | Обязательно | Положительное число путешественников. |
| `budgetRub` | `integer` | Обязательно | Положительная сумма в рублях на всю группу и всю поездку, включая резерв. |
| `preferences` | `string`, `null` | Обязательно | Текст пожеланий. `null` означает, что пожелания отсутствуют. |

#### Coordinates

`Coordinates` — объект с двумя обязательными полями `latitude` и `longitude` типа `number`. Широта допускает значения от −90 до 90, долгота — от −180 до 180.

#### Цена отеля

`price` у отеля — одно число в рублях за **всю группу и всё проживание на даты поездки**. Если источник даёт цену за ночь, номер или человека, Python приводит её к сумме на группу до отправки варианта. Если доступна лишь цена «от» и обоснованную оценку полной стоимости получить не удалось, передаётся `null`. Мок считает цену из фиксированной ставки на двухместный номер за ночь. C# сравнивает `price` с лимитом на отель и добавляет её в смету как ориентировочную стоимость проживания. [Единицы и ограничения цен в стенде](research/deepseek-web-trip/report.md#flash-с-веб-поиском)

| Поле | Тип | Присутствие | Смысл и ограничения |
|---|---|---|---|
| `price` | `integer`, `null` | Обязательно | Неотрицательная сумма в целых рублях за всю группу и все ночи. `null` означает неизвестную стоимость. |

#### AdmissionPriceQuote

| Поле `AdmissionPriceQuote` | Тип | Присутствие | Смысл и ограничения |
|---|---|---|---|
| `amountRub` | `integer` | Обязательно | Сумма в целых рублях для указанной единицы цены, неотрицательная. `0` используется для подтверждённой бесплатности. |
| `basis` | `string` | Обязательно | `person_admission` — одно посещение на человека, `group_admission` — одно посещение на группу. |
| `kind` | `string` | Обязательно | `source` — цена из источника, `estimate` — расчётная оценка. |
| `isFromPrice` | `boolean` | Необязательно | `true` для цены «от». При отсутствии поля используется `false`. |
| `sourceUrl` | `string`, `null` | Необязательно | HTTPS-ссылка на основание цены. Пустая строка приводится к `null`. |

Неизвестная цена посещения передаётся как `price: null`.

#### TaskAccepted и ошибки

| Объект | Поле | Тип | Присутствие и смысл |
|---|---|---|---|
| `TaskAccepted` | `taskId` | `string` | Обязательно. ID задачи из запроса C#. |
| `TaskAccepted` | `status` | `string` | Обязательно. Значение `accepted`. |
| `TaskStatus` | `taskId` | `string` | Обязательно. ID из URL опроса. |
| `TaskStatus` | `status` | `string` | Обязательно. `pending` или `completed`. |
| `TaskStatus` | `result` | `object`, `null` | Обязательно. Пока задача выполняется, содержит `null`. |
| `ErrorResponse` | `taskId` | `string`, `null` | Обязательно. ID задачи, если его удалось прочитать из отклонённого запроса. |
| `ErrorResponse` | `error` | `object` (`ErrorDetail`) | Обязательно. Причина отклонения POST или ошибка чтения задачи по GET. |
| `ErrorDetail` | `code` | `string` | Обязательно. Машинный код из таблицы HTTP-ошибок. |
| `ErrorDetail` | `message` | `string` | Обязательно. Краткое описание причины. |
| `ErrorDetail` | `fields` | `object` | Необязательно. Ключи — пути вроде `trip.endDate`, значения — непустые массивы `string` с ошибками полей. |

Ошибки HTTP возвращаются в формате `ErrorResponse`. [Коды HTTP-ошибок](CONTRACT.md#http-ошибки) Сбой принятой задачи сообщается в поле `result` с `error` в ответе сметы или в результате затронутого типа подбора.

### 1. Запрос рекомендаций

Для первичного подбора отправьте два POST с разными ID, один для отелей и один для достопримечательностей. Для догенерации создайте новый `taskId`, передайте уточнение и ID уже полученных или отклонённых объектов. При замене отеля или места C# высвобождает его стоимость при расчёте нового лимита. [Правила подбора](ARCHITECTURE.md#подбор-и-расчёт-бюджета)

| Поле `RecommendationsRequest` | Тип | Присутствие | Смысл и ограничения |
|---|---|---|---|
| `taskId` | `string` | Обязательно | Уникальный непустой ID, который создаёт C#. |
| `trip` | `object` (`TripContext`) | Обязательно | Актуальные параметры карточки. |
| `targets` | `string` | Обязательно | Одна категория, `hotels` или `attractions`. |
| `count` | `integer` | Обязательно | Положительное максимальное число вариантов. |
| `maxTotalRub` | `integer`, `null` | Обязательно | Лимит на один подходящий вариант. Для отеля это стоимость всех ночей на группу, для места — стоимость одного посещения всей группой. `null` означает поиск без отдельного лимита. |
| `refinement` | `string`, `null` | Обязательно | Уточнение для подбора этой категории. `null` отключает уточнение. Мок принимает текст как часть контракта. |
| `excludedObjectIds` | `array` из `string`, `null` | Обязательно | Уникальные `objectId`, которые нужно исключить. `null` и `[]` означают поиск без исключений. |

~~~json
{
  "taskId": "hotels-001",
  "trip": {
    "destinationId": "ru-moscow",
    "startDate": "2027-06-10",
    "endDate": "2027-06-15",
    "travelers": 2,
    "budgetRub": 60000,
    "preferences": "Отель рядом с метро, музеи и прогулки"
  },
  "targets": "hotels",
  "count": 2,
  "maxTotalRub": 30000,
  "refinement": "Можно дальше от центра",
  "excludedObjectIds": ["hotel-boulevard"]
}
~~~

Для первичного подбора можно передать `refinement: null` и `excludedObjectIds: []`. Для каждой новой задачи используйте отдельный `taskId`. Оба запроса также есть в Swagger.

Отдельное тело для достопримечательностей:

~~~json
{
  "taskId": "attractions-001",
  "trip": {
    "destinationId": "ru-moscow",
    "startDate": "2027-06-10",
    "endDate": "2027-06-15",
    "travelers": 2,
    "budgetRub": 60000,
    "preferences": "Отель рядом с метро, музеи и прогулки"
  },
  "targets": "attractions",
  "count": 2,
  "maxTotalRub": null,
  "refinement": null,
  "excludedObjectIds": null
}
~~~

### 2. Итоговый результат подбора

После завершения поиска GET возвращает в поле `result` объект `recommendations.finished` с вариантами одной категории. C# сохраняет пакет и обновляет статус соответствующего списка. `objectId` — стабильный ID объекта в каталоге TripFlow. C# связывает вариант и его цену с конкретной карточкой. [Идентификация объектов](ARCHITECTURE.md#постоянный-каталог-объектов)

| Общее поле результата | Тип | Присутствие | Смысл и ограничения |
|---|---|---|---|
| `taskId` | `string` | Обязательно | ID принятой задачи. |
| `event` | `string` | Обязательно | Рабочие имена `recommendations.finished` и `budget.finished`. Значение определяет остальные поля. |

| Поле результата подбора | Тип | Присутствие | Смысл и ограничения |
|---|---|---|---|
| `results` | `object` | Обязательно в `recommendations.finished` | Новая задача содержит один ключ, `hotels` либо `attractions`. Ранее принятая задача с двумя типами может содержать оба ключа. |
| `RecommendationResult.status` | `string` | Обязательно | `succeeded` — поиск завершён, включая пустую выдачу. `partial` — поиск прервался, но есть пригодные варианты. `failed` — поиск завершился с ошибкой и без пригодных вариантов. |
| `RecommendationResult.items` | `array` из `Candidate` | Обязательно | Все варианты этого типа, найденные за текущий запрос, в порядке подбора и в пределах запрошенного `count`. Пустая выдача и `failed` передаются как `[]`. |
| `RecommendationResult.hasMore` | `boolean`, `null` | Обязательно | `true` — найден следующий пригодный вариант за пределами пакета. `false` — поиск исчерпан. `null` — наличие следующих вариантов неизвестно, в том числе при `failed`. |
| `RecommendationResult.error` | `object` (`ErrorDetail`) | При `failed` обязательно, при `partial` необязательно | Причина сбоя или неполного поиска. |

#### Candidate

| Поле | Тип | Присутствие | Смысл и ограничения |
|---|---|---|---|
| `objectId` | `string` | Обязательно | Стабильный ID объекта из каталога Python. |
| `name` | `string` | Обязательно | Название отеля или места. В моке название вымышленное. |
| `address` | `string`, `null` | Обязательно | Адрес, если известен. |
| `coordinates` | `object` (`Coordinates`), `null` | Обязательно | Координаты, если установлены. |
| `imageUrl` | `string`, `null` | Обязательно | HTTPS-ссылка на изображение, если доступно. |
| `sourceUrl` | `string` | Обязательно | HTTPS-ссылка на источник. Мок использует адрес на `example.org`. |
| `price` | `integer`, `null` для отеля. `object` (`AdmissionPriceQuote`), `null` для места | Обязательно | Отель — сумма за всё проживание группы. Место — цена одного посещения с указанием единицы. |
| `description` | `string`, `null` | Необязательно | Краткое описание на основе источников. |
| `recommendationReason` | `string`, `null` | Необязательно | Краткое объяснение, почему вариант подходит под пожелания. |
| `stars` | `integer`, `null` | Необязательно для отеля | Звёздность от 1 до 5, если подтверждена. |
| `category` | `string`, `null` | Необязательно для места | Категория, например «Музей». |

У достопримечательности в `results.attractions.items` всегда присутствуют `imageUrl`, `coordinates` и `address`. Каждое из этих полей может иметь значение `null`, если у источников нет подтверждённых сведений.

~~~json
{
  "taskId": "hotels-001",
  "status": "completed",
  "result": {
    "taskId": "hotels-001",
    "event": "recommendations.finished",
    "results": {
      "hotels": {
        "status": "succeeded",
        "items": [
          {
            "objectId": "hotel-metro",
            "name": "Отель у метро",
            "address": null,
            "coordinates": null,
            "imageUrl": null,
            "sourceUrl": "https://example.org/tripflow-mock/hotel-metro",
            "price": 22000,
            "stars": 3
          }
        ],
        "hasMore": false
      }
    }
  }
}
~~~

Мок выдаёт `succeeded` или `failed`. `partial` предусмотрен для будущего поиска по источникам. Если поиск отелей завершится ошибкой, результат `hotels` получит `status: "failed"`, `items: []`, `hasMore: null` и `error`. Задача на достопримечательности завершится независимо.

### 3. Запрос бюджета после выбора

C# фиксирует версию карточки и отправляет в Python параметры поездки, выбранный отель, выбранные места и имеющиеся цены. [Правила бюджета](ARCHITECTURE.md#подбор-и-расчёт-бюджета)

| Поле `BudgetRequest` | Тип | Присутствие | Смысл и ограничения |
|---|---|---|---|
| `taskId` | `string` | Обязательно | ID новой задачи расчёта. |
| `trip` | `object` (`TripContext`) | Обязательно | Снимок исходных параметров. |
| `selectedHotel` | `object` (`SelectedHotel`), `null` | Обязательно | Выбранный отель. `null` означает, что отель в расчёт не передан. |
| `selectedAttractions` | `array` из `SelectedAttraction` | Обязательно | Выбранные посещения. Пустой массив означает план без посещений. |

| Объект | Поле | Тип | Присутствие и смысл |
|---|---|---|---|
| `SelectedHotel` | `objectId` | `string` | Обязательно. ID отеля из каталога. |
| `SelectedHotel` | `price` | `integer`, `null` | Обязательно. Сохранённая сумма выбранного варианта за всю группу и все ночи. |
| `SelectedAttraction` | `objectId` | `string` | Обязательно. ID места из каталога. |
| `SelectedAttraction` | `price` | `object` (`AdmissionPriceQuote`), `null` | Обязательно. Цена одного посещения, если известна. Единица цены соответствует достопримечательности. |

Отсутствие отеля трактуется в контексте маршрута: при поездке без ночёвки проживание равно нулю, а при незапланированном проживании с ночёвкой смета остаётся неполной.

~~~json
{
  "taskId": "budget-001",
  "trip": {
    "destinationId": "ru-moscow",
    "startDate": "2027-06-10",
    "endDate": "2027-06-15",
    "travelers": 2,
    "budgetRub": 60000,
    "preferences": "Отель рядом с метро, музеи и прогулки"
  },
  "selectedHotel": {
    "objectId": "hotel-boulevard",
    "price": 27000
  },
  "selectedAttractions": [
    {
      "objectId": "place-museum",
      "price": {
        "amountRub": 900,
        "basis": "person_admission",
        "kind": "estimate"
      }
    }
  ]
}
~~~

### 4. Итоговый результат бюджета

Рабочее имя события в примере — `budget.finished`. Python возвращает дополнительные расходы на всю группу за поездку. C# суммирует их с проживанием и билетами по тому выбору, к которому привязана задача. В примере итог **56 400 ₽** получается из **27 000 ₽** за отель, **1 800 ₽** за два билета и **27 600 ₽** дополнительных расходов. Остаток — **3 600 ₽**. Если у выбранного места цена неизвестна, C# показывает известную сумму и помечает смету как неполную. [Смета и версия карточки](ARCHITECTURE.md#подбор-и-расчёт-бюджета)

| Дополнительное поле `budget.finished` | Тип | Присутствие | Смысл и ограничения |
|---|---|---|---|
| `status` | `string` | Обязательно | `succeeded` или `failed`. Успешная оценка дополнительных расходов допускает неполную итоговую смету C#, если отсутствуют цены выбранных объектов. |
| `expenses` | `object` (`Expenses`), `null` | Обязательно | При `succeeded` передаётся объект, при `failed` — `null`. |
| `error` | `object` (`ErrorDetail`) | Обязательно при `failed` | Причина сбоя. |

Все поля `Expenses` обязательны. Суммы — неотрицательные целые рубли на всю группу и поездку.

| Поле `Expenses` | Тип | Смысл |
|---|---|---|
| `foodTotalRub` | `integer` | Питание на всю группу за поездку. |
| `localTransportTotalRub` | `integer` | Городской транспорт. |
| `otherExpensesTotalRub` | `integer` | Прочие траты, исключая уже учтённые статьи. |
| `reserveTotalRub` | `integer` | Резерв на поездку. |

## Версии и повторы

1. C# до отправки связывает `taskId` с версией карточки и снимком входных данных. Для сметы снимок включает выбранный отель и места.
2. Python хранит итог и возвращает его при каждом чтении статуса.
3. C# проверяет версию карточки и применяет результат транзакционно один раз. После `completed` опрос задачи завершён.
4. Новый поиск, догенерация и пересчёт получают новые ID. Повтор POST с прежними ID и данными возвращает `202`.

На стороне C# для принятой задачи нужен предельный срок ожидания. Если итог не поступил, текущая попытка переходит в `failed`, чтобы React завершил polling и мог предложить повтор. Точные сроки и паузы между попытками чтения согласуются при реализации.

## Контракты React → C#

`{dashboard}` означает `/api/dashboards/{dashboardId}`, `{card}` — `{dashboard}/cards/{cardId}`. Оба параметра пути — строки в формате UUID. В маршрутах текущего backend используются существующие DTO. Маршруты подбора, выбора и сметы уже есть. Клиенту C# предстоит перейти с callback на контракт Python из этого документа. [Маршруты карточек](../../Backend/Dashboards.cs#L22) · [Состояние backend](../../Backend/README.md#проверка-через-swagger)

| Маршрут | Тело запроса | Успешный ответ | Состояние |
|---|---|---|---|
| `GET /api/destinations` | Без тела | `200`, `array` из `DestinationView` | Есть |
| `POST {dashboard}/cards` | `TripInput` | `201`, `TripCardView` | Есть |
| `GET {card}` | Без тела | `200`, `TripCardView` | Есть |
| `PUT {card}` | `TripInput` | `200`, `TripCardView` | Есть |
| `POST {card}/publish` | Без тела | `200`, `TripCardView` | Есть |
| `POST {card}/generation` | `CardGenerationInput` | `202`, `TripCardView` с состоянием запрошенных типов подбора | Есть |
| `PUT {card}/hotel` | `HotelSelectionInput` | `200`, `TripCardView` | Есть |
| `PUT {card}/attractions` | `AttractionSelectionInput` | `200`, `TripCardView` | Есть |
| `POST {card}/budget` | Без тела. C# берёт сохранённый выбор | `202`, `TripCardView` с текущим состоянием сметы | Есть |

Целевой сценарий polling после перевода клиента C# выглядит так.

1. C# сохраняет `taskId`, версию карточки и снимок входных данных, отмечает запрошенные типы подбора или смету как `pending` и отправляет задачу в Python. После подтверждения приёма C# возвращает React `202 Accepted` и текущее состояние карточки. Если Python явно отклонил задачу, C# завершает попытку с ошибкой.
2. Пока экран открыт и хотя бы один нужный статус равен `pending`, React раз в несколько секунд делает короткий `GET {card}`. C# возвращает состояние из своего хранилища.
3. При `succeeded` или `partial` React показывает весь полученный список соответствующего типа. При `partial` он может дополнительно показать причину неполной выдачи. При `failed` показывает ошибку. Для сметы React показывает `budget.result` при `succeeded` и `budget.error` при `failed`.
4. React прекращает polling, когда нужные статусы вышли из `pending` или экран закрыт. При повторном открытии редактора первый `GET {card}` возвращает последнее состояние и позволяет возобновить опрос, если работа ещё идёт.

Догенерация запрашивает пакет для одного типа. Ранее сохранённые варианты остаются видны, пока идёт поиск. По завершении C# добавляет весь новый пакет разом. Если догенерация завершается ошибкой, ранее сохранённый список и выбор остаются доступны.

После редактирования параметров или выбора старая смета получает статус `stale`. Актуальный расчёт запускается через `POST {card}/budget`.

### TripInput и DestinationView

В сохранённом `TripCardView.trip` поле `preferences` присутствует. Поле `hotelBudgetLimitRub` предлагается добавить к `TripInput` отдельно: необязательное, тип `integer` или `null`, положительный максимум в рублях на всю группу за проживание. Пустое значение означает автоматический ориентир, когда для него достаточно данных. [Валидация карточки](../../Backend/Dashboards.cs#L222)

## Что ещё согласовать

- Правила подтверждения цен и расширение списка направлений. Для отеля сумма уже относится ко всему проживанию группы. Способ поиска и получения цен уточняется по результатам стендов. [Исследование вариантов поиска](research/deepseek-web-trip/report.md#что-проверить-перед-интеграцией)
- Как задавать лимиты при первом подборе, пока смета ещё не рассчитана. `maxTotalRub` показывает возможное место для ручного лимита на отель, если его передал автор карточки.
- Срок ожидания со стороны C#, политика повторов при недоступности Python и публичные поля клиентских DTO.
- Правила публикации при неполной смете, отсутствии отеля и пустом списке мест.
