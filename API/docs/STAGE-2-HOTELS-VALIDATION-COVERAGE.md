# Stage 2 · Ослабить валидацию и стабильно выдавать реальные варианты проживания

**Задача для разработчика.** На первом этапе приоритет — регулярно возвращать путешественнику хотя бы один реальный объект в выбранном городе с понятной ориентировочной ценой. Второй показатель — заполнение запрошенного пакета. Идентичность объекта, цена, доступность, предпочтения и оформление проверяются независимо. Ошибка в одном тарифе должна оставлять в работе гостиницу, её адрес, сайт и другие тарифы. Решение должно работать для ранее неизвестного объекта и языка страницы. Мадрид и Стамбул ниже нужны для регрессии; приёмка включает отдельные города и источники.

Публичный `HotelItem` сейчас требует целую групповую `price` в рублях и `sourceUrl`. Поэтому одного найденного названия для контрактной выдачи недостаточно. В этой итерации расширяем основания оценки, сохраняем происхождение суммы и доводим кандидата до существующего формата. Если даже приблизительную сумму обосновать нечем, сохраняем объект в каталоге и показываем причину недобора. Для городов без подтверждённого туристического жилья нормален пустой результат. ## 2. Что считать достаточным для карточки

Учитывать регион для одноимённых городов. | Сохранить кандидата для уточнения. При явном противоречии страны, города или филиала исключить. |

Цену соседнего филиала нельзя считать ценой выбранного. |

## 3. Изменить путь кандидата

1. **Сначала зарегистрировать объект.** Объединить каталог, геоисточник, Russhotels при наличии и веб-поиск. Сохранять устойчивый ID, подтверждение города и ссылки, даже если у всех предложений пока нет принятой цены. Неправильный формат необязательного поля в ответе модели или одного из нескольких тарифов должен отклонять это поле или тариф. Проверить случай «один повреждённый тариф, один нормальный» внутри одного объекта. [Каталог](../tripflow_api/hotel_catalog.py) · [Источники](../tripflow_api/hotel_sources.py)
2. **Привязать страницы к объекту до извлечения цены.** Начинать с уже известной страницы объекта. При несовпадении номеров источников у имени и города проверить город в собственном заголовке, адресе и привязанной геозаписи. Для двух страниц сопоставлять ID в пространстве имён поставщика. Например, локализованные URL могут хранить один ID в пути и параметре. Дополнительно проверять географические противоречия. Простое равенство цифр на разных сайтах, бренд сети, похожее название или общий домен недостаточны. Поддержать независимые страницы через адрес/координаты филиала. Нечёткое совпадение использовать для поиска подтверждения.
3. **Сделать единицей проверки предложение номера.** Python сохраняет ID страницы и блока, заголовок, соседние строки, валюту документа, сведения о гостях и длительности. Flash возвращает структурированный смысл и ссылки на исходные строки. При неверном индексе блока попробовать найти единственное совпадение по сумме, валюте, номеру и выдержкам в блоках той же страницы. При двух правдоподобных совпадениях искать дополнительный признак. Если удалось подтвердить цену по другой языковой версии этой же страницы, использовать её с собственными доказательствами.
4. **Учитывать язык через контекст.** Одноместность может быть выражена названием категории, количеством взрослых при размещении в отдельном номере или структурированным полем предложения. Пример — заголовок раздела `Single` рядом с ценой и описанием комнаты. Одно слово `single` в выражении «две односпальные кровати» не задаёт размещение. Использовать Flash для нормализации смысла на любом языке с возвратом цитаты; Python проверяет числа, валюту и связь с объектом. Расширение одного регулярного выражения на несколько испанских названий не закроет задачу. Проверять также страницы, где язык города, прайса и интерфейса отличается.
5. **Повторять только недостающую проверку.** Для сохранённого кандидата последовательно попробовать другие строки его блока, другой блок на той же странице, другой локализованный источник и затем точечный внешний запрос. Вести отдельно «страница просмотрена» и «из неё удалось обосновать цену». Учитывать уже сделанные попытки по объекту, источнику и причине. Общему дедлайну и лимитам подчиняются все ветки; положительные частичные результаты сохраняются.
6. **Использовать ручную цель с начала поиска.** Передавать `targetHotelTotalRub` и вычисленный ориентир на номер за ночь в первоначальный план, даже при нуле готовых объектов. Сначала обеспечить несколько разнотипных реальных кандидатов; искать дополнительные подходящие категории, если первые сильно далеки от ориентира. При ранжировании учитывать доступность, основания цены, обязательные условия и отклонение от цели. При смене цели цены одного и того же сохранённого тарифа должны совпадать. Сам пользовательский бюджет не является источником рыночной стоимости.

## 4. Каскад оценки, когда точного тарифа не хватает

Реализовать общий путь от наиболее сильного основания к более приблизительному. Для каждого принятого варианта записывать исходные суммы, валюту и курс, ссылки, количество номеров и ночей, ограничения, метод расчёта и понятную подпись. Приведённые ниже основания — предлагаемый инженерный способ расширить выдачу. В публичном `price` оставлять одну воспроизводимую групповую сумму.

| Приоритет | Когда применить | Расчёт и подпись |
|---|---|---|
| 1. Тариф предложения | Установлены объект, размещение, сумма, валюта и единица. Допускаются ставка «от», диапазон, сезонный прайс и тариф на другие даты. | Переиспользовать текущую арифметику. Например, для «от» брать применимую нижнюю ставку, в карточке явно показывать «от» и период наблюдения. |
| 2. Ориентир по самому объекту | Страница однозначно указывает ночную цену за отдельный номер в этой гостинице, но точная категория или одноместный тариф неизвестны. Известны валюта и единица; предложение не содержит противоречия обязательным условиям. | Допустить опубликованную цену номера как приближение стоимости одной отдельной комнаты. Например, ночная ставка за весь частный двухместный номер может служить ориентиром для комнаты на человека. Сохранить исходное размещение, не делить ставку на два и не выдавать её за подтверждённый single-тариф. Подпись «Ориентир по цене отдельного номера в этой гостинице». |
| 3. Ориентир по местному рынку | Объект и город подтверждены, а прямой цены нет. Есть хотя бы два независимых объекта-донора с проверенной сопоставимой ночной ставкой за частную комнату, в том же городе или ясно обозначенной локальной зоне, сопоставимого типа. | Сначала использовать близкий район, класс и свежие данные. При пропусках в звёздности разрешить более широкий ориентир по городу и типу жилья. Хостел с отдельными комнатами сравнивать с такими же комнатами. Брать медиану нормализованных ставок, хранить доноров и разброс, явно подписывать «Оценка по другим объектам города». |

Если в каталоге ещё нет доноров, **искать рыночные ставки отдельно от поиска конкретного отеля**. Например, выделить один ограниченный запрос на подходящие местные прайсы сразу для всей задачи. Сохранить наблюдения для других кандидатов. При переносе подхода стенда взять работу с сопоставимыми объектами; исключить режим, где число выводилось из бюджета пользователя или из ответа модели без источника. Не использовать цепочку «оценка по аналогам одного объекта стала тарифом второго». [Методика экспериментального стенда](../experiments/deepseek-web-controlled/lodging.py)

Для уровней 2–3 проверить явный `maxTotalRub` по итоговой оценке и показать, что сумма приблизительна. Если единственная доступная цена относится к койке, платежу рассрочки, пакету с перелётом, имеет неизвестную валюту или непонятное количество комнат, перейти к другим наблюдениям. Защитить расчёт для «два номера за одну ночь» от повторного умножения. Для `sourceUrl` сохранить проверяемую ссылку на объект или его ставку; источники оценки по рынку вынести в детали подбора. В конструкторе тип оценки должен быть виден до выбора отеля, в том числе для кандидата со старым тарифом.

## 5. Диагностика, кэш и совместимость

Для каждого перехода сохранять конкретный исход: неверный город, не удалось связать филиал, неоднозначный блок, не распознана единица, валюта не определена, курс недоступен, не хватает доноров, обязательное условие не подтверждено, превышен потолок. Например, когда строка с ценой найдена, а сопоставление филиала не прошло, записать обе части. Общая причина `missing_rate` на уровне объекта скрывает эту разницу. В метриках задачи вывести числа **уникальных объектов** по этапам «обнаружено → подтверждён город → принято по каждому из трёх оснований → выдано». Отдельно указать токены, вызовы и время. Отклонение одного предложения и успешное принятие другого у того же отеля не должны удваивать счётчик объектов.

Тёплый каталог должен использовать проверенные факты и повторно оценивать применимость под новые даты, состав группы, цель и условия. Учитывать версию обработчика у старых отказов и приблизительных оценок, чтобы предыдущий `missing_rate` не мешал новому разбору, а догадка о цене не превратилась в опубликованный тариф. При появлении более сильного основания обновлять следующую выдачу. Проверить повторный POST, восстановление и GET завершённого снимка, недопустимость дублей при «Ещё» и доступ владельца к журналу. При исчерпании времени или квоты сохранить готовую часть по действующим правилам `partial/failed`. Если выдача пуста при неизвестном запасе, показать, сколько объектов обнаружено и чего не хватило для оценки. ## 6. Как проверить, что исправлен класс ошибок

**Сначала офлайн.** Сделать воспроизводимые тесты через обычные POST и polling с подменой поставщиков на границе HTTP. Для регрессий взять сохранённые страницы и первоначальные ответы Flash из истории: разработчик не должен вручную переписывать ID источников или упрощать строки до удачного формата. Затем менять название объекта, порядок страниц, язык, валюту и формат URL при неизменном смысле. Проверять и результат, и основание цены. [Тесты](../tests/test_hotels.py) · [Подмена поставщиков](../tests/hotel_fixtures.py)

| Проверка | Ожидаемый результат |
|---|---|
| Название и город указаны моделью на разных страницах. Город есть и в заголовке первой. Блок номера на третьей языковой версии однозначен. | Реальный вариант доходит до `items` без нового Search. Число и источник итоговой ставки можно сверить. |
| Две локали одного провайдера, одинаковый ID, разные написания адреса. Затем заменить ID второй страницы на ID соседнего филиала. | В первом случае разрешена привязка и отдельно проверена цена. Во втором цена чужого филиала не попадает к объекту. |
| Категория single дана заголовком; на другой странице тот же термин встречается только в описании кроватей. | В первом случае проходит тариф при подтверждённых остальных полях. Во втором не появляется ложное подтверждение одноместности. |
| Две комнаты одного отеля, один неверно указанный блок, один подходящий тариф. Затем подменить сумму так, чтобы подходили два разных блока. | Восстановить единственное соответствие, сохранить нормальный тариф. Не выбирать произвольно при неоднозначности. |
| У объекта есть только опубликованная цена частной комнаты другой вместимости; во втором прогоне прямой цены нет, есть два местных донора. | Получить подписанные основания уровней 2 и 3 соответственно. Проверить медиану, курс, число комнат и ночей. При добавлении точного тарифа отдаётся более сильное основание. |
| У объектов нет пригодных прямых ставок или доноров; либо найдено только жильё в другом одноимённом городе. | Объяснимый недобор. В выдаче нет выдуманной цены, чужого города или номера с невыполненным обязательным требованием. |
| Мягкая цель 400 000 ₽, явный потолок отсутствует, подходящие оценки заметно дешевле. | Цель попадает в первый план, доступные варианты выдаются со своей ценой и пометкой об отклонении. Повтор с другой целью не меняет исходную стоимость того же предложения. |

**Затем измерить переносимость.** До настройки зафиксировать две группы. В первой — известные проблемные сценарии для отладки. Во второй — минимум шесть других направлений: крупный город, небольшой населённый пункт, одноимённые города, разные языки и валюты, случаи с покрытием российского поставщика и без него. Названия, URL и номера источников из контрольной группы не добавлять в правила. Для каждой карточки запросить два разных варианта. Отдельно взять отрицательный сценарий без подтверждаемых объектов. Если разработчик изучил контрольный пример и донастроил на нём алгоритм, для финальной проверки взять новый пример.

Сравнить текущую и новую сборки на одинаковых запросах, начальных снимках каталога и, где возможно, одинаковых ответах источников. Холодные и тёплые запуски считать отдельно. Главные числа — **сколько запросов дали ≥1 вариант**, **сколько дали весь пакет**, **сколько вариантов получены на каждом уровне оценки**, сколько стоили успешные и пустые попытки. Показать числители и знаменатели. Не исключать неудачные города из общей таблицы. Для разбора результата отдельно отметить, где ручная проверка сохранённых источников действительно нашла пригодное основание.

**Критерий сдачи.** На фиксированных положительных сценариях с достаточным основанием должна возвращаться хотя бы одна гостиница; там, где подготовлено два разных подходящих объекта и запрошено два, — обе. Все отрицательные проверки из таблицы должны пройти. На отдельной группе показать прирост покрытия относительно исходной сборки, вручную сверить город и расчёт для первых выданных вариантов, назвать оставшиеся пустые случаи и их причины. Если рост достигнут только на Мадриде и Стамбуле, задача по обобщению остаётся открытой. Точную долю успеха живого рынка заранее не обещать.

Из `API/` запустить `python -m unittest discover -s tests -v`, гостиничный набор на отдельной PostgreSQL по README и локальную сборку Docker. Через конструктор проверить хотя бы один объект с собственным тарифом, один с рыночной оценкой, повторный выбор и «Ещё». В ответе автору дать сравнительную таблицу, по одной проверяемой цепочке расчёта для каждого основания и результат живого прогона отдельно от фикстур.
