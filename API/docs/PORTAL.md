# Кабинет TripFlow API на Render

Кабинет выдаёт ключи для интеграции с Python API. Его аккаунт служит для разработки и проверки API. Аккаунты основного приложения TripFlow обслуживает C# backend.

| Что открыть | Адрес |
|---|---|
| Вход и заявка | [Кабинет TripFlow API](https://tripflow-api-x1p5.onrender.com/portal) |
| Отправка тестовых запросов | [Swagger](https://tripflow-api-x1p5.onrender.com/docs) |
| Схема опубликованной версии | [OpenAPI JSON](https://tripflow-api-x1p5.onrender.com/openapi.json) |
| Доступность сервиса и БД | [Health check](https://tripflow-api-x1p5.onrender.com/health) |
| Настройки и история выпусков | [Сервис в Render Dashboard](https://dashboard.render.com/web/srv-dc1etrmtlv9c73btv8e0) |
| Статус PostgreSQL | [База в Render Dashboard](https://dashboard.render.com/d/dpg-dc1es9l9fdbs73alib9g-a) |

## Получение API-ключа

1. На странице кабинета нажмите **Запросить доступ**. Укажите email и пароль длиной от 12 до 128 символов. Нажмите **Отправить заявку**.
2. Когда заявку рассмотрят, попробуйте войти с теми же данными. Пока заявка ожидает решения или отклонена, форма входа показывает её статус. После одобрения открывается кабинет. Проверяйте решение здесь.
3. В разделе **Ключ доступа** нажмите **Выпустить ключ** и скопируйте его из диалога. Полное значение показывается при выпуске. В списке остаются последние символы и дата выпуска.
4. Передавайте ключ в заголовке `X-API-Key` во всех запросах создания задач и опроса. Для C# храните его в окружении backend. Для ручной проверки вставляйте его в Swagger через **Authorize**.
5. Если ключ потерян, воспользуйтесь **Перевыпустить**. Старое значение сразу перестанет работать. **Отозвать** отключает действующий ключ. После выпуска нового ключа можно снова читать прежние задачи своего аккаунта.

В **Журнале задач** видны последние 30 заданий, их ID, операция, время и состояние. Счётчики «Всего», «В обработке» и «Завершено» относятся ко всем задачам аккаунта. **Обновить** перечитывает состояние.

## Проверка API через Render

1. Откройте опубликованный Swagger и нажмите **Authorize**. Вставьте значение своего ключа целиком.
2. Разверните `POST /v1/recommendations`, выберите «Отели» или «Достопримечательности» и нажмите **Try it out**. Готовые примеры берутся из запущенной версии. Если меняете параметры, задайте новый `taskId`. Нажмите **Execute** и проверьте ответ `202 Accepted`.
3. Разверните `GET /v1/tasks/{taskId}`. Вставьте ID из ответа POST и отправьте запрос с тем же ключом. `pending` означает, что задача ещё выполняется. Повторите запрос через время из `Retry-After`, сейчас это две секунды. При `completed` прочитайте `result`, где указаны данные или прикладная ошибка.
4. Для сметы воспользуйтесь примером из `POST /v1/budget`. Смета создаёт собственную задачу, которую можно прочитать тем же GET.

В новом контракте `targets` — строка, а `selectedHotel` содержит `objectId` и `price`. В первом релизе `8fabdd7` использовались объект `targets` и поле `tariff`. Актуальный формат на каждом адресе показывает его Swagger. [Ветка выпуска](https://github.com/AndZas/TripFlow/tree/deploy/api) · [Текущий контракт](CONTRACT.md)

| Что видно | Что проверить |
|---|---|
| Render показывает загрузку | Дождитесь запуска и повторите запрос. Бесплатный сервис засыпает при простое. |
| `401 INVALID_API_KEY` | Проверьте, что Swagger авторизован с действующим ключом. |
| `404 TASK_NOT_FOUND` | Проверьте ID, базовый URL и аккаунт ключа. |
| `409 TASK_ID_CONFLICT` | Используйте новый ID для изменившегося тела или другой операции. |
| `422 VALIDATION_ERROR` | Сверьте отправленное тело со Swagger именно того адреса, на который отправляете запрос. |

## Конструктор карточки

Вкладка доступна всем одобренным пользователям. Для запуска из конструктора достаточно войти в кабинет. Swagger и внешние клиенты используют `X-API-Key`.

1. Откройте **Конструктор карточки**. Введите город, даты, число путешественников, общий бюджет и пожелания. **Заполнить пример** подставляет тестовую поездку.
2. В **Настройках подбора** можно изменить количество, лимит и уточнение для каждой категории. **Подобрать отели и места** создаёт отдельную задачу для отелей и отдельную для достопримечательностей. Готовые списки появляются по мере завершения.
3. **Подобрать ещё** запускает новую задачу по нужной категории с исключением уже показанных объектов. Текущий выбор сохраняется. При изменении исходных параметров поездки выполните подбор заново.
4. Выберите один отель или **Без отеля**, отметьте нужные места и нажмите **Рассчитать смету**. Python вернёт четыре статьи дополнительных расходов.
5. **Запрос и результат JSON** показывает тело для публичного API, ID задачи и результат опроса. Все задачи, созданные в конструкторе, попадают в **Журнал задач** того же аккаунта и доступны по его API-ключу.

Конструктор работает с тестовым каталогом Москвы. Его тела запросов, обработчики и хранилище совпадают с публичным API. [Контракт и JSON-примеры](BACKEND-HANDOFF.md)

## Заявки и роли

Владелец и администратор открывают **Заявки и пользователи**. В блоке **Ожидают решения** видны новые заявки. Кнопка **Одобрить** открывает доступ сразу, **Отклонить** оставляет доступ закрытым. **Обновить** перечитывает список.

| Роль | Что доступно |
|---|---|
| Разработчик | Выпуск и отзыв своего ключа, чтение своих задач. |
| Администратор | Те же функции, рассмотрение обычных заявок и активность аккаунтов разработчиков. |
| Владелец | Список всех аккаунтов и их активность. Назначение и снятие администраторов. Отключение аккаунтов и рассмотрение заявок после отключения. |

Владелец выдаёт роль через **Назначить администратором** в карточке уже одобренного разработчика. **Снять роль администратора** возвращает роль разработчика. **Отключить доступ** отзывает сессии и текущий API-ключ, а администратор становится разработчиком. История задач остаётся. Для восстановления пользователь отправляет новую заявку с прежними email и паролем, а решение принимает владелец.

В карточке пользователя откройте **Активность API**. В ней видны число запросов за последние 24 часовых интервала и метрики за семь дней. Метрики включают попытки запуска задач, опросы, HTTP-ошибки, пиковое количество запросов за час и час последнего запроса. Это счётчики запросов с действующим ключом. Число созданных задач отображается отдельно, поэтому повтор POST может увеличить счётчик запросов без создания новой задачи.

## Эксплуатация на Render

Код публикуется из `deploy/api`. PostgreSQL хранит аккаунты, ключи, задачи и метрики между перезапусками. Бесплатный инстанс PostgreSQL действует 30 дней с создания. Дату окончания показывает страница базы. Установка переменных, настройка health check и порядок выпуска описаны в README. [Запуск и выпуск](../README.md#размещение-на-render) · [Условия Render](https://render.com/docs/free)

Если это первое размещение с пустой базой, владелец входит с email и паролем начальной настройки. После успешного входа эти две переменные можно удалить из Environment и сохранить изменение. Переменная `DATABASE_URL` нужна сервису при каждом запуске.
