# Stage 2 · Исправление подбора отелей по результатам ревью

**Задача для разработчика.** Исправить пять воспроизведённых дефектов гостиничного поиска. Пользователь должен иметь возможность подобрать отель в конструкторе, проверить основание цены и понять причину остановки, если подходящий вариант получить не удалось. Критерии ниже рассчитаны на проверку через обычный путь создания задачи и polling, включая повторный поиск по накопленному каталогу.

Рабочая область — локальная сборка в `API/`. Для проверки использовать Docker и отдельную тестовую БД. Коммиты и выкладка на Render в эту задачу не входят. Публичные поля отеля, семантика `taskId`, `partial`, `hasMore` и правила расчёта остаются точками совместимости с C#. Подробную диагностику показывать в кабинете владельца задачи. [Исходное ТЗ Stage 2](STAGE-2-HOTELS.md) · [Контракт интеграции](BACKEND-HANDOFF.md) · [Кабинет](PORTAL.md) · [Инструкции для API](../AGENTS.md)

## 1. Исходный сценарий и контрольные результаты

В конструкторе выбрали Санкт-Петербург, RU, координаты 59.938732, 30.316229, заезд 1 декабря 2026 года, выезд 4 декабря, два путешественника, общий бюджет 85 000 ₽, `targets="hotels"`, `count=2`, `maxTotalRub=null`. В карточке были пожелания. Расчёт проживания охватывает три ночи и два отдельных номера. Для точного локального повтора взять исходный JSON из истории задачи и заменить только `taskId`. Контроль без пожеланий и с `count=1` — другой эксперимент.

| Что проверили при ревью | Что получили |
|---|---|
| Две задачи пользователя, включая повтор из портала | Обе вернули `failed`, пустые `items` и `HOTEL_TOKEN_LIMIT`. Суммарно 65 797 фактических токенов гостиничного Flash, без Stage 1. В каталоге было девять объектов с пустыми `rates`. |
| Повтор исходного запроса через авторизованный `POST /portal/data/builder/recommendations` на отдельной БД с копией гостиничного каталога | HTTP 202, по завершении снова `failed` и ноль отелей. За 55,8 с выполнено 5 Search, 5 Fetch и 5 Flash. Гостиничный Flash израсходовал 28 051 входной и 5 468 выходных токенов. |
| Чистый каталог, тот же город и даты, один отель, без пожеланий | За 28,1 с вернулась «Академия» за 25 860 ₽ на группу. В ссылке на объект стояли даты 6–9 ноября. Это повод отдельно проверить источник именно **ставки**. Сам дефект переноса цены между датами подтверждён изолированным тестом из раздела 4. |
| Контроль совместимости | Прошёл 41 тест на SQLite. Отдельно прошли 14 гостиничных тестов на PostgreSQL 13. Подсказки городов, моковые места и смета отработали. Существующие фикстуры пропускали ошибки ниже. |

**С чего начать.** На доступной копии SQLite прочитать `tasks.payload`, `hotel_diagnostics.outcome` и `hotel_attempts` по паре `client_id, task_id`, в порядке `attempt`. Поля `kind, request_bytes, output_reserved, usage, error` позволяют восстановить расход. В `response` сохранены ответы Search, Fetch и извлечения Flash. Отказ перед резервированием шага не создаёт строку физического вызова. Сохранить в тестовых фикстурах только короткие обезличенные фрагменты страниц, ответы извлечения и нужные счётчики. Если локальная история недоступна, примеры ниже дают воспроизводимые входы без ключей и сетевых запросов. [Тесты](../tests/test_hotels.py) · [HTTP-фикстуры](../tests/hotel_fixtures.py)

## 2. Первый приоритет · Бюджет вызовов и повтор после остановки

**Причина цикла.** `HotelSearch.extract` берёт до шести новых страниц и четырёх предыдущих, ограничивает набор девятью и передаёт фрагменты до 2 600 символов каждый. За каждый вызов извлечения резервируются 3 200 выходных токенов. Для русского текста число UTF-8 байт заметно больше числа символов. В двух исходных задачах следующая порция превысила общий предел входа 150 000 байт. Резерв выхода ещё помещался в 18 000 токенов. Обе проверки возвращают один внутренний `token_limit`. После отказа `extract` записывает причину и возвращает управление наружному циклу, который всё ещё может вызвать Search и Fetch. Новый `taskId` получает новый бюджет, но при отсутствии пригодных ставок снова доходит до дорогого извлечения. [Цикл поиска, gaps и extract](../tripflow_api/hotels.py) · [Атомарный учёт HotelTools.step](../tripflow_api/hotel_tools.py)

**Предлагаемое исправление.**

1. Вычислять остатки по **отдельным единицам** — физическим Search/Fetch/Flash, байтам сериализованного Flash-запроса, резерву выхода и времени. Измерять собранный запрос той же сериализацией UTF-8, что и `step`, включая промпт и оболочку. Предварительная проверка нужна планировщику, а последняя атомарная проверка остаётся в транзакции с проверкой владения задачей. Сохранённый ответ шага при восстановлении по прежнему ID остаётся доступным даже после расходования бюджета.
2. После обнаружения объектов выбирать кандидата и конкретный пробел — например, «есть точный адрес и одноместный номер, нужна ставка за ночь». Передавать подходящий фрагмент тарифа с соседним заголовком. Повторную передачу того же текста оправдывает новая проверка, для которой он нужен. Порядок кандидатов определять по недостающим подтверждениям и предыдущим попыткам. Сейчас `gaps` обрезает список до четырёх, а точечный цикл берёт первые два.
3. Если порция не помещается, уменьшить её до осмысленного блока и проверить размер снова. Если остатка недостаточно даже для проверки одного кандидата, завершить поиск сразу после оценки уже сохранённых фактов. При недоступности одного инструмента продолжать лишь те действия, которыми ещё можно подтвердить результат. Отмечать `rateSearchCompleted` только после реально выполненной точечной проверки. Повторная ссылка на ещё не разобранную страницу сама по себе такой проверкой не является.
4. При новой попытке использовать проверенные объекты и уже известные пробелы. Для точного повтора брать подходящие результаты предыдущей работы с учётом аккаунта, дат, условий и исключений. Для изменившейся карточки заново оценивать применимость. Параллельные задачи, повторный GET и восстановление старого POST не должны задваивать платный шаг. Не переносить пожелания другого аккаунта с общим объектом гостиницы.
5. В кабинете различать «исчерпан объём текста для анализа», резерв выхода, число вызовов и ответ провайдера. Показать этап, использованное значение, предел и число объектов с подтверждённой ценой. Фактические токены брать из `usage`. Сообщение для карточки может выглядеть так: «Нашли 9 объектов. Ни для одного пока не подтвердили цену на ваши даты. Поиск остановлен по лимиту объёма текста». Подставлять фактические числа задачи. При сохранении старого публичного кода внутреннюю причину и разбор расхода можно добавить в личную диагностику. [Диагностика каталога](../tripflow_api/hotel_catalog.py) · [Представление метрик](../tripflow_api/portal_assets/preference-view.js) · [Повтор в конструкторе](../tripflow_api/portal_assets/card-builder.js)

**Приёмка.** На фикстуре с длинными кириллическими страницами проверить три границы — точное попадание в лимит, превышение входа на один байт и отдельное превышение резерва выхода. Положить подтверждаемую ставку в небольшой блок, который помещается в остаток. Поиск успевает проверить его. На варианте, где минимальная проверка уже невозможна, после остановки счётчики бесполезных внешних вызовов не растут. При одном готовом отеле из двух вернуть `partial` с этим отелем, при нуле — `failed`; в обоих случаях `hasMore=null`. Для повтора проверить по журналу, какой пробел он закрыл. Увеличение констант само по себе этот тест не закрывает.

## 3. Русские тарифы · Извлечение, дословность и условия

**Почему объекты остаются без цены.** `NIGHT` пропускает «за 1 ночь», `OCCUPANCY` пропускает «для 1 гостя», а `checked_rate` отклоняет любое непустое `caveat`. Другая причина независима от регулярных выражений. По «Артбокс отелю» и «Мэдоу» Flash склеил название номера, цену и единицу через `...`. В сохранённых источниках таких непрерывных цитат нет. Проверка дословности отработала правильно. По «Лайту» сумма и «за 1 ночь» действительно присутствовали, но одна эта строка ещё не доказывает одноместное размещение. [Подготовка excerpt, verified и checked_rate](../tripflow_api/hotel_evidence.py) · [Промпт EXTRACT](../tripflow_api/hotels.py)

**Как исправить.** Выделять на стороне Python блок одного предложения — заголовок номера, строку ставки, единицу и относящиеся к ним сноски. Можно передать модели пронумерованные строки, попросить ссылки на них, а дословные выдержки восстановить в Python. Для нескольких выдержек проверять каждую по исходному тексту и проверять их связь с одним отелем, номером и тарифом. Одинакового URL у двух строк таблицы недостаточно. При повторном использовании выдержек сохранять исходный URL каждой. Затем распознавать словоформы ночи и размещения и классифицировать ограничения. Невозвратность и отсутствие питания можно сохранить как свойства тарифа. Если путешественник требует завтрак или бесплатную отмену, проверить их для выбранной ставки. Обязательная неизвестная доплата, скидка по недоказанному членству и неясная единица оставляют сумму непригодной.

| Регрессионный вход | Ожидаемый результат |
|---|---|
| «Одноместный номер — 2 100 ₽ за 1 ночь»; «Отдельный номер для 1 гостя — 2 100 ₽ за ночь» | Оба дают ставку 2 100 ₽ за номер за ночь. Два номера на три ночи дают 12 600 ₽. |
| Та же строка, «без питания, оплата не возвращается», пожеланий о питании и отмене нет | Ставка пригодна, оговорки доступны в диагностике. При обязательном включённом завтраке эта ставка не проходит. |
| Заголовок одноместного номера и цена на двух строках его тарифа; второй пример с ценой в соседнем двухместном тарифе | Первый проходит с двумя проверяемыми выдержками. Второй отклоняется. Вставленные моделью многоточия не считаются доказательством. |
| «от 2 100 ₽» за подтверждённый одноместный номер за ночь; «4 800 ₽ за человека, авиаперелёт включён» | Первый сохраняется с типом «от». Из второго нельзя получить стоимость отдельного номера. |

В диагностике различать хотя бы отсутствующую цитату, неизвестное размещение, единицу и неприменимое условие. Иначе все четыре случая снова выглядят одинаково как «нет подходящей ставки».

## 4. Даты · Привязка цены к предложению и повторное использование

**Минимальный пример.** У страницы параметры `checkin=2026-11-06&checkout=2026-11-09`. Заголовок сообщает «Цены на выбранный период 06.11.2026 — 09.11.2026», строка ниже — «Одноместный номер 4 310 ₽ за ночь». Модель процитировала только строку и оставила `start/end=null`. В таком виде `checked_rate` сохранил ставку, а `rate_applies` допустил её на 1–4 декабря. На двух путешественников получаются арифметически верные 25 860 ₽ из неприменимой ставки. [Проверка ставки и дат](../tripflow_api/hotel_evidence.py) · [Повторное использование в evaluate и analogs](../tripflow_api/hotels.py)

**Как исправить.** Для ставки хранить источник и область действия — предложение на выбранные даты, опубликованный интервал действия тарифа либо общий прайс. Передавать на проверку заголовок и контекст предложения. Учитывать известные параметры бронирования, включая пары `public_filter_checkin_date/public_filter_checkout_date`. URL с другими датами — сигнал сверить основание цены. Даты публикации статьи и даты соседних предложений к ставке не относятся. Если цена взята с отдельной страницы общего прайса, проверить именно эту страницу. Неоднозначные или противоречивые основания требуют повторной проверки. Пустые поля ответа Flash не подтверждают бессрочность.

Проверять область действия до сохранения и перед расчётом по каталогу, в том числе для гостиниц-аналогов. Датированное предложение на фиксированный заезд использовать на те же даты; для сезонного прайса проверять все ночи внутри периода. У старой записи без достаточного контекста переиспользовать идентичность отеля и перепроверить тариф. Сохранённый результат ранее завершённой задачи остаётся историческим снимком.

**Приёмка.** Ноябрьская ставка подходит исходному ноябрьскому предложению, не попадает в декабрьскую выдачу ни на холодном, ни на тёплом поиске и не участвует в декабрьской медиане. Подтверждённый общий прайс остаётся пригодным на обе поездки. Для старой записи проверить стабильность `objectId` после получения нового тарифа.

## 5. Время · Проверка услуги и интервала

**Минимальные примеры.** Передать в `adequate_timing` обязательное условие и проверку Flash с `verdict="confirmed"`. Сейчас функция принимает обе пары из первых двух строк таблицы. Ветка «24 часа» может завершить проверку до сопоставления услуги. Для числового заезда ветка с «полуночью» не вызывается при формулировке «заезд в 01:30», и наличие часов в цитате позволяет дойти до общего `True`. [adequate_timing и conditions_for](../tripflow_api/hotels.py)

| Требование | Дословное основание | Ожидание |
|---|---|---|
| Завтрак до 07:00 | «24-hour reception» | Время завтрака неизвестно. Обязательное условие не выполнено для целей выдачи. |
| Заезд в 01:30 | «Стойка регистрации с 07:00 до 23:00» | Заезд в 01:30 не подтверждён. |
| Заезд в 01:30 | «Заселение с 22:00 до 02:00» | Подтверждено при применимости к дню заезда. Проверяется переход через полночь. |
| Завтрак до 07:00 | «Завтрак с 06:30 ежедневно» | Подтверждено при соответствии выбранному тарифу. Если источник говорит «только в выходные», проверить дни поездки. |

**Как исправить.** Сначала установить, к какой услуге относится цитата, затем проверить интервал в минутах местного времени, его границы, день и тариф. Обрабатывать явное «круглосуточное заселение» как положительный пример для заезда. Сохранять различие между «неизвестно» и явным противоречием. Для `required` неизвестность исключает вариант, для `preferred` влияет на ранжирование. Проверить также сохранённую в каталоге доказательную базу и ранее записанные проверки условий при новом подборе. Тест должен намеренно подать ошибочный `confirmed` от модели и дойти до результата категории.

## 6. Местоположение · Проверка страны до записи в каталог

**Минимальный пример.** Входное направление — Paris, FR с координатами французского Парижа. Страница конкретного отеля содержит «Paris, Texas, USA», координаты объекта отсутствуют. `checked_candidate` принимает цитату, затем `HotelSearch.extract` находит в ней слово Paris и вызывает `catalog.store` с кодом страны из запроса. Проверка расстояния срабатывает только при наличии координат отеля. Страна, подставленная из запроса при записи, не может служить подтверждением страны источника. [Проверка объекта](../tripflow_api/hotel_evidence.py) · [Проверка города перед store](../tripflow_api/hotels.py) · [Каталог](../tripflow_api/hotel_catalog.py)

**Как исправить.** Проверять адрес конкретного филиала до записи. Сопоставлять указанные в адресе название или код страны, регион и подтверждённые координаты с выбранным направлением. Разбирать страну в контексте адреса, чтобы слово Paris в названии отеля или перечень стран в подвале страницы не стали основанием. Явное противоречие отклонять. Если у одноимённых городов страна или регион не определяются, искать дополнительное подтверждение по тому же филиалу. Варианты написания города от Flash помогают найти страницу, но сами по себе не подтверждают географию.

**Приёмка.** «Paris, Texas, USA» не сохраняется для Paris, FR. «Paris, France» с подтверждённым адресом проходит и без координат объекта. Одна надпись «Paris» при неоднозначном местоположении требует дополнительного источника. Прогнать второй запрос по тёплой БД и проверить также списки кандидатов для расчёта по аналогам. Для ранее сохранённого объекта с явным конфликтом предусмотреть перепроверку до выдачи.

## 7. Порядок реализации и сдачи

1. Сначала зафиксировать примеры разделов 2–6 падающими тестами. Для короткого цикла разработки запускать гостиничный набор. Для петербургского сценария воспроизвести ответы на границе HTTP с помощью существующего `HotelProvider`. Подготовить два случая — на страницах есть достаточные доказательства и на страницах их действительно нет.
2. Исправить извлечение тарифа, даты, условия и страну. Это даст планировщику конкретные причины для следующего запроса. Затем исправить распределение бюджета, повтор и отображение диагностики. Сохранить поддержку старых записей SQLite/PostgreSQL, исключений `excludedObjectIds`, прерванной задачи и изоляции кабинетов.
3. Из каталога `API/` выполнить команды ниже. Для отдельной тестовой PostgreSQL перед повтором гостиничного набора задать `TRIPFLOW_TEST_DATABASE_URL` по README. Сверить результаты с исходными 41 и 14 тестами с учётом добавленных регрессий. [Запуск тестов и локальной сборки](../README.md)
