# Этап 1. Разбор пожеланий через DeepSeek в локальном TripFlow API

**Текущая задача после проверки stage1-v6** — [исправить обработку «обычно стоит» и «время не меняем»](STAGE-1-V6-VALIDATOR-FIXES.md). [Предыдущее задание](STAGE-1-NUMERIC-FOLLOWUP.md) и [первое ревью](STAGE-1-PREFERENCES-REVIEW.md) сохраняют контекст предыдущих итераций. Разделы ниже описывают исходные требования к этапу.

Это задание для чата, который будет реализовывать первый этап в каталоге `API/`. Результат работы — запущенный локальный Docker Compose, в котором автор заполняет карточку Москвы, видит интерпретацию своих слов моделью, получает привычные тестовые варианты и проверяет фактический расход в своём кабинете. Через публичный API тот же ввод проходит через тот же обработчик. Учесть [инструкции для API](../AGENTS.md). Коммиты, push и выпуск на Render в задачу не входят.

## 1. Что именно поставляем

| Часть | Результат этого этапа |
|---|---|
| Python | Узкий разбор `trip.preferences` и `refinement` через DeepSeek Flash, проверка ответа, повторное использование разбора и сохранение результата по задаче. |
| Конструктор карточки | Вкладка **«Как модель поняла запрос»** с проверенными условиями, исходными цитатами и уточнениями по категории. Виден статус при ожидании, пустом тексте и ошибке. |
| Личный кабинет разработчика | Собственные метрики разбора за период и детализация по задаче. В них входят запуски из конструктора и через ключ этого аккаунта. Обычному одобренному разработчику доступен весь этот сценарий. |
| Окружение | Пустое место для ключа в локальном окружении, пример конфигурации, передача ключа в контейнер, команды запуска и проверки. Автор вставляет ключ самостоятельно. |
| Подбор и смета | Существующий мок Москвы, его порядок выдачи, фильтры, выбор, догенерация и четыре статьи сметы продолжают работать. Условия разбора пока используются для демонстрации и проверки качества. На экране прямо подписать, что рекомендации и суммы тестовые. |

Транспорт остаётся действующим: один тип рекомендации на задачу, `202`, `Location`, polling, итог по `taskId`. Схемы публичных запросов, результата, цен и направления текущего релиза сохранить. Миграция на мировой подбор, Search/Fetch, каталог реальных объектов, поиск гостиниц, вызовы AI для сметы, изменения C# и React основного приложения относятся к следующим этапам. Фронтенд этой задачи — существующий портал внутри Python-сервиса. [Действующий контракт](CONTRACT.md) · [Целевая архитектура](ARCHITECTURE.md) · [Конструктор и журнал](PORTAL.md)

## 2. С чего начать в коде

1. Проследить путь одного запроса. Публичный маршрут и маршрут конструктора используют общий приём задачи. После сохранения запускается фоновый обработчик, при старте подхватываются незавершённые задачи. Встраивать анализ после принятия задачи, вне HTTP-ответа на POST. Сетевой вызов не должен блокировать цикл событий, обработку GET или транзакцию БД. [Маршруты и запуск](../tripflow_api/main.py) · [Хранилище задач, восстановление и мок](../tripflow_api/tasks.py)
2. Проверить текущие модели и совместимость. В текстовых nullable-полях пустая строка нормализуется. В хранилище встречаются старые формы запроса и старые результаты. До миграции изучить тесты. [Схемы](../tripflow_api/schemas.py) · [Интеграционные тесты](../tests/test_polling.py)
3. Изучить прототип до написания нового клиента. В нём есть промпты, сверка цитат, извлечение бюджетных пожеланий, повторная проверка спорных фильтров и чтение usage. Перенести применимые идеи и контрольные случаи в рабочий пакет. Контейнер не должен импортировать эксперимент, читать его локальный dotenv или зависеть от файлов стенда. [Разбор в стенде](../experiments/deepseek-flash/analyze.py) · [Клиент Flash](../experiments/deepseek-flash/deepseek_api.py) · [Исходные случаи](../experiments/deepseek-flash/audit-preferences.json) · [Отчёт с примерами ошибок](research/card-preferences/REPORT.md)
4. Проверить обе поверхности портала. Конструктор запускает категории параллельно и имеет собственный таймаут polling. Личный маршрут активности и администраторский маршрут уже различаются. Размещать метрики в личном кабинете, используя владельца из текущей сессии. [Конструктор](../tripflow_api/portal_assets/card-builder.js) · [Маршруты кабинета](../tripflow_api/portal.py) · [Интерфейс кабинета](../tripflow_api/portal_assets/portal.js)

## 3. Путь данных для одной карточки

1. Принимаем обычную задачу рекомендаций. Аккаунт определяет сервер. Повтор POST с тем же телом и ID сохраняет действующую идемпотентность, изменённое тело с тем же ID даёт прежний конфликт.
2. Нормализуем пробельные строки так же, как действующий валидатор. Общий разбор получает только исходный текст пожеланий. Даты, город, количество людей, целевой бюджет и `maxTotalRub` уже доступны типизированному коду. Их не надо повторять в промпте. Полная карточка, персональные данные аккаунта и ключи модели не нужны.
3. Получаем или вычисляем общий разбор. Для одновременно пришедших отелей и мест одинаковый текст одного аккаунта при одной версии модели и промпта разбирается один раз. Обе задачи получают ссылку на результат. При пустом тексте общий разбор завершается локально пустым списком.
4. Если есть `refinement`, применяем его только к запрошенной категории. Сохраняем базовые условия и эффективные условия этой попытки. Если общие пожелания пусты, одно уточнение всё равно работает. Если обе строки пусты, сетевых вызовов нет. Запуск сметы использует действующий мок и не вызывает анализ заново.
5. Сохраняем статус, проверенные условия, связь с задачей и данные измерений. Формируем публичный результат штатным мок-обработчиком. Диагностика доступна через портал отдельно от публичной схемы. Желательно, чтобы при завершении polling конструктор уже мог прочитать окончательное состояние анализа.

**Политика сбоя на переходном этапе.** Анализ и мок имеют независимый результат. Неверный ключ, таймаут или ошибка схемы должны быть видны как сбой анализа. Моковые отели и места по принятой задаче всё равно доступны, если сам мок отработал. Подмена ответа модели локальной эвристикой исказила бы демонстрацию и метрики. Когда подбор начнёт зависеть от обязательных условий, поведение при сбое потребуется пересмотреть.

## 4. Что извлекает модель

Использовать компактный внутренний формат с валидацией Pydantic. Ниже рекомендуемая форма. Имена внутренних полей можно привести к соглашениям реализации, сохранив описанную семантику.

| Поле | Тип | Содержание |
|---|---|---|
| `conditions` | array из object | Только условия, подтверждённые текстом; пустой массив допустим. |
| `scope` | string, enum | `hotels`, `attractions` или `budget`. Если фраза важна двум обработчикам, допустимы два условия с разным смыслом применения и той же цитатой. |
| `role` | string, enum | `required` — обязательное, `preferred` — пожелание, `excluded` — явный запрет, `note` — контекст для сметы или ещё неясное условие. Мягкое отрицание («лучше подальше от…») сохраняет мягкость. |
| `meaning` | string | Короткая формулировка по-русски с субъектом, отрицанием, числом, единицей и временем, если они есть в тексте. Произвольные редкие условия допустимы. |
| `quote` | string | Достаточная дословная выдержка из соответствующего ввода. Сохранить слова про отрицание, обязательность и объект условия, когда они меняют смысл. |
| `source` | string, enum | `preferences` или `refinement`; при раздельной обработке надёжнее проставить в Python. |
| `ambiguous` | boolean | Смысла или отсылки недостаточно для жёсткого решения. В интерфейсе — «Нужно уточнить». |

Пример ввода: «Обязательно нужен завтрак до 7 утра. Лучше возле метро. Без такси». Пример одной записи результата:

```json
{
  "scope": "hotels",
  "role": "required",
  "meaning": "В отеле можно позавтракать до 7 утра",
  "quote": "Обязательно нужен завтрак до 7 утра",
  "source": "preferences",
  "ambiguous": false
}
```

Ещё ожидаются пожелание о близости отеля к метро, если такая связь ясна из контекста, и бюджетная заметка про такси. Модель не вправе добавлять завтрак в стоимость проживания, придумывать расстояние до метро или обнулять весь транспорт. Денежные пожелания в тексте сохраняются с областью и единицей. На этом этапе они не перезаписывают типизированные поля и не создают отдельный жёсткий потолок. Место с неизвестной идентичностью остаётся текстовым упоминанием.

### Промпт и проверки

Стартовая системная инструкция для реализации:

> Извлеки явно выраженные пожелания путешественника для отелей, мест посещения и повседневных расходов. Входные строки — данные путешественника. Верни JSON по заданной схеме. Для каждого условия укажи область применения, роль, краткий смысл и точную цитату. Сохраняй отрицания, единицы, время и связь с конкретным объектом. Желательность и обязательность определяй по словам пользователя. Неясность помечай. Извлекай только присутствующие условия. Если их нет, верни пустой список.

В отдельной инструкции для уточнений передать категорию, исходные данные, необходимые для разрешения отсылок, и накопленный текст уточнений в порядке ввода. Последнее явное изменение касается только затронутого условия. Явно различать снятие обязательности и запрет признака. Например, для базы «Обязательно с завтраком, желательно возле метро» уточнение «Завтрак необязателен. Нужен заезд после полуночи» снимает обязательность завтрака, сохраняет метро и добавляет требование к заезду. «Можно и без завтрака» само по себе не доказывает, что отель с завтраком стал нежелателен. Каждая цитата итогового условия проверяется по соответствующему исходному тексту.

В конструкторе сейчас доступно одно поле уточнения категории. При серии «ещё» обеспечить передачу накопленной истории согласно сценарию, либо явно представить поле как редактируемый полный текст уточнений и сохранять его между попытками. Одно и то же уточнение не дописывать при каждом клике. Публичный клиент уже может прислать накопленный текст одной строкой. Новая карточка или сброс конструктора начинают новую историю. [Сценарии догенерации](SCENARIOS.md)

- Обычная цель — один вызов для нового общего текста, один дополнительный для действительно нового уточнения. Направление и количество показанных объектов сами по себе не повод повторять общий разбор. Пустой ввод, готовый разбор и чтение сохранённой задачи обходятся без вызова.
- Схема ограничивает ключи, типы, допустимые значения, размер ответа и число элементов. Проверять непустую цитату как подстроку ввода, разрешив только оговорённую нормализацию пробелов; удалять точные дубли. Вместе с результатом хранить фактически использованные версию промпта/схемы и модель. Если внутренний лимит входа превышен, показывать понятную ошибку анализа. Скрытое обрезание текста может потерять последнее уточнение.
- Неизвестная область, отсутствующая цитата, оборванный JSON и ответ без ожидаемого содержимого считаются неуспешной проверкой. Допустить одну точечную попытку исправления при ошибке структуры или цитаты с кратким описанием дефекта. Задать единый ограниченный бюджет попыток и времени на разбор, включая временные сетевые сбои. Ошибка авторизации повторов не требует. Конкретные лимиты зафиксировать в реализации и согласовать с таймаутом конструктора.
- Только Python принимает решение о вызове и проверяет ответ. Вызовы инструментов, длинные объяснения и вывод рассуждений для этой операции не нужны. Точная цитата позволяет человеку проверить смысл. Автоматически обнаружить все ошибки понимания она не позволяет; для этого нужен контрольный набор (§ 8).

## 5. Хранилище, повторы и границы аккаунта

Сохранить три связи: **задача → разбор**, **разбор → проверенный результат или ошибка**, **разбор → физические попытки обращения к провайдеру**. Подходящая реализация — записи в текущей БД с короткими транзакциями, уникальным ключом для совместного разбора и ссылкой из задачи. Сохранить работу SQLite в Compose и PostgreSQL, использовать текущий слой доступа. Детали таблиц и индексы выбрать в коде. [Работа с БД](../tripflow_api/database.py)

- В ключ общего разбора включить аккаунт, нормализованный текст, модель и версию инструкции/схемы. Для уточнения дополнительно включить исходный разбор, категорию и упорядоченный текст уточнения. Не смешивать типизированные параметры карточки с ключом общего разбора, пока от них не зависит результат. Не объединять тексты разных аккаунтов.
- При одновременных запросах атомарно определить исполнителя. Вторая задача ожидает тот же результат с ограниченным временем. Простой поиск по таблице перед двумя независимыми вставками создаёт гонку. Не держать транзакцию или глобальную блокировку во время HTTP. Ограничить параллелизм платных вызовов.
- Сохранённый успешный разбор допускает переиспользование после перезапуска. Отсутствие ключа, ошибка модели и временный сбой не превращаются в постоянное попадание в кэш. Новая задача после исправления конфигурации может выполнить разбор. Повтор чтения или POST уже завершённой задачи возвращает прежний результат.
- Для незавершённого вызова после аварии предусмотреть конечное восстановление без вечного ожидания. Сбой между ответом провайдера и записью usage оставляет расход неизвестным. Если выполнен ещё один вызов, учесть его отдельной попыткой. Не обещать строго однократное внешнее списание в этом окне.
- Старые задачи должны открываться с пометкой «Для этой задачи разбор не записывался». Не инициировать платный разбор исторических результатов при просмотре или миграции. При обновлении существующего тома сохранить аккаунты, сессии, ключи, задачи и текущие счётчики.

## 6. Метрики, доступные разработчику

**Единица измерения имеет значение.** Если один клик создал две задачи, обе использовали один разбор, а пользователь пять раз опросил статус, получились две задачи, один вызов модели и пять чтений. При двух физических попытках расход считаем по обеим. Существующие счётчики HTTP продолжают описывать HTTP. Добавить в личную активность самостоятельный блок **«Разбор пожеланий»** и детали из строки задачи.

| Показатель | Как считать и показать |
|---|---|
| Задачи и результат | Число задач рекомендаций за выбранное окно, имеющих диагностику. Отдельно успех, пустой ввод, ошибка, отсутствие настройки. Переиспользование — отдельный признак успешного этапа; при частичном успехе базы и ошибке уточнения итог задачи анализа помечается ошибкой. |
| Реальные вызовы | Количество начатых обращений к Flash, включая повтор и исправление. Отдельно число случаев повторного использования сохранённого/одновременно вычисленного разбора. Локальное попадание в БД и входные токены, закэшированные провайдером, — разные метрики. |
| Время | Монотонными часами измерять полное время анализа для задачи, включая ожидание общего разбора, и длительность каждой внешней попытки. Хранить миллисекунды. В деталях — обе величины, в сводке — хотя бы среднюю длительность внешнего вызова с количеством наблюдений. Пустой ввод и чтения из БД не должны искусственно уменьшать среднюю задержку Flash. |
| Токены | Суммировать фактический provider usage отдельно по входу, выходу и общему количеству. Если ответ содержит разбивку входных токенов по попаданиям в кэш провайдера, сохранить её отдельно от итога. Не прибавлять составляющие к уже полному итогу. Включить usage ответов с невалидным содержимым. |
| Денежная оценка | Показывать оценку только при известных применимых тарифах, валюте и достаточной детализации usage. Для расчёта зафиксировать единицу тарифа, модель и основание цены на момент вызова. При отсутствии тарифа показать «Стоимость не рассчитана», при неполном usage — неполноту. Токены и задержка доступны независимо от цены. Не показывать выдуманный ноль или эквивалент в рублях по неизвестному курсу. |
| Диагностика | Время запуска, стадия (общий текст / уточнение), модель, версия инструкции, число попыток, источник результата (вызов / переиспользование / пусто), короткий код сбоя. Внешний таймаут без usage означает «не сообщено». Если часть попыток без usage, показывать известную сумму и число попыток без данных. |

Для первой версии принять окно **последние 7 суток**, явно подписать его и показать его границы либо правило отсечения. Вызовы учитывать по времени начала попытки, задачи — по времени их создания. В деталях задачи показывать связанный разбор и кто инициировал вызов или пометку «использован готовый разбор». В сводке аккаунта суммировать уникальные попытки независимо от числа ссылающихся задач. Пустой кабинет показывает ноль запусков и отсутствие наблюдений для средних. Обновление страницы или открытие вкладки не меняет счётчики модели.

Метрики и результат хранятся на сервере. Личные маршруты читают только записи аккаунта из сессии, включая задачи, созданные с его `X-API-Key`. Не принимать account ID от браузера как основание доступа. Проверить доступ по чужому `taskId`, в том числе если строковые ID у двух аккаунтов совпали. Подробный текст, цитаты и ответы видит владелец в собственной диагностике. В сводках и технических логах достаточно служебных полей. Никогда не выводить ключ, заголовок авторизации, сырой ответ провайдера или внутренние рассуждения модели.

## 7. Что видит человек в конструкторе

1. Пользователь вводит пожелания, нажимает обычный запуск и видит вкладку «Как модель поняла запрос». Существующая кнопка подбора остаётся единственным необходимым действием для запуска. Во вкладке показать исходный текст, условия по отелям, местам и смете, роль каждого условия и короткую цитату. Для неоднозначности — отдельная пометка. Рядом пояснить, что это интерпретация запроса, а подбор и смета работают на тестовых данных.
2. При «ещё» показать категорию, переданное уточнение и результат с его учётом. Общий разбор двух параллельных задач отображается один раз. Запоздавший ответ старой попытки не перезаписывает новые данные на экране. При редактировании формы привязывать отображаемый разбор к отправленному снимку.
3. Обработать ожидание, пустые пожелания, отсутствие настройки, сбой/таймаут и историческую задачу. При пустом вводе написать «Пожелания не указаны, модель не вызывалась». При ненастроенном ключе объяснить, что анализ недоступен; шаги настройки относятся к локальному владельцу. В деталях дать переход к расходу этой задачи или показать краткую сводку рядом. При недоступности диагностики сохранить доступ к уже полученным моковым вариантам.
4. Для результата достаточно приватного чтения в пространстве `/portal/data/`. Разницу между публичным результатом и диагностикой не перекладывать на клиент C#. Не рендерить пользовательские цитаты как HTML. Использовать компоненты и оформление текущего кабинета. [HTML портала](../tripflow_api/portal_assets/index.html) · [Стили](../tripflow_api/portal_assets/portal.css)

## 8. Как проверить реализацию

### Автоматические проверки без оплаты

Подменить клиент провайдера на границе HTTP. Тестировать через обычный путь приёма задачи, а чистые правила разбора — отдельно. Сохранить существующий набор polling-тестов. Зафиксировать минимум следующие случаи.

| Случай | Наблюдаемый результат |
|---|---|
| Пустые или пробельные оба поля | Мок завершился, условий и внешних вызовов нет. При одном непустом уточнении оно разобрано. |
| Обязательное, мягкое, исключение и заметка о расходах | Условие в правильной категории, роль и цитата соответствуют вводу. Редкое условие не потерялось из-за отсутствия в словаре. |
| Парковка у аэропорта; исключён один музей; завтрак до 7:00 | Нет выдуманного требования парковки у отеля, общего запрета музеев или утраты времени. На живой модели проверить по отдельным эталонным текстам. |
| Два уточнения подряд | Последнее изменение применяется по своей теме; прежние незатронутые пожелания и другая категория сохраняются. Снятие обязательности не превращается в запрет. |
| Невалидный JSON или отсутствует цитата | Ограниченный повтор, корректное число попыток, сохранённый usage обеих при наличии. После исчерпания — видимый сбой анализа, мок завершается. |
| Таймаут, ответ без usage, отказ авторизации, ключ отсутствует | Различимые состояния. Таймаут без данных о токенах отличается от известного нулевого расхода, отсутствие ключа даёт ноль физических вызовов. |
| Параллельные задачи из конструктора и API; повтор POST/GET | Общий разбор одного аккаунта выполняется один раз. Две ссылки на него не удваивают токены. Чтение журнала и polling не запускают модель. Конфликт прежнего ID с новым телом сохраняется. |
| События за границей периода, второй аккаунт, одинаковый taskId | Корректная сводка за семь суток; чужие результаты и расходы недоступны. |
| Перезапуск, старые записи, неудавшаяся попытка | Завершённая задача читается как прежде, удачный разбор переиспользуется. Незавершённая работа получает конечный статус, ошибка не отравляет будущий кэш. |
| Мок без анализа, с анализом и при его ошибке | На одинаковом входе предметная часть ответов совпадает. Выбор отеля, места и запуск сметы работают. Бюджет не создаёт платного вызова. |

### Проверка смысла и первый замер на живой модели

Автотест с подставленным JSON доказывает работу harness. Для проверки смысла взять знакомые фразы из стенда и отдельную небольшую выборку новых перефразировок. До прогона записать ожидаемые область, роль, числа/единицы, исключения и эффект уточнения. Оценивать семантическое совпадение, а не дословное равенство `meaning`. Посчитать на фактически проверенном числе фраз пропущенные и придуманные обязательные условия, ошибочную область и потерянные уточнения. Записать число вызовов, длительность и usage. Не подгонять промпт по закрытой выборке и затем выдавать её за независимую. [Эксперимент DeepSeek](research/deepseek-web-trip/report.md) · [Отдельная выборка стенда](../experiments/deepseek-flash/holdout.json)

Живой запрос выполняется с ключом, который владелец намеренно положил в окружение этого сервиса. Не искать ключ в файлах экспериментов. Обычные тесты и старт контейнера не должны отправлять пробный платный запрос. Если ключ ещё не вставлен, проверить автономный сценарий и состояние «Ключ не настроен», оставить рабочий контейнер для ручной проверки. Не заявлять успешный вызов Flash по результатам подмены.

## 9. Локальное окружение и Docker

- В `API/.env.example` добавить пустую строку `DEEPSEEK_API_KEY=` с комментарием. Подготовить такую же строку в игнорируемом `API/.env`, только если переменной там ещё нет. Если файла нет, создать его из примера. Сохранить текущие значения остальных переменных и существующий ключ. Не печатать содержимое dotenv, значение ключа или полный результат развёрнутой конфигурации Compose.
- В секцию `environment` сервиса `api` передать `DEEPSEEK_API_KEY: ${DEEPSEEK_API_KEY:-}`. Существующий Compose передаёт только явно перечисленные переменные. Отсутствие ключа позволяет запустить сервис, кабинет и моки. Модель по умолчанию взять из проверенного стенда Flash; фактическое имя записывать в диагностике. Секрет доступен только серверному процессу.
- Локально использовать текущий Compose и именованный том. По умолчанию приложение берёт SQLite. При уже настроенной БД сохранить конфигурацию и данные; убедиться, что локальная проверка выполняется на предназначенной для неё базе. Не удалять том и не переинициализировать аккаунты. Проверить [Compose](../compose.yaml), [Dockerfile](../Dockerfile) и [список файлов сборки](../Dockerfile.dockerignore): если добавились модули в подпапке или новый статический ресурс, они должны попасть в образ. Dotenv и каталоги экспериментов в образ не копировать.
- Обновить инструкцию локального запуска в [README API](../README.md) и описание новых экранов в [гайде по порталу](PORTAL.md) по итогам фактической реализации. При первом старте с пустой БД владелец задаёт в `.env` также email и пароль администратора по существующей инструкции. При существующем аккаунте использовать прежний вход.

**Команды из каталога `API` после изменения кода**:

```powershell
docker compose up -d --build
docker compose ps
```

**После ввода или смены только ключа**:

```powershell
docker compose up -d --force-recreate api
```

Пересоздание контейнера применит окружение и сохранит именованный том. Обычный restart оставляет старое окружение. Для изменения одного ключа пересборка образа не требуется. По умолчанию проверять `http://127.0.0.1:8000/health` и `http://127.0.0.1:8000/portal`; если выставлен `TRIPFLOW_API_PORT`, подставить его.

## 10. Сценарий ручной приёмки автором

1. Вставить ключ в подготовленную строку `API/.env`, применить окружение, открыть портал под своим одобренным аккаунтом. Запомнить исходные показатели в разделе «Разбор пожеланий».
2. В конструкторе выбрать Москву и ввести «Обязательно нужен завтрак до 7 утра. Желательно рядом с метро. Хотим посетить музеи. На такси ездить не планируем». Нажать подбор. Проверить ожидаемые смысл, роли и цитаты. В обеих категориях доступны тестовые варианты.
3. Открыть собственную активность. На новом для этого аккаунта тексте без сбоев ожидается один физический вызов общего разбора для двух задач. Сверить входные и выходные токены, время, модель и тип использования по задачам. При повторной попытке исправления проверить обе строки расходов. Повторное открытие вкладки не увеличивает показатели.
4. Для отелей ввести «Завтрак уже необязателен. Нужен заезд после полуночи» и нажать «Ещё». Во вкладке видеть новое требование, снятую обязательность и сохранённое метро; пожелания к музеям остаются прежними. Новый вызов относится к уточнению. Повторить новый поиск с тем же текстом и уточнением — проверить повторное использование.
5. Выбрать тестовый отель и место, запустить смету. Убедиться, что ответ содержит прежние четыре статьи, а число вызовов Flash от этого действия не увеличилось.
6. Через Swagger с ключом **TripFlow** своего аккаунта отправить рекомендацию по действующей схеме с новым `taskId`. Дочитать результат через polling. Найти эту задачу и её диагностику в том же кабинете. Ключ DeepSeek в Swagger не вводится.
7. Проверить пустую строку, состояние без ключа и доступ обычного разработчика. Поведение при 401, 429 и таймауте достаточно воспроизвести управляемой подменой клиента. После проверки оставить локальный сервис в состоянии, пригодном для демонстрации.

## 11. Что передать по завершении

Перед сдачей заново собрать локальный образ, проверить здоровье сервиса, обе страницы портала и регрессионные тесты из README. По возможности пройти ручной сценарий в интерфейсе обычного разработчика. В итоговом сообщении дать автору адрес портала, место для ключа, команду применения окружения, путь до вкладки и метрик. Кратко перечислить, какие тесты и какой реальный запрос выполнены, что показали замеры и какие проверки ещё требуют ключа или входа владельца. Результаты живого прогона и прогона с подменой отмечать отдельно. Оставить изменения для просмотра автором без коммита.
