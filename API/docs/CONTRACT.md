# Контракт C# backend ↔ Python API

Контракт описывает эту версию FastAPI. Подбор и смета выполняются в фоне, а статус читается отдельным запросом. Публичный Swagger показывает схему релиза, который сейчас работает на Render. [Контракт опубликованной версии](https://tripflow-api-x1p5.onrender.com/openapi.json) · [Архитектура](ARCHITECTURE.md) · [Схемы и примеры JSON](BACKEND-HANDOFF.md)

## Маршруты и авторизация

| Маршрут | Направление | Назначение |
|---|---|---|
| `POST /v1/recommendations` | C# → Python | Первичный подбор и догенерация. |
| `POST /v1/budget` | C# → Python | Расчёт дополнительных расходов по текущему выбору. |
| `GET /v1/tasks/{taskId}` | C# → Python | Статус и сохранённый результат своей задачи. |

Все три маршрута используют один заголовок `X-API-Key` из кабинета. Оба POST принимают JSON и возвращают `202 Accepted`, например `{"taskId":"rec-001","status":"accepted"}`. Заголовок `Location` указывает относительный путь для опроса, `Retry-After` задаёт рекомендуемую задержку в секундах.

GET возвращает `200`. Пока задача выполняется, тело имеет вид `{"taskId":"rec-001","status":"pending","result":null}`. После завершения `status` равен `completed`, а `result` содержит объект `recommendations.finished` или `budget.finished` по схемам ниже. `completed` означает готовность к чтению, включая результат с прикладной ошибкой. Повторный GET возвращает тот же итог. Чужой или неизвестный ID даёт `404`, неверный или отозванный ключ — `401`.

Для первичной генерации C# отправляет две независимые задачи с разными ID, по одной на `hotels` и `attractions`. Смета получает третий ID после выбора. Сохраняйте ID до POST. При потере ответа повторяйте тот же POST. Тот же ID с изменённым содержимым или операцией даёт `409`. При временном сетевом сбое продолжайте GET с увеличенной паузой. Сохраняйте незавершённые ID для возобновления после перезапуска C#. Локальному backend достаточно исходящего HTTPS к Python.

Ключ определяет аккаунт. ID задачи уникален в пределах аккаунта. Заголовок `Location` содержит относительный путь, а ответ GET задачи содержит `Cache-Control: no-store`. `/portal` выдаёт и отзывает ключи, `/docs` показывает маршруты задач, `/openapi.json` отдаёт схему, `/health` проверяет доступность БД. [Гайд по кабинету на Render](PORTAL.md)

## HTTP-ошибки

| HTTP | `error.code` | Когда возникает |
|---|---|---|
| `401` | `INVALID_API_KEY` | Ключ отсутствует, неверен или отозван. |
| `404` | `TASK_NOT_FOUND` | GET запрашивает неизвестную задачу либо задачу другого аккаунта. |
| `409` | `TASK_ID_CONFLICT` | POST повторяет ID с изменённым телом или для другой операции. |
| `422` | `VALIDATION_ERROR` | Тело нарушает схему или содержит неизвестный `trip.destinationId`. |

Ответ ошибки содержит `taskId`, когда его удалось определить, либо `null`, а также `error.code` и `error.message`. Ошибки валидации содержат `error.fields`. Ключ — путь поля, например `trip.endDate`, значение — список сообщений. Для ошибки фоновой задачи GET возвращает `200` со статусом `completed` и причиной внутри `result`.

Перед сравнением тел Python приводит `excludedObjectIds: null` к `[]`, сортирует исключения и приводит пустой или пробельный текст в nullable-полях к `null`. Для новой формы запроса после смены контракта используйте новый ID. Ранее созданную задачу можно прочитать по старому ID.

## Общие типы и направления

- Формат обмена — JSON с именами полей в `camelCase`. Обязательные ключи присутствуют всегда. В nullable-поле неизвестное значение передаётся как `null`. Пустой список передаётся как `[]`. Допустимость пропуска поля определяется схемой. Python приводит пустые и пробельные входные nullable-строки к `null`.
- `trip.budgetRub` — целевой бюджет в целых рублях на всю группу и поездку, включая резерв. Положительные дробные суммы после приведения к рублям округляются вверх. Нулевая цена объекта означает подтверждённую бесплатность.
- Даты задаются в формате `YYYY-MM-DD`. Ночи проживания — разница дат. Питание и прочие ежедневные расходы учитывают обе даты включительно. Например, с 10 по 15 июня — пять ночей и шесть дней.
- React получает направления из C#. В рабочей схеме C# передаёт в Python `trip.destinationId` из общего справочника. Справочник содержит стабильный ID, город, страну, координаты и регион при наличии. `regionName` может быть `null`. При добавлении направления проверяется доступность реальных объектов и пригодных денежных ориентиров. [Справочник](../../shared/data/destinations.json) · [TripContext и общие типы](BACKEND-HANDOFF.md#общие-правила-типов)

## Подбор и догенерация

C# передаёт `taskId`, `trip` и поля верхнего уровня `targets`, `count`, `maxTotalRub`, `refinement` и `excludedObjectIds`. В `targets` передаётся одна строка, `hotels` или `attractions`. `count` задаёт максимальное число вариантов. Если отдельного лимита пока нет, передаёт `maxTotalRub: null`. Для отеля лимит относится ко всей группе и всем ночам, для места — к одному посещению всей группой.

Догенерация использует тот же маршрут с новым `taskId` и одним типом. C# передаёт актуальное уточнение `refinement` и `excludedObjectIds`, включая уже полученные и отклонённые варианты. Оба поля обязательны. `refinement: null` отключает уточнение. `excludedObjectIds: null` и `[]` означают поиск без исключений. В версии с AI уточнение должно влиять на подбор этой категории. Текущий мок принимает поля `refinement` и `trip.preferences`, а порядок выдачи задаёт тестовый каталог. При замене C# освобождает стоимость заменяемого варианта при расчёте лимита. Сохранённый выбор меняется после действия пользователя. [Схема запроса и примеры](BACKEND-HANDOFF.md#1-запрос-рекомендаций)

Python сохраняет `recommendations.finished` после завершения задачи. `results` содержит один ключ, соответствующий `targets`. Каждый результат включает статус, список `items` в порядке подбора, `hasMore` и ошибку при необходимости. Список ограничен `count`. Пустая законченная выдача получает `succeeded`, прерванная выдача с пригодными вариантами — `partial`, сбой без пригодных вариантов — `failed`.

`hasMore: true` означает, что найден ещё один подходящий вариант сверх пакета, `false` — что поиск исчерпан, `null` — что наличие дополнительных вариантов неизвестно. При `null` пользователь может запустить повторный поиск с новым `taskId`. Сбой подбора влияет только на задачу этой категории. Текущий мок формирует `succeeded` при завершении подбора и `failed` при сбое. `partial` предусмотрен для будущего поиска по источникам. [Схема результата и пример пакета](BACKEND-HANDOFF.md#2-итоговый-результат-подбора)

### Цены кандидатов

- `price` отеля — целая сумма в рублях за всё проживание группы или `null`, если обоснованная полная стоимость неизвестна. Итоговая сумма по отелю не умножается повторно на ночи или путешественников.
- Для достопримечательности `price` содержит сумму, единицу посещения и тип основания `source` или `estimate`. `price: null` обозначает неизвестную цену. У такого кандидата соответствие лимиту не подтверждено.
- Мок использует вымышленные объекты Москвы. Если задан лимит, вариант с неизвестной ценой исключается. В версии с внешними источниками рекомендация должна опираться на реальный объект и проверяемые данные. [Типы цен](BACKEND-HANDOFF.md#цена-отеля) · [Источники](EXTERNAL_APIS.md)

## Смета после выбора

Для `POST /v1/budget` C# отправляет новый `taskId`, актуальную поездку, выбранный отель с ID и ценой, выбранные места и имеющиеся цены. [Схема запроса сметы](BACKEND-HANDOFF.md#3-запрос-бюджета-после-выбора)

В `budget.finished` Python возвращает `expenses` с оценками питания, городского транспорта, прочих расходов и резерва за всю поездку для всей группы. Каждая статья — неотрицательное целое число. Если обязательную оценку получить невозможно, Python возвращает `failed` с `expenses: null` и ошибкой. Мок берёт `1 400 × число дней × travelers` на питание, `400 × число дней × travelers` на городской транспорт, `0` на прочие расходы и `10% от trip.budgetRub` с округлением резерва вверх. Выбранные объекты передаются для контекста. Текущая формула использует даты, группу и целевой бюджет.

C# складывает расходы с ценой выбранного проживания и посещений, рассчитывает итог, сумму на участника и остаток либо превышение бюджета. Цена билета на человека умножается на число путешественников, групповая цена учитывается один раз за посещение. При неизвестной цене часть расходов остаётся неучтённой. C# показывает известную сумму и отмечает смету как неполную. ## Применение результата в карточке

Это последовательность для подключения C# и React к polling Python. Состояние реализации C# описано отдельно. [Интеграция C#](../../Backend/README.md#связь-с-python)

1. До вызова Python C# связывает новый `taskId` с версией карточки и снимком входных данных. Python после принятия задачи возвращает `202 Accepted` со статусом `accepted` и тем же `taskId`. При явном отклонении запроса до приёма Python возвращает HTTP-ошибку с `ErrorResponse`.
2. React опрашивает `GET {card}` у C#, пока нужные статусы имеют значение `pending` и экран открыт. C# читает сохранённое состояние карточки. Точный интервал опроса предстоит согласовать.
3. Python сохраняет итог до выдачи по GET. Незавершённые задачи возобновляются при запуске процесса с той же базой.
4. C# сверяет версию карточки, сохраняет итог и обновляет статусы в одной транзакции. Устаревшие задачи не меняют текущую версию.
5. Если срок ожидания истёк, C# переводит попытку в `failed`, чтобы React мог завершить polling. Новая попытка или новый набор входных данных получает новый `taskId`.
