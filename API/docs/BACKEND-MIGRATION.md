# План подключения C# к мировому подбору TripFlow

Адресат — разработчик и агент, работающие в `Backend/`. Состояние на 22 ноября 2026 года: клиент C# ожидает callback, опубликованный Python обслуживает задачи через polling на моке Москвы. Ниже описаны два самостоятельных этапа. Первый можно подключать к существующему релизу. Для второго потребуется согласованный выпуск Python, C# и конструктора портала. [Работающие схемы и ошибки](BACKEND-HANDOFF.md) · [Архитектура реального подбора](ARCHITECTURE.md)

## 1. Перевести транспорт на polling

- В [PythonIntegration.cs](../../Backend/PythonIntegration.cs) заменить зависимость от входящего callback на исходящий опрос. Для клиента нужны `BaseUrl` и `ApiKey`. Отвязать готовность от `CallbackKey`, обновить регистрацию в [Program.cs](../../Backend/Program.cs) и конфигурацию. После переключения убрать старый приёмник `/internal/tripflow/events`. Использовать имеющуюся логику применения результата к версии карточки.
- В [CardPlanning.cs](../../Backend/CardPlanning.cs) перед отправкой сохранить ID, операцию, категорию, версию карточки и снимок входа. Создать две независимые задачи `POST /v1/recommendations` с разными ID, затем отдельную `POST /v1/budget` после выбора. Поля подбора верхнего уровня: одна строка `targets`, `count`, `maxTotalRub`, `refinement`, `excludedObjectIds`. Последние два ключа присутствуют всегда. При первом запросе допустимы `null` и пустой список исключений.
- Получив `202`, читать относительный `Location` на том же сервере с тем же `X-API-Key`. Пока статус `pending`, учитывать `Retry-After`. При потере ответа на POST повторять тот же ID и тело. При временном сбое GET продолжать опрос до дедлайна, возобновлять сохранённые задачи после перезапуска. Изменённое тело требует нового ID. Обрабатывать немедленные ошибки API отдельно от ошибки внутри завершённой задачи.
- При `completed` сохранить результат и обновить состояние карточки один раз, только для соответствующей версии и актуальной попытки этой категории. Две параллельные категории одной версии завершаются независимо. Смена текущего выбора делает прежнюю смету устаревшей. React опрашивает карточку у C# и может закрыть экран, пока backend продолжает обработку.

## 2. Переключить данные на мировой подбор

| Поле | Мок на Render | Следующий релиз |
|---|---|---|
| Направление в подборе и смете | `trip.destinationId` из общего справочника | `trip.destination` с четырьмя обязательными полями: `city` (непустая строка), `countryCode` (двухбуквенный код страны), `latitude` и `longitude` (числа от −90 до 90 и от −180 до 180 соответственно). |
| `price` отеля | Сумма за всю группу и все ночи либо `null` | Обязательная целая сумма в рублях в выдаче и в выбранном отеле. При отсутствии выбора `selectedHotel: null`. |
| `price` места | Объект с суммой, единицей и основанием либо `null` | Целые рубли за одно посещение всей группой, `0` при подтверждённой бесплатности, `null` при неизвестной цене. Одинаковое представление в выдаче и в `selectedAttractions`. |
| Пояснение подбора | Схема допускает `recommendationReason` | Клиенту достаточно итоговых объектов; генерация и отображение текста причины не требуются. |

**Выбор города.** Заменить зависимость маршрута подсказок, валидации карточки и конструктора `TripDetails` от статического списка Москвы. Точки входа — [Program.cs](../../Backend/Program.cs), [Dashboards.cs](../../Backend/Dashboards.cs) и [Storage.cs](../../Backend/Storage.cs). Предлагаемый источник — Geoapify Autocomplete: C# отправляет введённый текст с `type=city`, `lang=ru`, берёт `city`, `country_code`, `lat`, `lon` и передаёт фронту подпись с регионом при наличии. Ключ поставщика остаётся на стороне C#. Пользователь выбирает конкретную строку. C# проверяет четыре поля, сохраняет выбранное направление и может хранить свой ID или SQL-кэш для подсказок. В Python отправляются только четыре поля объекта. Выбор поставщика и хранилища остаётся за backend. [Geoapify Autocomplete](https://apidocs.geoapify.com/docs/geocoding/address-autocomplete/)

Пример тела **следующего релиза** для догенерации отелей:

```json
{
  "taskId": "1f3741de-eca1-459c-8ac6-94ff5704f6df",
  "trip": {
    "destination": {"city": "Киото", "countryCode": "JP", "latitude": 35.01, "longitude": 135.77},
    "startDate": "2027-05-15",
    "endDate": "2027-05-17",
    "travelers": 3,
    "budgetRub": 100000,
    "preferences": "Отель с завтраком, рядом с вокзалом"
  },
  "targets": "hotels",
  "count": 2,
  "maxTotalRub": 48000,
  "refinement": "Завтрак необязателен.\nНужна стойка регистрации после полуночи.",
  "excludedObjectIds": ["hotel-previous-1", "hotel-previous-2"]
}
```

**Повторный подбор.** C# обычно просит два-три объекта за раз. Сохраняет по карточке и категории все показанные `objectId` Python, включая пригодные элементы из `partial`. При каждом «ещё» или повторе завершившегося с ошибкой поиска создаёт новый ID задачи и передаёт эти исключения даже при новых условиях. Локальный ID строки списка не заменяет `objectId`. Пакет добавляется к сохранённым вариантам, выбор меняет пользователь. C# накапливает уточнения в порядке ввода и передаёт их одной строкой. Без нового текста отправляет прежний `refinement`. Последнее уточнение приоритетно только в затронутой части.

**Стоимость и представление карточки.** В [PlanningModels.cs](../../Backend/PlanningModels.cs) и разборе событий обновить типы, расчёт, проекцию для React и сравнение направлений при изменении версии. `maxTotalRub` — единственный жёсткий потолок на один вариант за всю группу. `null` снимает отдельный лимит. При замене высвобождается стоимость заменяемого выбора. Отель и каждое посещение из новой выдачи добавляются к четырём статьям Python по одному разу. Например, при отеле за 48 000 ₽, месте за 1 800 ₽ для троих и дополнительных расходах 12 000 ₽ учтено 61 800 ₽. Если также выбрано место с `price: null`, сумма остаётся 61 800 ₽ и выводится признак неполной сметы. Фронт может сообщить, что билет стоит проверить самостоятельно. Групповой билет с известной ценой никогда не умножается повторно на число людей.

**Состояние для React.** При `succeeded` показать полученные объекты. Если `hasMore: false`, предложить изменить условия. При `true` или `null` разрешить «ещё». `partial` и `failed` дают одно действие «Попробовать ещё раз». При `partial` сохранить полученные объекты. Успешный полный пакет с `hasMore: null` не вызывает сообщения об ошибке.

## Переход и проверка готовности

1. Реализовать и проверить polling на форматах действующего релиза. Сверить поддерживаемую схему перед переключением сериализации. Сегодняшний валидатор Python отклонит `trip.destination`.
2. Для следующего релиза согласованно обновить Python DTO, конструктор портала, C# DTO и React-представление. Учесть сохранённые карточки и незавершённые задачи в [хранилище](../../Backend/Storage.cs). Старый ID Москвы можно разрешить по прежнему справочнику. При прежнем объекте цены применять прежнюю единицу к сохранённому составу группы; у нового числа единица уже групповая. Старый результат с неизвестной ценой проживания читается как исторический. Снимок ранее принятой задачи сохраняет исходный формат для повтора и чтения.
3. Проверить сквозные примеры: город вне России с координатами; две категории одной версии готовы в разное время; два раунда уточнений исключают все ранее показанные ID; повтор POST после потери ответа и повтор GET не дублируют элементы; опоздавшая задача не меняет новую версию; `partial` сохраняет варианты; известная, бесплатная и неизвестная цены дают корректный итог и признак полноты. Обновить справку запуска и Swagger по фактически выпущенному клиенту.
