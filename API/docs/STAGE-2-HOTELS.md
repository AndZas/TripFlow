# Stage 2. Реальный подбор отелей для произвольного города

**Задание для исполнителя.** Реализовать гостиничный подбор в существующем TripFlow API, собрать и проверить его в локальном Docker. Пользователь выбирает город через Geoapify, задаёт поездку и получает пригодные для выбора отели. У каждого отеля есть собственный стабильный ID, проверяемый источник, соответствие обязательным условиям и обоснованная групповая цена в рублях. Повторная задача использует каталог и ищет недостающие сведения. Конструктор портала и публичный API обращаются к одному обработчику.

**Что согласовано с автором.** Реальными становятся только отели. Конструктор продолжает отправлять отдельные задачи отелей и мест, затем смету после выбора. Для любого выбранного города места берутся из нынешнего московского мока, смета — из нынешней формулы. Гостиничная задача при недоступном поиске использует подтверждённые данные каталога и честно сообщает исход. Область реализации — `API/`; результат сдаётся локально, без коммита и деплоя на Render. Клиенты C# и React основного приложения остаются в зоне работы других участников. [Инструкции для API](../AGENTS.md) · [Согласованная архитектура](ARCHITECTURE.md) · [План миграции клиента](BACKEND-MIGRATION.md)

## 2. Вход, выбор города и переход с московского мока

**Новый запрос.** Сохраняются маршруты `POST /v1/recommendations`, `POST /v1/budget`, `GET /v1/tasks/{taskId}`, заголовок `X-API-Key`, относительный `Location` и `Retry-After`. Пример первого подбора:

```json
{
  "taskId": "kyoto-hotels-001",
  "trip": {
    "destination": {"city": "Киото", "countryCode": "JP", "latitude": 35.01, "longitude": 135.77},
    "startDate": "2027-05-15",
    "endDate": "2027-05-17",
    "travelers": 3,
    "budgetRub": 100000,
    "preferences": "Обязательно заселение после полуночи. Желательно возле вокзала."
  },
  "targets": "hotels",
  "count": 2,
  "maxTotalRub": 48000,
  "refinement": null,
  "excludedObjectIds": []
}
```

- Для `trip.destination` обязательны `city` (непустая string), `countryCode` (string, двухбуквенный код страны), `latitude` и `longitude` (конечные number, соответственно от −90 до 90 и от −180 до 180). Удалить крайние пробелы в названии, нормализовать код в верхний регистр. Обрабатывать нулевые координаты как числа. Отклонить обе формы направления одновременно, отсутствие обеих, неполный объект, неверный тип и координаты вне диапазона по принятой схеме `422`.
- Для прежнего `trip.destinationId` разрешать известный ID через имеющийся [справочник](../../shared/data/destinations.json). Удобно разделить две допустимые формы типизированного входа и привести их к одному внутреннему направлению **после** определения идентичности запроса. Публичный клиент, который передал валидные четыре поля, не должен зависеть от доступности Geoapify в момент POST.
- В конструкторе заменить выбор единственной Москвы на поле подсказок. Приватный маршрут кабинета, например `GET /portal/data/builder/cities?q=...`, вызывает Geoapify Autocomplete на сервере с выборкой городов и русским языком. Вариант ответа кабинету — подпись с городом, регионом и страной плюс четыре поля направления. Использовать координаты выбранной строки. После изменения текста сбрасывать прежний выбор. Показывать разные одноимённые города отдельными строками. Задержка ввода порядка 300 мс, ограничение результата и игнорирование устаревшего ответа уменьшают лишние запросы. Для пустого запроса, отсутствующего ключа и недоступного геокодера нужны различимые состояния.
- Портальный префикс и способ авторизации уже различаются у кабинета и публичного API. После выбора города тела задач и правила валидации должны совпадать. Не добавлять специальный флаг «реальные отели» в конструктор. Независимая задача `attractions` и `POST /v1/budget` принимают то же направление. Смена города очищает выбранные варианты в конструкторе.
- Для новых реальных отелей `price` — целая сумма за проживание всей группы. В новом формате сметы выбранный отель передаётся как `{objectId, price}` с известной групповой ценой либо `selectedHotel: null`. Совместимость старого входа с историческим `price: null` сохранить. Перевод билетов на единую групповую цену относится к этапу реальных мест: сейчас у `selectedAttractions` и выдачи мест остаётся действующий объект цены либо `null`. [Контракт мока](CONTRACT.md) · [Поля и примеры](BACKEND-HANDOFF.md)

**Сохранённые задачи.** В текущем хранилище уникальны `(client_id, task_id)`. Повтор того же POST должен найти исходный снимок, изменённое тело — дать `409`. Добавление `destination: null` во все старые снимки при сериализации может сломать сравнение. Покрыть это тестом с записью до обновления. Различать версию исполнения по сохранённому при приёме признаку, например номеру версии обработчика с миграционным значением для прежних строк. Старую принятую, но незавершённую задачу завершать по прежним правилам, включая исторический многокатегорийный ввод. Новый POST с новым ID запускает реальный подбор отелей и для старого московского ID. Чтение ранее завершённой задачи не запускает поиск, перерасчёт или списание токенов.

## 3. Один проход гостиничного обработчика

1. **Посчитать ночи и получить эффективные условия.** При нуле ночей — успешный пустой пакет без платных вызовов для гостиничной задачи. При непустых пожеланиях использовать сохранённый успешный разбор Stage 1. Если пришло уточнение, брать эффективный список из завершённого этапа уточнения. Пустой список после снятия всех условий допустим. Если непустой текст или уточнение не удалось разобрать, завершить поиск с ошибкой: переход к старой базе или пустому списку может потерять обязательное требование. При пустом тексте и отсутствии уточнения поиск допустим без вызова Flash для интерпретации.
2. **Получить кандидатов из каталога.** Ограничить по выбранному городу и категории, исключить все `excludedObjectIds`, выбрать применимые ставки и признаки. Каждый кандидат имеет опубликованную идентичность. Если набирается полный пакет с достаточными доказательствами, вернуть его из каталога. Менять ID из-за новых дат, языка запроса, другой ссылки или нового тарифа нельзя.
3. **Определить пробел.** Если кандидатов мало, построить запросы для обнаружения гостиниц. Если отели уже известны, сформулировать запросы про конкретный пробел, например позднее заселение в филиале у вокзала или тариф на одноместное размещение. Flash получает город, нужные условия, необходимую информацию о размещении и краткое задание на поисковые фразы. Гостиничной задаче не нужны пожелания о музеях, генерация сметы или второй общий разбор текста.
4. **Search → Fetch → извлечение.** Python запускает запросы, удаляет повторные и трекинговые ссылки, сохраняя значимые параметры объекта или тарифа. Для важных сведений получать страницу объекта или иной источник с достаточным контекстом. Удерживать заголовки таблиц, подписи тарифов и соседние строки, чтобы единицу цены и условия можно было проверить. Модели передавать ограниченный набор пронумерованных источников. Предпочитать официальную страницу гостиницы и явно относящиеся к этому объекту условия. Поисковый сниппет со списком разных отелей годится для обнаружения, но обычно недостаточен для привязки цены.
5. **Проверить структурированный ответ.** Практичная форма результата извлечения — локальный ID источника, значение, исходная единица, условия применения и дословная выдержка. Python проверяет присутствие ID в переданном наборе, цитату в тексте страницы, числовые поля и соответствие конкретному отелю или тарифу. Ссылка выбирается из известных Python источников. Отсутствующие координаты, звёзды и изображения допускают `null`. Текст страницы используется как данные. Параметрами инструментов, разрешёнными запросами и лимитами управляет Python.
6. **Проверить требования у лидеров.** Хранить по каждому существенному условию ответ «подтверждено / опровергнуто / неизвестно» и основание. Для `required` нужна подтверждённая применимость, для `excluded` проверяется именно запрещённое свойство. Не считать неизвестность доказательством отсутствия запрещённого признака. Для `preferred` неизвестность снижает приоритет. Нейтральная заметка, отменённое пожелание и неоднозначное предположение не должны самопроизвольно стать жёстким фильтром.
7. **Посчитать цену, упорядочить и записать.** Проверить цену каждого кандидата по правилам ниже, применить `maxTotalRub`. При прочих равных предпочитать лучшее подтверждение и соответствие пожеланиям; порядок равнозначных кандидатов сделать устойчивым, например по `objectId`. При использовании Flash для смыслового ранжирования разрешать только ID прошедших кандидатов, повторно проверить отсутствие дублей и исключений. Записать итог и вернуть через обычный polling.

**Проверочный пример доказательства.** При обязательном заезде после полуночи выдержка «стойка регистрации работает с 07:00 до 23:00» не допускает отель без других сведений о позднем заселении. Фраза «бесплатный завтрак» не доказывает завтрак до 07:00. Если ранний завтрак предоставляется только по субботам или относится к другому тарифу, проверять реальные дни и выбранное предложение. При нехватке доказательства обратиться к другому источнику или перейти к следующему кандидату.

## 4. Каталог и сохранение прогресса

Постоянный каталог пополняется по запросам. Локально он работает в том же SQLite-томе, на PostgreSQL использует существующий слой доступа. Открытые сведения об отелях можно переиспользовать между поисками. Текст конкретной поездки, исключения, запрос, результаты, диагностические детали и затраты принадлежат аккаунту. Не записывать в общедоступные свойства гостиницы фразу пользователя или личную интерпретацию его поездки. [Слой БД](../tripflow_api/database.py)

| Что хранить | Минимально полезное содержание |
|---|---|
| Направление и объект | Внутренний ID направления, страна, город, географическая привязка; постоянный ID гостиницы, варианты имени, адрес, координаты при наличии. Ключ из одного названия не различает одноимённые города и филиалы. |
| Страницы и факты | Связь гостиницы с канонической страницей, выдержка, нормализованный факт, значение и ограничения: тариф, тип размещения, часы, день недели, необходимость согласования и доплата. Кэшировать только подтверждённые сведения с применимым контекстом. |
| Ставки | Сумма или диапазон в исходной валюте, единица расчёта, вместимость, период действия, тариф, привязанный источник. Для оценки по аналогам — ссылки на использованные сопоставимые ставки. |
| Исполнение конкретной задачи | Аккаунт и задача, версия, выполненные платные шаги, проверенные ID, привязки к фактам, причина пропуска, исходные ставки, курс, арифметика и снимок итоговой цены. Этого достаточно для повторного GET и объяснения полученной суммы. |

**Как не задвоить гостиницу.** Сначала сверить известную страницу конкретного объекта. Для новой ссылки проверить город и тип, варианты названия, адрес и координаты. Один сайт гостиничной сети, одно имя или близкие координаты недостаточны. При уверенном совпадении добавить алиас к существующему `objectId`. При двух возможных филиалах уточнить адрес; если не удалось, пропустить. Сетевую работу выполнять до короткой транзакции. В транзакции повторно сверить совпадение и присвоить ID, сериализовав финальное решение хотя бы для одного города и категории. После привязки нового URL снова проверить исключения. Протестировать два одновременных запроса в пустой город.

**Как переиспользовать данные.** Другие даты или размер группы могут изменить цену при том же ID. Для каждого запроса вычислять сумму заново из применимой исходной ставки. Завтрак в тарифе A не переносится в B. При совпадающем адресе и новом пожелании достаточно проверить только новое условие. Для курсовой версии архитектура не требует истории версий и TTL у всех фактов; период действия самого тарифа и применимость к поездке всё равно обязательны, когда они указаны источником.

## 5. Цена гостиницы и выбор ставки

**Расчётный договор:** один путешественник занимает один отдельный номер. Цена в API — целые рубли за всех людей и все ночи. Текущий мок считает двухместное размещение по другой формуле. Не использовать его вычисление комнат в новой ветке. Изменение цены объекта не пересчитывает ранее сохранённый результат задачи.

| Исходные данные | Что считать |
|---|---|
| 8 000 ₽ за отдельный номер за ночь, три человека, две ночи | `8000 × 3 × 2 = 48000`. При `maxTotalRub=48000` кандидат проходит, при 47999 — исключается. |
| 16 000 ₽ за один отдельный номер на весь нужный двухночный период | `16000 × 3 = 48000`. Проверить продолжительность и область ставки до расчёта. |
| Цена всего размещения уже соответствует датам, числу отдельных номеров и группе | Взять групповую сумму один раз. Слова «на троих» сами по себе не подтверждают три отдельных номера. |
| Ставка в другой валюте | Использовать Decimal. Для курса с номиналом 100 единиц сначала получить RUB за одну единицу. Округлить вверх только конечную положительную сумму в рублях. Записать валюту, источник курса, дату и номинал. При недоступности пригодного курса попробовать другой обоснованный вариант, а не подставлять курс 1. |
| «От …» или опубликованный диапазон | Допустим ориентир по нижней применимой ставке с сохранением того, что это «от» либо диапазон. Проверить размещение, условия тарифа и связь с отелем. Не объявлять эту сумму подтверждением доступности номеров на даты. |
| Нет тарифа данного отеля | Сначала точечный поиск. Затем допустима оценка по реальным гостиницам того же района и сопоставимого класса. Если сопоставимость или единицы не установлены, кандидат не попадает в выдачу. |

Для первой реализации курса подойдёт проверенный в стенде подход с XML Банка России: учитывать `Nominal`, `Value`, валюту и дату документа, RUB обрабатывать локально. Если используется иной источник, зафиксировать тот же набор данных и контрольный пример. Для первого варианта оценки по аналогам рекомендуемое воспроизводимое правило — минимум две **разные** сопоставимые гостиницы, сопоставимые условия размещения, ставки приведены к одному номеру за ночь; брать медиану нормализованных ориентиров. Хранить основание сопоставления и отмечать «оценка по аналогам» в диагностике. Это инженерный стартовый выбор, подлежащий проверке на примерах. Целевой бюджет и потолок не должны участвовать в выводе исходной рыночной ставки. `maxTotalRub: null` снимает отдельный потолок на отель.

## 6. Результат, ошибки и платные операции

Сохранить внешнюю оболочку `pending/completed` и событие `recommendations.finished` с ключом `results.hotels`. В реальной гостиничной выдаче обязательны `objectId`, `name`, целочисленная групповая `price` и ссылка `sourceUrl` на объект. Поля `stars` (1–5 либо `null`), `address`, `coordinates` и `imageUrl` сериализовать по handoff с явным `null` для неизвестного значения. Перед сохранением валидировать сформированный пакет отдельной моделью результата: текущий `TaskStatus.result` объявлен как `dict`, одной его проверки недостаточно. Цитаты, попытки и трассировку оставлять в личном кабинете.

| Как закончилась гостиничная задача | Результат категории |
|---|---|
| Собран пакет или штатно закончился осмысленный поиск, включая ноль совпадений | `succeeded` с найденными элементами. |
| Поиск прервался из-за провайдера, времени или лимита, но часть гостиниц уже проверена | `partial`, сохранить пригодные `items`, сообщить причину и дать повтор. |
| Поиск прервался до первого пригодного результата | `failed`, пустые `items`, понятная прикладная ошибка. Отдельная задача мест может успешно завершиться. |

`hasMore: true` требует ещё одного **проверенного** подходящего кандидата сверх выданных. `false` означает исчерпание поиска по условиям, `null` — запас неизвестен. Заполненный пакет без проверки следующего кандидата — `succeeded` с `null`. Ни пустая БД, ни временный сбой сайта, ни расход лимита сами по себе не доказывают исчерпание. При недоступных внешних инструментах полный пригодный пакет из каталога может завершиться успехом. Если каталога не хватило, применять правила прерванного поиска. Подстановку мокового отеля исключить.

**Лимиты и восстановление.** Ввести отдельно учитываемые пределы числа Search, Fetch, Flash, токенов, одновременных задач и полного времени задачи, включая Stage 1. Практический старт для настройки — взять за верхний ориентир стенд (7 Search, 5 Fetch, 6 Flash на его совмещённый поиск) и измерить затраты для одной категории, не перенося эти числа как продуктовую квоту. Конкретные настройки, единицу учёта попытки и фактическое время описать в README. Согласовать дедлайн задачи с таймаутом polling конструктора. Не выполнять блокирующий сетевой вызов в цикле событий или внутри транзакции. Временный сбой допускает ограниченный повтор с паузой в пределах общего бюджета.

Для платной работы предусмотреть захват задачи в БД на ограниченное время. Фиксировать завершённые дорогие шаги и физические попытки. После перезапуска подхватывать незавершённую задачу с подтверждённой точки, не записывать запоздалый результат поверх уже завершённого. Сбой после ответа поставщика до записи в БД оставляет неопределённость по расходу; в диагностике показывать неизвестное значение. Повтор POST, GET, открытие вкладки и просмотр журнала не должны сами инициировать новую платную попытку.

## 7. Что показать в портале и метриках

- **Пользователю.** Реальный отель, название, доступные атрибуты, ссылка и подпись «Ориентир за всю группу и все ночи». Выбор работает с `objectId`. Для текущих мест и четырёх статей сметы оставить явную подпись «тестовые данные», в том числе у зарубежного направления. Обновить старую общую подпись о полностью тестовой выдаче.
- **Для демонстрации.** В деталях своего гостиничного результата показывать источник, ставку и единицу, число номеров и ночей, применённый курс, тип оценки и групповую сумму. Для существенного условия — слова путешественника, проверяемая выдержка со страницы и результат проверки. Это позволяет разобрать, почему «завтрак включён» не подтверждает раннее начало завтрака.
- **Для разработчика.** По задаче и в личном журнале различать время до готового пакета, обращения к каталогу, число взятых оттуда пригодных отелей, физические Search/Fetch/Flash и повторы, известные входные/выходные токены. Токены Stage 1 при переиспользовании общего разбора не задваивать. Денежную сумму показывать только при известных тарифах и достаточном usage. Новый раздел диагностики должен быть доступен владельцу задачи, включая созданную через публичный API. [Портал и действующие метрики](PORTAL.md)
- **Для «Ещё».** Сохранять прежнюю подборку и выбранный отель, добавлять новые объекты, передавать все показанные ID категории и полный текст уточнений. После `partial` сохранять пригодные объекты. Для повтора завершившейся попытки — новый `taskId`; повтор из-за потери HTTP-ответа использует прежний ID и тело. При смене направления или сбросе формы не показывать опоздавший ответ как результат новой поездки. [Сценарии](SCENARIOS.md)

## 8. Проверка перед сдачей

**Автоматические тесты** запускать без внешней сети и оплаты. Подменить HTTP на границах Geoapify, Flash, Search, Fetch и FX, оставив настоящий путь POST → БД → обработчик → GET. Для источников цен брать небольшие воспроизводимые фрагменты с заголовками и единицами. Существующие тесты, ожидающие моковые отели у новых задач, перевести на фикстуры поставщиков; отдельно сохранить тесты старых сохранённых задач. Не включать моковую замену в рабочий код ради прохождения тестов.

| Набор | Обязательная проверка |
|---|---|
| Направления и API | Москва через старый ID, зарубежный город с четырьмя полями, одноимённые города, неверные координаты, обе формы сразу. Эквивалентные запросы конструктора и публичного API проходят одну валидацию. Старое тело с тем же ID остаётся идемпотентным. |
| Холодная БД и достоверность | От источника до первого реального отеля, сумма 48 000 ₽ в контрольном сценарии. Выдуманное название, чужая цитата, конфликт филиалов, неизвестная цена и тариф другой вместимости не проходят. Неизвестное необязательное поле сериализуется как `null`. |
| Условия | Обязательное, мягкое, исключённое и снятое пожелание. Одинаковый завтрак в разных тарифах; часы только в выходные; последнее уточнение снимает обязательность. Пустой эффективный список не восстанавливает старые ограничения. |
| Ставки | За номер/ночь, за период, за группу, валютный номинал, дробное округление, нулевые ночи, равенство лимиту и превышение на рубль. Для аналогов проверить достаточные и недостаточные основания. |
| Каталог и гонки | Тёплый поиск без новых внешних вызовов при достаточных фактах. Новые даты пересчитывают цену; неподходящий тариф не используется. Два сайта одного отеля дают один ID, два филиала сети остаются разными. Две параллельные задачи не создают дубль. |
| Завершение | Полный пакет и неизвестный запас; проверенный лишний кандидат; штатное исчерпание; ошибка до первого результата; сбой после одного пригодного отеля; технический предел при недоборе. Для каждого проверить статус, `items`, `hasMore`, ошибку и действия кнопок. |
| Совместимость и приватность | Оба аккаунта могут искать один реальный объект; диагностика, история и расход доступны только владельцу задачи. Прежняя задача читается после рестарта, просроченная задача восстанавливается, повторный GET не меняет показатели. Места и смета продолжают работать и для Киото. |

**Живая приёмка.** Подготовить пустые образцы переменных `GEOAPIFY_API_KEY` и `DEEPSEEK_API_KEY` и их явную передачу в [Compose](../compose.yaml). Сохранить существующий локальный dotenv и том. Не читать ключи из стендов. Из `API/` прогнать `python -m unittest discover -s tests -v`, затем `docker compose up -d --build`, проверить `/health` и `/portal`. Проверить включение новых файлов в [Dockerfile.dockerignore](../Dockerfile.dockerignore). Для PostgreSQL использовать отдельную тестовую базу по инструкции проекта; если проверена только SQLite, указать это при сдаче. [Запуск](../README.md)

1. В локальном портале выбрать Москву и Киото через подсказки. Проверить тела запросов и выбор конкретной строки. Подтвердить, что Москва не ограничивает перечень доступных городов.
2. На холодном каталоге запросить один отель, затем пакет. Для найденного отеля вручную открыть источник, проверить идентичность, одно обязательное условие и расчёт цены. Если конкретный источник в этот день не дал данных, зафиксировать реальный исход; детерминированную успешную ветку подтвердить фикстурой и отдельно попытаться получить живой результат на другом подходящем запросе.
3. Повторить тот же запрос новой задачей, затем изменить число людей, добавить уточнение и запросить «Ещё» с исключениями. Записать время, вызовы и токены по этапам. Проверить, какие значения удалось взять из каталога. Не зачищать рабочий том ради сравнения: холодный сценарий можно выполнить на отдельной временной БД.
4. Выбрать отель и тестовое место, запустить смету. Открыть тот же результат через собственный журнал и проверить отдельный вызов гостиничной задачи через Swagger с ключом **TripFlow**. При отсутствии ключей провайдера проверить сценарий с подготовленным каталогом и статусы, сообщить, какая живая проверка осталась.

**Сдача.** Обновить документацию фактической локальной сборки, Swagger, гайд по порталу и handoff для C#, явно обозначив отличия от опубликованного мока. В сообщении автору дать адрес портала, шаги проверки одной карточки, перечень выполненных тестов, пример проверенного отеля с основанием цены и измерения холодного/тёплого поиска. Отдельно отметить ограничения покрытия источников и невыполненные проверки. Готовность Stage 2 означает работающий пакет через обычный API и конструктор; самостоятельный прототип в каталоге экспериментов не заменяет этот результат.
