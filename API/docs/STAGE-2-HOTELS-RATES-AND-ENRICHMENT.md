# Stage 2 · Приём ориентировочных тарифов, ручная цена проживания и заполнение карточки

**Результат для пользователя.** В конструкторе можно вручную указать желаемую сумму проживания всей группы, получить варианты близкого ценового уровня и увидеть, из какого тарифа получилась цена. У выбранного объекта есть ссылка на источник цены, а при наличии подтверждённых данных — адрес, фотография и сайт самого объекта. Первая сквозная проверка для зарубежного жилья — Hotel «Беларусь» в Минске, для ручного ориентира и оформления — Оренбург.

Рабочая область — Python API, его локальный портал, тесты и интеграционная документация. Позднее целевую сумму передаст C#. Сейчас её вводит человек. Границы задачи и исходный контракт описаны в [инструкциях API](../AGENTS.md), [handoff для C#](BACKEND-HANDOFF.md) и [предыдущем задании по покрытию](STAGE-2-HOTELS-COVERAGE.md).

## 2. Тарифы · Ослабить требования к форме записи, сохранить смысл суммы

**Минский сбой состоит из нескольких проверок.** Список валют в `PRICE_MARK` при подготовке страницы пропускает BYN. Паттерн `NIGHT` распознаёт «/сутки», но отклоняет «/сут.». Ответ Flash может содержать исходную оговорку «цена зависит от загрузки гостиницы, и может меняться в зависимости от даты бронирования»; общий отказ при неизвестном `caveat` теряет полезный ориентир. Возможны и отдельные ошибки привязки источника к филиалу. Нужен тест с оригинальным блоком, названием, цитатой и оговоркой. [Разметка страницы, валидация ставки и Exchange](../tripflow_api/hotel_evidence.py)

**Предлагаемая последовательность обработки.**

1. Выделять предложение одного объекта и одной категории номера. Сохранять заголовок номера, строки цены, ближайший относящийся к ним заголовок таблицы и сноску. Одноместность, валюта и период могут находиться в разных строках одного предложения. При повторяющихся ценах не переносить данные из соседнего тарифа. Если модель склеила выдержку, можно восстановить подтверждённые строки по ID блока.
2. Использовать общий распознаватель сумм и валют в обнаружении блока и в финальной проверке. Принимать явные ISO-коды с обеих сторон числа, поддерживать локальные знаки и словоформы («бел. руб.», «US$», «₽»), нормализовать неразрывные пробелы и пунктуацию. Для трёхбуквенного слова проверить, что это код валюты. Доступность курса проверять отдельным шагом. Для неоднозначного символа брать валюту из заголовка прайса или явного пояснения источника; если её установить нельзя — запустить узкую проверку. Обрабатывать `/сут.`, «за сутки», «за 1 ночь», `per room per night`. Исходную выдержку хранить дословно.
3. Flash поручить смысловую работу — выделить объект, размещение, исходную сумму, валюту, единицу, тип цены и оговорки со ссылками на фрагменты. Python сверяет сумму с записью в источнике и считает итог. При исправимом расхождении сначала повторно разобрать имеющийся блок, потом при необходимости запросить недостающий факт. Это особенно важно для уже скачанных иностранных прайсов.
4. Различать принятую ставку, принятую ориентировочную ставку и ставку, требующую уточнения. Тип можно хранить существующими полями `kind`, `scope`, `basis` и основаниями оценки. «От», диапазон с известными границами, зависимость от загрузки, отсутствие подтверждённой доступности и опубликованная ночная ставка другого периода допускают **оценку**. Отражать это у цены и в личной диагностике. Информация о завтраке или возвратности влияет на выдачу при соответствующем требовании пользователя. Если информации не хватает для обязательного условия — искать подтверждение у того же филиала.
5. Основания для отклонения конкретного тарифа — ошибочный город или филиал, неизвестная валюта после уточнения, невозможность отличить койку от отдельного номера, неясное количество ночей или комнат в общей сумме, неизвестная обязательная доплата, рассрочка без полной стоимости либо заведомо неприменимая льгота. Для объекта пробовать другой тариф или проверенные аналоги по действующим правилам. «Цена может измениться» и «обязательный сбор в неизвестном размере» должны приводить к разным решениям.

**Арифметика.** Расчёт в рублях реализуем обычным кодом. `Exchange.quote` уже читает значение и номинал валюты, а `group_price` использует `Decimal`. Переиспользовать этот путь. Для одной ночи в одном номере формула — `сумма × valueRub / nominal × номера × ночи`. Для `group_night` умножить только на ночи, для `room_stay` — только на номера, для группового предложения на весь период взять сумму один раз. Округление вверх один раз в конце. RUB проходит без сети. В деталях оставить исходную валюту, дату, источник курса, номинал, ставку и множители. Для ставки другого периода подписывать отдельно дату тарифа и дату курса. [Получение и кэширование документа курсов](../tripflow_api/hotel_tools.py)

**Если курса нет.** Отличать неизвестный код, отсутствие валюты в документе и временную недоступность FX. Использовать применимый кэш по текущим правилам. Если он не помог, искать предложение с подтверждённой рублёвой ценой либо другую ставку с доступной конверсией. Flash может найти такой источник и извлечь цитату. Придуманный курс или рублёвая сумма по памяти модели не дают проверяемой оценки. Неудача одной валюты не должна останавливать обработку остальных объектов. В личной диагностике показывать точную причину, например «ставка распознана в BYN, конвертация отложена».

## 3. Ручной ориентир · Подобрать номер и гостиницу под желаемую сумму

**Семантика.** Предлагаемое имя нового необязательного поля верхнего уровня — `targetHotelTotalRub`. Это положительное целое число рублей на всех путешественников и все ночи. Пропущенное поле и `null` означают отсутствие ориентира. Для гостиничной формы добавить ввод «Желаемая сумма проживания на всю группу, ₽», по умолчанию пустой. Если поле заполнено, допускаются варианты как ниже, так и выше цели. Отправлять его при первичном подборе и «Ещё». При смене суммы начинать новую подборку. Для `targets="attractions"` конструктор поле не передаёт.

**Совместимость.** `trip.budgetRub` относится ко всей поездке. Не выводить из него ни долю на жильё, ни верхнюю цену. В действующем контракте `maxTotalRub` — явный жёсткий предел, который некоторые клиенты уже могут использовать. Для нового ручного сценария конструктор отправляет `maxTotalRub=null`. Если интеграционный клиент прислал оба поля, сначала применить явно запрошенный потолок, затем ранжировать по близости к цели. Прежнюю ручку потолка в форме отелей заменить вводом ориентира, форму мест оставить с её текущей семантикой. Обновить Swagger и пример для C#, чтобы значения не путали. [DTO](../tripflow_api/schemas.py) · [Конструктор](../tripflow_api/portal_assets/card-builder.js) · [Контракт](CONTRACT.md)

~~~json
{
  "taskId": "orenburg-target-400k",
  "trip": {
    "destination": {"city": "Оренбург", "countryCode": "RU", "latitude": 51.77, "longitude": 55.10},
    "startDate": "2026-12-02", "endDate": "2026-12-05", "travelers": 2,
    "budgetRub": 850000, "preferences": null
  },
  "targets": "hotels", "count": 2, "targetHotelTotalRub": 400000,
  "maxTotalRub": null, "excludedObjectIds": [], "refinement": null
}
~~~

**Как выбирать.** После проверки обязательных условий сформировать допустимые пары «объект + тариф». При наличии цели сначала выбрать подходящую категорию номера внутри объекта, затем сравнить лучшие предложения разных отелей. Практичная мера близости — `abs(groupRub − targetRub) / targetRub`. Среди сопоставимых по качеству основания, доступности и предпочтениям первыми идут ближайшие суммы. Учитывать давность данных, тип комнаты и подтверждённые признаки уровня, чтобы старый экономтариф не выигрывал только из-за порядка ID. Использовать ID для разрешения реального равенства. Высокая цена сама по себе не доказывает премиальный класс. В деталях показывать выбранную категорию, итог и разницу с желаемой суммой.

Для поисковых фраз можно вычислить ориентир на номер за ночь. При 400 000 ₽, двух путешественниках и трёх ночах это около 66 667 ₽. Использовать его для поиска более подходящих предложений, если первые два найдены только в экономсегменте. Ни ставка в БД, ни сумма по аналогам не должны выводиться из этой цифры. Если в доступных источниках близких цен нет, вернуть лучшие подтверждённые варианты с понятным пояснением. Выборку с одним лишь старым и далёким от цели предложением стоит дополнить ограниченным точечным поиском до финализации. [Планирование, evaluate и rank](../tripflow_api/hotels.py)

Учесть новый параметр в идентичности запроса и повторном подборе. Старый сохранённый POST без поля должен быть эквивалентен тому же POST с `null`; иная ненулевая цель с прежним ID использует обычную обработку конфликта. Смена цели с новым ID переиспользует факты, цены и метаданные объекта и пересчитывает порядок. Снимок старого результата остаётся читаемым. [Хранение и сравнение задач](../tripflow_api/tasks.py)

## 4. Enrich · Заполнение полей выбранных карточек

В `HotelSearch.run` полный пакет из БД и полный пакет от поставщика сейчас возвращаются до веб-поиска. Свести успешные выходы и пригодные элементы частичной выдачи к финализации, которая умеет обогатить отобранные объекты. Для частичной выдачи учитывать оставшееся время. Пропуск необязательного поля или сбой источника фотографий не должен уничтожить уже рассчитанную цену. Начинать с финалистов под `count`, применять кэш и общий дедлайн. [Экспериментальный enrich](../experiments/deepseek-web-controlled/trip.py) · [Чтение метаданных страницы в стенде](../experiments/deepseek-web-controlled/page_metadata.py)

| Поле | Откуда брать и как проверить |
|---|---|
| Адрес | Использовать подтверждённый адрес филиала у поставщика, геоисточника или на официальной странице. Для агрегатора нескольких квартир сверять адрес с выбранным предложением. В примере «Квартиры Надежда» нельзя взять улицу из произвольной соседней строки. |
| Сайт объекта | Проверить имя объекта вместе с городом, адресом или координатами. Кнопка «Сайт гостиницы» ведёт на подтверждённый объект. Текущий `sourceUrl` и отдельная ссылка «Источник цены» продолжают вести на источник ставки. Можно сначала хранить сайт в деталях владельца для портала; при добавлении в публичный результат описать nullable-поле в handoff. |
| Фото | Сначала проверить подтверждённую страницу объекта и связанные с ней изображение поставщика, `og:image` или подходящее изображение страницы. При необходимости — точечный поиск. Исключать логотип сайта, фото города и соседних гостиниц. Проверять принадлежность филиалу и сохранять URL изображения вместе со страницей-источником. Flash может помочь выбрать из найденных изображений с ID. |

Хранить у метаданных источник и объект или предложение, к которому они относятся. Удачный результат переиспользовать, для временных неудач учитывать дату попытки, чтобы не оплачивать одинаковую работу при каждом GET. Обновления из параллельных задач объединять без потери более полных полей. При чтении метаданных произвольных страниц использовать ограниченную сетевую загрузку с проверкой адресов, редиректов, типа и размера ответа. В интерфейсе **фактически отрисовать** `imageUrl`, адрес, доступные ссылки и тип оценки. При недоступной картинке выбор варианта и расчёт сметы должны работать. [Поставщики](../tripflow_api/hotel_sources.py) · [Хранение каталога](../tripflow_api/hotel_catalog.py) · [Детали в портале](../tripflow_api/portal_assets/preference-view.js)

## 5. Проверки для сдачи

| Сценарий | Ожидаемый результат |
|---|---|
| Минск, исходные строки «Сингл … 260 BYN/сут.», ответ Flash с оговоркой о загрузке | Выдать реальный объект через обычный путь. На фиксированном **тестовом** курсе 30 ₽ за 1 BYN, для двух комнат и трёх ночей результат 46 800 ₽. Имя, валюта, оговорка и расчёт видны в деталях. Независимо проверить формы «за сутки» и «/сут.». |
| Номинал 100 единиц, отсутствующая валюта, недоступный сервис курса | Отдельно проверить деление на 100 и округление вверх только итога. Для неизвестной валюты нет фиктивной рублёвой суммы. В той же задаче подтверждённый RUB-вариант выдаётся. |
| Числовые и смысловые пограничные случаи | `8,000 RUB` в англоязычном прайсе не превращается в 8 ₽. 13 000 ₽ за два номера за ночь на три ночи дают 39 000 ₽. «2 512 ₽ × 4 платежа» без проверенного полного итога не принимается как ночная цена. «От» и тариф другого периода с известной единицей дают помеченный ориентир; койка в общем номере не проходит как отдельная комната. |
| Одинаковый каталог, сопоставимые предложения на 35 000, 380 000 и 430 000 ₽ | При цели 400 000 ₽ в первых двух оказываются 380 000 и 430 000. При цели 40 000 первым становится 35 000. В одном отеле с двумя категориями меняется и выбор тарифа. Изменение только общего бюджета не создаёт автоматического потолка. При `maxTotalRub=400000` явно ограниченный клиент исключает вариант за 430 000. |
| Только далёкие от цели цены | Возвращаются реальные варианты с отклонением от цели. Записанные цены источников при смене ориентира совпадают. Отдельно проверить старые запросы без нового поля, дубликат POST, повторный GET и «Ещё» с исключениями. |
| Достаточный каталог Russhotels без картинок и официальный сайт с подтверждённым фото | Первый запрос выдаёт отель, адрес, разные ссылки по назначению и видимое фото. На повторе обогащённые поля читаются из кэша. Если на странице только логотип или сетевой сбой, карточка выдаётся с проверенными полями. Проверить это и в браузере при выборе отеля. |

**Порядок сдачи.** Сначала зафиксировать неудачный минский ответ и одинаковую выдачу для разных ценовых целей, затем пройти путь с фикстурами без внешних вызовов. Реализовать распознавание и проверку валюты, правила ориентировочной цены, ручной ввод и ранжирование, затем финализацию с enrich и вывод полей. Из каталога `API/` выполнить `python -m unittest discover -s tests -v`, гостиничный набор на отдельной PostgreSQL и `docker compose up -d --build`. В живом портале проверить Минск и Оренбург с двумя разными **целями проживания**. Если рынок конкретного города не даёт близких сумм, показать ближайшие реальные предложения и их отклонение. Для фиксированной проверки смены порядка использовать подготовленный каталог из таблицы. [Запуск и окружение](../README.md)

В ответе автору приложить по одному фактическому результату на каждый из трёх путей — иностранная ставка с курсом, ручной ценовой ориентир, обогащённая карточка. Указать число рассмотренных и оценённых объектов, причину непринятых ставок, обращения Flash/FX и обогащения, токены и время холодного и повторного запроса. Отдельно отметить результат живой проверки и результат на фикстурах. Работа выполняется локально, без коммита и выкладки на Render.
