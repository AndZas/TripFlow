# Архитектура Python-сервиса TripFlow

Текущий FastAPI-сервис принимает задачи на подбор и смету, обрабатывает их в фоне и сохраняет результаты для опроса по HTTP. Подбор и расчёт выполняются на тестовых данных Москвы. [HTTP-контракт](CONTRACT.md) · [Схемы и примеры](BACKEND-HANDOFF.md)

В `main` реализован первый этап работы с моделью. При настроенном `DEEPSEEK_API_KEY` фоновый обработчик разбирает пожелания поездки и уточнение категории. Python проверяет результат и сохраняет его для кабинета разработчика. Задачи одного аккаунта могут переиспользовать готовый разбор. Статус анализа и расход токенов доступны в журнале, а результат подбора для C# формируется из тестового каталога. [Разбор пожеланий в портале](PORTAL.md#разбор-пожеланий-локально)

Архитектура мирового подбора согласована 22 ноября 2026 года. Разделы начиная с «Модель и выполнение задач» описывают целевой процесс, включая поиск в источниках, ранжирование и оценку расходов. Изменения полей и последовательность подключения клиента собраны в [плане для C#](BACKEND-MIGRATION.md).

## Ответственность сервисов

| Компонент | Что делает |
|---|---|
| Python API | Проверяет ключ и тело запроса, сохраняет задачу, формирует результат и отдаёт его по ID. Обслуживает кабинет интеграции. |
| C# backend | Хранит состояние основного приложения. Связывает задачи с версиями карточек, сохраняет выбор и считает итог карточки. Для подключения к текущему Python API нужно перевести клиент C# на polling и новый формат запросов. |
| React | Получает карточки и состояние подбора через C#. Целевой сценарий предусматривает опрос карточки до готовности нужного списка или сметы. |
| Хостинг | Сервис работает в Docker. Render использует PostgreSQL. Docker Compose по умолчанию использует SQLite в именованном томе. |

Связь между сервисами идёт от C# к Python. Ключ Python API хранится на стороне C#. Дашборды, карточки и голоса принадлежат C#. Python хранит аккаунты своего кабинета и состояние своего API. [Текущее состояние C#](../../Backend/README.md#связь-с-python)

## Подбор и расчёт бюджета

| Операция | Что принимает Python | Результат |
|---|---|---|
| `POST /v1/recommendations` | `taskId`, `trip`, одна категория `targets`, `count`, `maxTotalRub`, `refinement` и `excludedObjectIds`. | Результат подбора по одному типу. Мок применяет фильтр цены, исключения и предел числа вариантов. Текст пожеланий и уточнение проходят валидацию. Ранжирование по ним относится к подключению AI. |
| `POST /v1/budget` | `taskId`, `trip`, выбранные отель и места с ID и ценами. | Четыре статьи дополнительных расходов на всю группу. Текущая формула использует только число дней, путешественников и бюджет. |
| `GET /v1/tasks/{taskId}` | ID задачи и тот же `X-API-Key`. | Возвращает состояние `pending` или `completed` и сохранённый `result`. |

Целевой клиент запускает отели и достопримечательности отдельными задачами. Отели и места могут стать доступны в разное время. Догенерация отправляет новый ID, актуальные ограничения и исключения. C# записывает результат в список соответствующей категории и сохраняет текущий выбор. Смета запускается отдельной задачей после выбора. Стоимость проживания и посещений C# добавляет к ответу Python при расчёте карточки. [Сценарии](SCENARIOS.md)

## Опрос задач и завершение выдачи

Python сохраняет запрос и возвращает `202 Accepted`, `Location` и `Retry-After: 2`. После сохранения запускается фоновый обработчик в том же процессе Uvicorn. При старте процесса из базы подхватываются задачи без результата. Это позволяет продолжить работу после перезапуска с той же БД.

Владелец задачи определяется по API-ключу. Повтор POST с тем же ID и нормализованным телом даёт `202`. Смена данных или операции при том же ID даёт `409`. Готовое тело читается повторно с тем же ключом. Статус `completed` означает, что обработка закончилась. Успех или ошибка указаны внутри `result`.

| Событие | Результат |
|---|---|
| `recommendations.finished` | Результат одной категории со статусом, списком `items` и признаком `hasMore`. |
| `budget.finished` | Четыре статьи дополнительных расходов либо прикладная ошибка. |

При подключении polling C# должен хранить версию карточки и применять готовый результат один раз. При изменении параметров карточки старый результат остаётся связан со старой версией. React читает сохранённое состояние из C#. [Версии и повторы](BACKEND-HANDOFF.md#версии-и-повторы)

## Кабинет и хранилище

Кабинет `/portal` принимает заявки с email и паролем. Владелец и администраторы рассматривают обычные заявки. Владелец управляет ролями, отключает аккаунты и рассматривает повторные заявки после отключения. Решение видно при входе. Пользователь выпускает один ключ и смотрит журнал своих задач. Административная панель показывает использование API по аккаунтам. Конструктор карточки запускает задачи по той же схеме и с тем же хранилищем. Он определяет аккаунт по сессии кабинета, а задачи и запросы опроса учитываются вместе с вызовами публичного API. [Кабинет разработчика](../README.md#кабинет-разработчика)

Пароли хранятся в виде хешей Argon2. В базе хранятся хеши ключей и сессий. Полное значение ключа доступно при выпуске. Перевыпуск и отзыв лишают прежний ключ доступа к API. Сессия кабинета использует cookie, а запросы интеграции используют `X-API-Key`.

PostgreSQL и SQLite содержат аккаунты кабинета, сессии, задания, результаты и почасовые счётчики API. `/health` выполняет проверочный запрос к БД. Инструкция по запуску, переменные и ветка деплоя описаны в README. [Размещение](../README.md#размещение-на-render) · [Гайд по порталу](PORTAL.md)

## Модель и выполнение задач

Цель следующего этапа — подбор по всему миру для русскоязычной аудитории. Первый запрос по городу должен работать при пустом каталоге объектов. C# передаёт выбранный город, код страны и координаты. Python пользуется открытым веб-поиском. Специализированный источник можно подключить для конкретной географии или поля, когда он улучшает результат. Для всех публичных денежных полей используется рубль.

### От запроса до выдачи

1. Python принимает отдельную задачу для отелей или мест. Внутри обработчика DeepSeek Flash разбирает свободные пожелания на обязательные условия, предпочтения, исключения и вопросы к источникам. Код берёт даты, численность, направление и суммы из типизированного входа. Две задачи одной поездки могут переиспользовать общий разбор. Для догенерации применяется накопленный текст уточнений этой категории в порядке ввода. Более позднее уточнение меняет только затронутое условие.
2. Обработчик выбирает из PostgreSQL реальные объекты нужной категории в нужном городе. Исключает все переданные C# `excludedObjectIds`. Учитывает применимые цены, подтверждённые признаки и область действия каждого факта. Когда сведений достаточно, формирует пакет из каталога.
3. При нехватке кандидатов модель предлагает поисковые фразы с учётом языка и направления. Python вызывает Search, удаляет повторные ссылки и выбирает страницы для Fetch. Если кандидаты уже есть, поиск адресуется только пробелу у перспективных объектов. На сайтах с разной вёрсткой модель получает текст страницы с заголовками, строками тарифов и соседним контекстом. Извлекает структурированные значения и короткие цитаты. Код проверяет типы, наличие цитат, связь с конкретным объектом, единицы, валюту и область применения. Недоступный сайт допускает переход к другому источнику.
4. Обработчик проверяет обязательные условия у лидеров, при необходимости переходит к следующим кандидатам. Например, «по выходным завтрак с 6:30» отвечает на вопрос о раннем завтраке в субботу. «Завтрак включён» оставляет время неизвестным и относится только к указанному тарифу. Для обязательного признака нужен подтверждённый ответ. Для желательного признака неизвестность или несовпадение снижают приоритет.
5. Python отбрасывает превышение единственного потолка `maxTotalRub`, если цена известна. При сопоставимом соответствии пожеланиям можно предпочесть более качественный вариант ближе к потолку. Более дешёвые подходящие объекты участвуют в доборе. Модель может упорядочить короткий список по смыслу пожеланий. Код принимает только ID из списка и повторно проверяет обязательные условия, исключения, цены и дубли.
6. Цель — заполнить `count`; обычная порция C# составляет два-три объекта. При нехватке ослабляются только желательные признаки. Результат может быть меньше запрошенного. Перед записью Python валидирует всё событие по типу задачи. Наружу передаются данные объекта, ссылка на источник и служебные поля результата. Цитаты для проверок остаются внутри Python. Генерация рассказа о причинах рекомендации не требуется.

| Завершение задачи категории | Статус внутри результата | Значение для клиента |
|---|---|---|
| Найден пакет либо штатно исчерпан поиск, в том числе с пустой выдачей | `succeeded` | Показать найденное. Полный пакет допускает `hasMore: null`, когда следующий объект не проверяли. |
| Поиск прервался, есть проверенные объекты | `partial` | Показать объекты и разрешить повтор. |
| Поиск прервался до первого пригодного объекта | `failed` | Показать ошибку и разрешить повтор. |

`hasMore` сообщает только о запасе вариантов: `true` требует ещё одного проверенного подходящего объекта, `false` означает исчерпание поиска, `null` — неизвестность. Один неудачный запрос к сайту сам по себе не доказывает исчерпание. Технический предел времени или стоимости до заполнения пакета завершает прерванный поиск по таблице.

## Постоянный каталог объектов

Каталог в PostgreSQL пополняется по запросам. Он хранит объекты и проверяемые сведения, в том числе об объектах, не выбранных группой. Выбор и исключения карточки ведёт C#. В курсовой БД у фактов нет истории версий, дат проверок и срока жизни. Срок действия тарифа, часы работы, день недели и ограничения на число гостей — часть содержания факта.

| Запись | Что переиспользуется |
|---|---|
| Объект | Собственный неизменяемый `objectId`, тип, город, варианты названия, адрес, координаты при наличии, ссылки на страницы объекта. |
| Факт | Нормализованный признак или вопрос, значение, условия применения, источник и выдержка. Вердикты по условиям различают `true`, `false` и `unknown`. Сходство формулировок помогает найти сведения, повторное использование требует совпадения смысла и области действия. |
| Исходная ставка | Сумма или диапазон, валюта, единица, тариф, применимость к датам и размещению. Для пересчёта хранится использованный курс. |
| Результат задачи | Итоговые рублёвые суммы и пакет, сохранённые для конкретного аккаунта и `taskId`. Повтор GET возвращает прежний итог. |

**Сопоставление объекта.** Сначала ищем известную ссылку на страницу конкретного объекта. Для новой ссылки сверяем город и тип, варианты названия, адрес и доступные координаты. Страница сети отелей, одинаковое имя или близкие координаты по отдельности недостаточны. Например, кириллическое и латинское названия гостиницы с одним точным адресом могут обозначать одну запись. При уверенном совпадении добавляем источник и варианты имени к прежнему ID. Новому объекту выдаём ID, например UUID. При вероятном дубле уточняем адрес или филиал; при оставшейся неоднозначности пропускаем кандидата. Финальную сверку и создание записи сериализуем для города и типа в короткой транзакции без сетевых вызовов. После сопоставления снова применяем исключения. Это снижает риск, что при одновременном поиске или смене сайта один отель получит два ID.

## Цены и смета

Все суммы для пользователя ориентировочные. Python переводит исходные суммы в RUB с учётом единицы тарифа и округляет положительную дробную итоговую сумму вверх. Код сохраняет основание расчёта внутри сервиса.

- **Отель.** Для выдачи обязательна обоснованная цена за всю группу и все ночи. Берём опубликованную ставку подходящего размещения, при диапазоне ориентируемся на нижнюю часть с учётом пожеланий, для ставки «от» допустимо исходное значение. Если ставка отсутствует, можно оценить её по сопоставимым реальным отелям того же района и класса. При отсутствии основания пропускаем отель. Ставку за один отдельный номер за ночь умножаем на число путешественников и ночей. Тариф за весь период сначала приводим к нужной единице. Например, 8 000 ₽ за номер за ночь × 3 человека × 2 ночи = 48 000 ₽. Целевой бюджет путешественника не служит источником ставки.
- **Достопримечательность.** `price` — целые рубли за одно посещение всей группой. Индивидуальный билет умножаем на число участников, применимую групповую ставку учитываем один раз. Подтверждённая бесплатность даёт `0`, неизвестная стоимость — `null`. Приоритет у подходящих мест с известной ценой в пределах лимита. Место с неизвестной ценой допустимо для добора даже при лимите, если хорошо соответствует условиям. Запрос «только бесплатное» требует подтверждённого нуля.
- **Смета после выбора.** По выбранным ID и ценам Python подбирает применимые местные ставки и подтверждённые включения. Завтрак учитывается как включённый только при однозначной связи с выбранным предложением. DeepSeek оценивает сценарий питания, городского транспорта и прочих трат по данным и пожеланиям. Python проверяет единицы, числа и арифметику и рассчитывает резерв по принятому правилу. Формулы мока, включая 10% резерва, описывают действующий релиз. Ночи считаются разницей дат, расходы по дням охватывают обе даты.
- **Итог.** Python возвращает четыре неотрицательных целых суммы за поездку группы: `foodTotalRub`, `localTransportTotalRub`, `otherExpensesTotalRub`, `reserveTotalRub`. Если обязательную оценку получить не удалось, возвращает `failed` и `expenses: null`. C# добавляет уже рассчитанные групповые цены выбранных объектов по одному разу. Неизвестный билет пропускает в сумме и помечает смету как неполную.

## Выполнение на Render и стоимость

План реализации использует существующий FastAPI и PostgreSQL. Внутри обработчика задачи Python управляет инструментами каталога, Search и Fetch и короткими структурированными запросами к DeepSeek. На каждом этапе модель получает цель, кандидатов, релевантные факты и недостающие поля. Содержимое страницы служит данными для извлечения. Выбор инструмента, ограничения и проверку результата контролирует Python.

Время задачи, число обращений к модели, Search и Fetch, объём токенов и параллелизм ограничиваются настройками. Общий разбор и одинаковые проверки, запущенные одновременно, можно выполнить один раз. Временный сетевой сбой допускает ограниченный повтор с паузой. Ошибка структуры допускает точечное исправление. Отсутствующее доказательство требует другого источника или кандидата. Отдельно учитываем затраты и время по этапам, попадания в каталог и холодный старт Render.

Для платных этапов планируется ограниченная очередь с захватом задачи в БД на время исполнения и сохранением завершённых дорогих шагов. После перезапуска исполнитель подхватывает незавершённую работу. Повтор POST безопасен на уровне задачи; обрыв после ответа поставщика до записи результата всё ещё может привести к повторной оплате этапа. Кабинет и публичная API используют один обработчик и формат поездки.

**Дополнительный вариант.** Локальный клиент LM Studio может выполнять узкие операции, например извлекать цитаты. Для удалённого портала рассматривается исходящее подключение клиента своего аккаунта, ограничение времени и явная настройка платного перехода на DeepSeek. Это отдельное расширение. Значения лимитов, конкретный источник курсов и параметры сопоставления подбираются при реализации. [Результаты экспериментов](research/deepseek-web-trip/report.md)
