# Архитектура Python-сервиса TripFlow

Текущий FastAPI-сервис принимает задачи на подбор и смету, обрабатывает их в фоне и сохраняет результаты для опроса по HTTP. Подбор и расчёт выполняются на тестовых данных Москвы. [HTTP-контракт](CONTRACT.md) · [Схемы и примеры](BACKEND-HANDOFF.md)

## Ответственность сервисов

| Компонент | Что делает |
|---|---|
| Python API | Проверяет ключ и тело запроса, сохраняет задачу, формирует результат и отдаёт его по ID. Обслуживает кабинет интеграции. |
| C# backend | Хранит состояние основного приложения. Связывает задачи с версиями карточек, сохраняет выбор и считает итог карточки. Для подключения к текущему Python API нужно перевести клиент C# на polling и новый формат запросов. |
| React | Получает карточки и состояние подбора через C#. Целевой сценарий предусматривает опрос карточки до готовности нужного списка или сметы. |
| Хостинг | Сервис работает в Docker. Render использует PostgreSQL. Docker Compose по умолчанию использует SQLite в именованном томе. |

Связь между сервисами идёт от C# к Python. Ключ Python API хранится на стороне C#. Дашборды, карточки и голоса принадлежат C#. Python хранит аккаунты своего кабинета и состояние своего API. [Текущее состояние C#](../../Backend/README.md#связь-с-python)

## Подбор и расчёт бюджета

| Операция | Что принимает Python | Результат |
|---|---|---|
| `POST /v1/recommendations` | `taskId`, `trip`, одна категория `targets`, `count`, `maxTotalRub`, `refinement` и `excludedObjectIds`. | Результат подбора по одному типу. Мок применяет фильтр цены, исключения и предел числа вариантов. Текст пожеланий и уточнение проходят валидацию. Ранжирование по ним относится к подключению AI. |
| `POST /v1/budget` | `taskId`, `trip`, выбранные отель и места с ID и ценами. | Четыре статьи дополнительных расходов на всю группу. Текущая формула использует только число дней, путешественников и бюджет. |
| `GET /v1/tasks/{taskId}` | ID задачи и тот же `X-API-Key`. | Возвращает состояние `pending` или `completed` и сохранённый `result`. |

Целевой клиент запускает отели и достопримечательности отдельными задачами. Отели и места могут стать доступны в разное время. Догенерация отправляет новый ID, актуальные ограничения и исключения. C# записывает результат в список соответствующей категории и сохраняет текущий выбор. Смета запускается отдельной задачей после выбора. Стоимость проживания и посещений C# добавляет к ответу Python при расчёте карточки. [Сценарии](SCENARIOS.md)

## Опрос задач и завершение выдачи

Python сохраняет запрос и возвращает `202 Accepted`, `Location` и `Retry-After: 2`. После сохранения запускается фоновый обработчик в том же процессе Uvicorn. При старте процесса из базы подхватываются задачи без результата. Это позволяет продолжить работу после перезапуска с той же БД.

Владелец задачи определяется по API-ключу. Повтор POST с тем же ID и нормализованным телом даёт `202`. Смена данных или операции при том же ID даёт `409`. Готовое тело читается повторно с тем же ключом. Статус `completed` означает, что обработка закончилась. Успех или ошибка указаны внутри `result`.

| Событие | Результат |
|---|---|
| `recommendations.finished` | Результат одной категории со статусом, списком `items` и признаком `hasMore`. |
| `budget.finished` | Четыре статьи дополнительных расходов либо прикладная ошибка. |

При подключении polling C# должен хранить версию карточки и применять готовый результат один раз. При изменении параметров карточки старый результат остаётся связан со старой версией. React читает сохранённое состояние из C#. [Версии и повторы](BACKEND-HANDOFF.md#версии-и-повторы)

## Кабинет и хранилище

Кабинет `/portal` принимает заявки с email и паролем. Владелец и администраторы рассматривают обычные заявки. Владелец управляет ролями, отключает аккаунты и рассматривает повторные заявки после отключения. Решение видно при входе. Пользователь выпускает один ключ и смотрит журнал своих задач. Административная панель показывает использование API по аккаунтам. Конструктор карточки запускает задачи по той же схеме и с тем же хранилищем. Он определяет аккаунт по сессии кабинета, а задачи и запросы опроса учитываются вместе с вызовами публичного API. [Кабинет разработчика](../README.md#кабинет-разработчика)

Пароли хранятся в виде хешей Argon2. В базе хранятся хеши ключей и сессий. Полное значение ключа доступно при выпуске. Перевыпуск и отзыв лишают прежний ключ доступа к API. Сессия кабинета использует cookie, а запросы интеграции используют `X-API-Key`.

PostgreSQL и SQLite содержат аккаунты кабинета, сессии, задания, результаты и почасовые счётчики API. `/health` выполняет проверочный запрос к БД. Инструкция по запуску, переменные и ветка деплоя описаны в README. [Размещение](../README.md#размещение-на-render) · [Гайд по порталу](PORTAL.md)

## Модель и выполнение задач

Для следующего этапа рассматривается прямой вызов DeepSeek с сервера Python. Способ веб-поиска и получения цен предстоит выбрать. LM Studio можно использовать в среде, где Python доступен его интерфейс. Способ подключения удалённой локальной модели оставлен открытым.

У модели остаются три основных сценария. Разбор пожеланий выделяет фильтры, дополнительные вопросы и сведения о тратах. Проверка условий сопоставляет вопрос с доказательствами по отелю или месту и возвращает вывод. Оценка бюджета опирается на справочные ставки и выбор пользователя. Код проверяет структуру, источники, единицы измерения и арифметику. Запросы к модели и веб-поиск учитываются отдельно, чтобы ограничение одного этапа не скрывало состояние другого.

## Постоянный каталог объектов

Проектируемый каталог относится к версии с внешними данными. Сейчас список объектов задан в коде мока.

Отель и достопримечательность получают собственный неизменяемый `objectId` TripFlow. Для сопоставления используются тип объекта, нормализованное название и координаты. Адрес и населённый пункт помогают разобрать неоднозначные случаи. Внешний ID можно сохранить рядом с названием источника для обновлений и диагностики. Запись можно создать, если объект уверенно распознан по названию и координатам, даже когда внешний ID отсутствует. При смене названия или уточнении координат уже связанный объект сохраняет свой `objectId`. Неоднозначное совпадение требует дополнительной проверки. Точный допуск по расстоянию предстоит подобрать на данных поставщиков.

Логически запись содержит три части:

- Основные поля объекта — название, адрес, координаты, тип, описание и другие доступные характеристики. Цены сохраняются вместе с условиями, к которым относятся.
- `filters` — список подтверждённых стандартных признаков объекта для быстрого подбора. Модель может предложить признак для проверки. В список он попадает после подтверждения по данным. Обязательность, желательность и исключение задаются в запросе пользователя.
- Дополнительные данные — словарь, где ключ обозначает смысл вопроса, а значение содержит ответы по областям действия. Для каждой области сохраняются `true`, `false` или `unknown` и источник, если он есть. `unknown` означает, что доказательств недостаточно.

Для курсового запуска достаточно одного сохранённого состояния каталога. Время получения данных и проверки условий, история версий факта и сроки актуальности в каталоге не ведутся.

Для распространённых вопросов сценарий разбора пожеланий выделяет известный признак и область действия. Для разных формулировок редких вопросов можно искать похожие проверки с помощью эмбеддингов. Перед повторным использованием нужно подтвердить совпадение смысла, отрицания и условий применения. Порог сходства и необходимость отдельного вызова модели определятся по результатам испытаний.

При первичном подборе и догенерации Python сначала ищет в каталоге записи по направлению, фильтрам, бюджету и условиям, применяя `excludedObjectIds` от C#. При догенерации C# передаёт ID уже полученных и отклонённых вариантов. Если готовых вариантов недостаточно, Python ищет кандидатов во внешних источниках, сопоставляет их с каталогом и проверяет недостающие факты. Каталог пополняется сведениями о рассмотренных объектах, включая те, которые не подошли текущей карточке. Каждый запрос подбора самодостаточен, для продолжения используется тот же эндпойнт с актуальными условиями и исключениями.

### Живая музыка в отеле

Для общего пожелания о живой музыке отель подходит, если источник сообщает, что её проводят. Совпадение с датами поездки даёт дополнительную информацию для карточки.

| Что сообщает источник | Как учитываем |
|---|---|
| Есть подтверждённое выступление в даты поездки | `true`. Можно указать подтверждённые дату и время. |
| Музыку проводят регулярно, например по воскресеньям | `true`. Показываем известное расписание. |
| Музыку проводят, расписание не указано | `true`. Отмечаем наличие музыки и неизвестное расписание. |
| Отель прямо сообщает, что живой музыки нет или выступления прекратились | `false`. |
| Сведений нет либо есть только анонс прошедшего разового выступления | `unknown`. |

Указанные в источнике дни и даты описывают выступления. C# может показать их вместе с результатом проверки. Для обязательного общего пожелания подходит `true`, в том числе при неизвестном расписании.
