# Архитектура Python-сервиса TripFlow

Актуальная схема интеграции зафиксирована 22 ноября 2026 года. React опрашивает C# во время подбора и расчёта сметы. Python обрабатывает запросы в фоне без отдельной очереди задач и публикует результат каждой задачи по её ID. [Контракт](CONTRACT.md) · [Схемы и примеры для команды](BACKEND-HANDOFF.md) · [Сценарии](SCENARIOS.md)

## Ответственность сервисов

| Компонент | Ответственность |
|---|---|
| React | Запускает подбор и смету через C#, опрашивает карточку до завершения и показывает весь полученный пакет вариантов. |
| C# backend | Хранит карточку и её версию, состояние задач, выбор пользователя, отклонённые и полученные варианты, итоговый бюджет. Задаёт лимиты, вызывает Python и опрашивает статус. |
| Python API | Выполняет подбор и смету в фоне, получает данные источников, вызывает модель, валидирует результаты и сохраняет итог для чтения. Ведёт каталог объектов и фактов о них. |
| Модель | Для основной интеграции рассматривается прямой вызов DeepSeek с сервера Python. LM Studio остаётся дополнительным вариантом для разработки и локальных прогонов. |
| Хостинг | Содержит Python API и закрытую панель управления. Render рассматривается как вариант размещения. Постоянное хранилище используется для каталога и итогов задач, необходимых для повторного чтения. |

## Подбор и расчёт бюджета

Две операции для C# используют общую асинхронную схему. Ниже приведены рабочие названия маршрутов.

| Операция | Что отправляет C# | Что возвращает Python |
|---|---|---|
| `POST /v1/recommendations` | `taskId`, параметры поездки, нужные типы и количество вариантов, лимиты. Для догенерации — актуальное уточнение и исключения, включая уже полученные и отклонённые объекты. | Один итоговый пакет с найденными отелями и/или местами, источниками, ценами и результатом по каждому запрошенному типу. |
| `POST /v1/budget` | `taskId`, актуальные параметры поездки, выбранный отель с тарифом и включёнными услугами, выбранные места, подтверждённые или оценочные цены при наличии. | Итог операции с оценками питания, городского транспорта, прочих расходов и резерва на всю группу за поездку. C# суммирует их с проживанием и посещениями и сохраняет итог для этой версии карточки. |

Первичный подбор и догенерация используют одну операцию. C# считает допустимую стоимость нового выбора, исходя из оставшегося бюджета. При замене действующего варианта его стоимость не удерживается в остатке. Бюджет по выбранным вариантам запрашивается отдельно. Текст пожеланий и текущий выбор привязаны к версии карточки.

Для подбора Python разбирает пожелания, ищет кандидатов в каталоге и внешних источниках, применяет фильтры и проверяет недостающие условия. Желательные условия влияют на порядок и могут сопровождаться отметкой о неопределённости. Python ждёт завершения поиска всех запрошенных типов и возвращает найденные варианты одним пакетом. C# сохраняет выдачу целиком. Пользователь выбирает один отель и может добавить несколько мест.

Цена источника, справочная оценка и неизвестная стоимость имеют разные значения. Условие о завтраке влияет на бюджет при подтверждении включения в выбранный тариф. Если цена выбранного посещения неизвестна, итог отмечается как неполный. При ограниченном бюджете можно сократить необязательные прочие расходы до нуля. Если оставшиеся статьи превышают бюджет, C# показывает превышение.

## Опрос задач и завершение выдачи

C# сохраняет ID задачи и версию карточки, отправляет POST и получает `202 Accepted`. Тем же ключом запрашивает `Location` до статуса `completed`. Поиск отелей и мест запускается двумя задачами.

| Событие | Назначение |
|---|---|
| `recommendations.finished` | По каждому запрошенному типу передаётся итоговый статус, список найденных вариантов, `hasMore` и ошибка при необходимости. Пустая завершённая выдача считается успешной. |
| `budget.finished` | Оценки готовы либо расчёт завершился ошибкой. Результат относится к выбору и версии карточки на момент запроса. |

Во время подбора и расчёта сметы React периодически читает `GET {card}` у C#. Опрос завершается, когда нужные статусы вышли из `pending` или экран закрыт. После чтения результата C# одной транзакцией сохраняет пакет и обновляет статусы. При догенерации прежний список и выбор остаются доступны, а новый пакет добавляется целиком. `hasMore` показывает, найден ли следующий пригодный вариант сверх выдачи. `null` означает, что это осталось неизвестно.

Результат хранится в базе API. Повтор GET позволяет восстановить обмен после обрыва соединения. C# проверяет актуальность версии и применяет каждый результат один раз. [Версии и повторы](BACKEND-HANDOFF.md#версии-и-повторы)

## Модель и выполнение задач

Python запускает фоновую обработку принятого запроса без отдельной очереди генерации. Для основной интеграции планируется прямой вызов DeepSeek с сервера Python. Способ веб-поиска и получения тарифов предстоит выбрать. LM Studio можно использовать в среде, где Python доступен его интерфейс. Способ подключения удалённой локальной модели оставлен открытым.

У модели остаются три основных сценария. Разбор пожеланий выделяет фильтры, дополнительные вопросы и сведения о тратах. Проверка условий сопоставляет вопрос с доказательствами по отелю, месту или тарифу и возвращает вывод. Оценка бюджета опирается на справочные ставки, известные включения и выбор пользователя. Код проверяет структуру, источники, единицы измерения и арифметику. Запросы к модели и веб-поиск учитываются отдельно, чтобы ограничение одного этапа не скрывало состояние другого.

## Постоянный каталог объектов

Отель и достопримечательность получают собственный неизменяемый `objectId` TripFlow. Для сопоставления используются тип объекта, нормализованное название и координаты. Адрес и населённый пункт помогают разобрать неоднозначные случаи. Внешний ID можно сохранить рядом с названием источника для обновлений и диагностики. Запись можно создать, если объект уверенно распознан по названию и координатам, даже когда внешний ID отсутствует. При смене названия или уточнении координат уже связанный объект сохраняет свой `objectId`. Неоднозначное совпадение требует дополнительной проверки. Точный допуск по расстоянию предстоит подобрать на данных поставщиков.

Логически запись содержит три части:

- Основные поля объекта — название, адрес, координаты, тип, описание и другие доступные характеристики. Тарифы и цены сохраняются вместе с условиями, к которым относятся.
- `filters` — список подтверждённых стандартных признаков объекта для быстрого подбора. Модель может предложить признак для проверки. В список он попадает после подтверждения по данным. Обязательность, желательность и исключение задаются в запросе пользователя.
- Дополнительные данные — словарь, где ключ обозначает смысл вопроса, а значение содержит ответы по областям действия. Для каждой области сохраняются `true`, `false` или `unknown` и источник, если он есть. Для разных тарифов или условий могут храниться разные ответы. `unknown` означает, что доказательств недостаточно.

Для курсового запуска достаточно одного сохранённого состояния каталога. Время получения данных и проверки условий, история версий факта и сроки актуальности в каталоге не ведутся.

Например, у вопроса «Завтрак включён в цену?» может быть ответ `true` для тарифа с питанием и `false` для тарифа без питания. Для распространённых вопросов сценарий разбора пожеланий выделяет известный признак и область действия. Для разных формулировок редких вопросов можно искать похожие проверки с помощью эмбеддингов. Перед повторным использованием нужно подтвердить совпадение смысла, отрицания и условий применения. Порог сходства и необходимость отдельного вызова модели определятся по результатам испытаний.

При первичном подборе и догенерации Python сначала ищет в каталоге записи по направлению, фильтрам, бюджету и условиям, применяя `excludedObjectIds` от C#. При догенерации C# передаёт ID уже полученных и отклонённых вариантов. Если готовых вариантов недостаточно, Python ищет кандидатов во внешних источниках, сопоставляет их с каталогом и проверяет недостающие факты. Каталог пополняется сведениями о рассмотренных объектах, включая те, которые не подошли текущей карточке. Каждый запрос подбора самодостаточен, для продолжения используется тот же эндпойнт с актуальными условиями и исключениями.

### Живая музыка в отеле

Для общего пожелания о живой музыке отель подходит, если источник сообщает, что её проводят. Совпадение с датами поездки даёт дополнительную информацию для карточки.

| Что сообщает источник | Как учитываем |
|---|---|
| Есть подтверждённое выступление в даты поездки | `true`. Можно указать подтверждённые дату и время. |
| Музыку проводят регулярно, например по воскресеньям | `true`. Показываем известное расписание. |
| Музыку проводят, расписание не указано | `true`. Отмечаем наличие музыки и неизвестное расписание. |
| Отель прямо сообщает, что живой музыки нет или выступления прекратились | `false`. |
| Сведений нет либо есть только анонс прошедшего разового выступления | `unknown`. |

Указанные в источнике дни и даты описывают выступления. C# может показать их вместе с результатом проверки. Для обязательного общего пожелания подходит `true`, в том числе при неизвестном расписании.

## Панель управления и конструктор

Первая версия панели доступна автору проекта. C# использует собственный ключ доступа. Для администратора предусмотрен отдельный вход.

Панель показывает модель, состояние задач, время до готового пакета, длительность этапов и ошибки. Вкладка «Конструктор карточки» запускает тот же подбор и расчёт бюджета. На ней можно задать параметры поездки, посмотреть готовый пакет, выбрать отель и места и рассчитать бюджет. Эту вкладку можно демонстрировать и тестировать без C# и основного сайта. Тестовые карточки живут в пространстве панели отдельно от пользовательских карточек.

## Развёртывание и дальнейшее развитие

Render — кандидат для размещения Python API и панели. До развёртывания нужно выбрать хранилище, проверить условия выбранного тарифа и учесть холодный запуск при настройке таймаутов и повторов. [Ограничения бесплатного Render](https://render.com/docs/free)

С хостинга проверяем доступ к DeepSeek и источникам, лимиты и время ответа. Обычные HTTP-запросы выполняет Python. Для демонстрации преподавателю или команде можно добавить отдельную роль с доступом к конструктору и результатам.

Перед интеграцией предстоит согласовать точные поля и коды ошибок, сроки ожидания и повторов, интервал polling, источники данных и правила сопоставления объектов. Сквозные проверки охватывают время до полного пакета с пустым и заполненным каталогом, пустую и частичную выдачу, повторное чтение результата, обновление статусов React, завершение ожидания при потере задачи и смету по выбранному тарифу.
