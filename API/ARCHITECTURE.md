# Архитектура Python-сервиса TripFlow

Дата фиксации — 15 ноября 2026 года. Здесь описан согласованный сценарий для продукта. [Контракт](CONTRACT.md) и [примеры сценариев](SCENARIOS.md) описывают предыдущую интеграцию. Перед реализацией нужно привести их к этой архитектуре и согласовать точные поля и коды ошибок с C# backend.

## Ответственность сервисов

| Компонент | Ответственность |
|---|---|
| C# backend | Хранит карточку и её версию, выбор пользователя, отклонённые варианты, очередь рекомендаций и итоговый бюджет. Задаёт лимиты на подбор, вызывает Python и принимает callback. |
| Python API | Сохраняет задачи, делит их на этапы, получает данные поставщиков, управляет проверками и моделью, валидирует результаты и доставляет события в C#. Ведёт постоянный каталог объектов и фактов о них. |
| Локальный клиент | Запускается на компьютере участника. Проверяет доступность LM Studio, загружает модель, выполняет короткий тест, сообщает о готовности и забирает задания по исходящему HTTPS. |
| LM Studio | Выполняет запросы модели на компьютере участника. Локальный HTTP-интерфейс доступен клиенту на этом же компьютере. |
| Хостинг | Содержит Python API и закрытую панель управления. Render рассматривается как первый вариант хостинга. Задачи, каталог и ожидающие отправки callback хранятся в постоянной БД. |

Первую интеграцию проверяем с одним локальным клиентом. Второй и последующие клиенты могут обрабатывать независимые задания одновременно. Адреса домашних компьютеров для выдачи заданий не требуются.

## Подбор и расчёт бюджета

Две операции для C# используют общую асинхронную схему. Названия путей ниже служат рабочими именами для обновления контракта.

| Операция | Что отправляет C# | Что возвращает Python |
|---|---|---|
| `POST /v1/recommendations` | `taskId`, параметры поездки, нужные типы и количество вариантов, лимиты. Для догенерации — актуальное уточнение и исключения, включая уже показанные и отклонённые объекты. | Варианты по мере готовности, сведения об источнике и цене, отдельное завершение подбора отелей и мест. |
| `POST /v1/budget` | `taskId`, актуальные параметры поездки, выбранный отель с тарифом и включёнными услугами, выбранные места, подтверждённые или оценочные цены при наличии. | Итог операции с оценками питания, городского транспорта, прочих расходов и резерва на всю группу за поездку. C# суммирует их с проживанием и посещениями и сохраняет итог для этой версии карточки. |

Первичный подбор и догенерация используют одну операцию. C# считает допустимую стоимость нового выбора, исходя из оставшегося бюджета. При замене действующего варианта его стоимость не удерживается в остатке. Бюджет по выбранным вариантам запрашивается отдельно. Текст пожеланий и текущий выбор привязаны к версии карточки.

Для подбора Python разбирает пожелания, ищет кандидатов в каталоге и у поставщиков, применяет фильтры и проверяет недостающие условия. Подходящий объект можно отправить сразу после проверки обязательных условий. Желательные условия влияют на порядок и могут сопровождаться отметкой о неопределённости. C# добавляет варианты в запас для карточки, а интерфейс показывает их по одному. Пользователь выбирает один отель и может добавить несколько мест.

Цена источника, справочная оценка и неизвестная стоимость имеют разные значения. Условие о завтраке влияет на бюджет при подтверждении включения в выбранный тариф. Если цена выбранного посещения неизвестна, итог отмечается как неполный. При ограниченном бюджете можно сократить необязательные прочие расходы до нуля. Если оставшиеся статьи превышают бюджет, C# показывает превышение.

## Callback и завершение выдачи

Python отвечает `202 Accepted` после сохранения задачи. C# заранее связывает `taskId` с версией карточки. Python доставляет события на настроенный HTTPS-адрес backend с отдельным ключом callback.

| Событие | Назначение |
|---|---|
| `recommendation.added` | Готов один вариант. Событие содержит объект и его тип, отель или достопримечательность. C# может показать его сразу. |
| `target.finished` | Текущий поиск данного типа завершён. Передаются итоговый статус, количество отправленных вариантов и `hasMore`. Событие отправляется и при пустой выдаче. |
| Итоговый callback бюджета | Оценки готовы либо расчёт завершился ошибкой. Результат относится к выбору и версии карточки на момент запроса. |

Отели и места завершаются независимо. Пока текущий поиск идёт, при пустом запасе интерфейс показывает ожидание следующего варианта. После завершения C# продолжает показывать накопленные варианты. По исчерпании запаса `hasMore: true` означает, что найден следующий пригодный кандидат, `false` — что поиск исчерпан, а `null` — что доступность следующих вариантов осталась неизвестной. При `null` интерфейс предлагает повторить поиск.

События сохраняются до первой отправки. Для повтора используются тот же `taskId` и порядковый номер `seq`. Внутри задачи доставка идёт по порядку. C# подтверждает событие после записи в БД, применяет его один раз и проверяет версию карточки. Временный сбой доставки сохраняет событие для следующей попытки. При повторе самого запроса с тем же `taskId` и теми же данными Python возвращает ранее принятый статус. Изменённые параметры требуют новой задачи.

## Очередь и локальная модель

1. Python сохраняет этапы задачи и их состояние в БД. Свободный клиент обращается к Python и получает одно задание, подходящее его модели. Выдача попытки атомарна.
2. Клиент выполняет задание через LM Studio, проверяет формат результата и возвращает его с идентификатором попытки. Python выполняет итоговую валидацию, учитывая данные поставщиков и контекст задачи.
3. У задачи есть общий срок, у каждой выданной попытки — срок закрепления за клиентом. При отключении клиента или истечении попытки Python может назначить новую. Запоздалый ответ старой попытки не заменяет актуальный результат.
4. Клиент регулярно сообщает состояние. Сервер определяет доступность по времени последнего контакта. Если свободных клиентов нет, задача ждёт до общего срока. К его истечению Python закрывает выдачу и сообщает о сбое или о частичном результате, если часть вариантов уже собрана.
5. После перезапуска Python восстанавливает незавершённые задачи и недоставленные callback из БД. При паузе клиент заканчивает текущую работу и прекращает брать новые задания.

У модели остаются три основных сценария. Разбор пожеланий выделяет фильтры, дополнительные вопросы и сведения о тратах. Проверка условий сопоставляет вопрос с доказательствами по отелю, месту или тарифу и возвращает вывод. Оценка бюджета опирается на справочные ставки, известные включения и выбор пользователя. Код проверяет структуру, источники, единицы измерения и арифметику. Запросы к модели и веб-поиск учитываются отдельно, чтобы ограничение одного этапа не скрывало состояние другого.

## Постоянный каталог объектов

Отель и достопримечательность получают собственный неизменяемый `objectId` TripFlow. Для сопоставления используются тип объекта, нормализованное название и координаты. Адрес и населённый пункт помогают разобрать неоднозначные случаи. Внешний ID можно сохранить рядом с названием источника для обновлений и диагностики. Запись можно создать, если объект уверенно распознан по названию и координатам, даже когда внешний ID отсутствует. При смене названия или уточнении координат уже связанный объект сохраняет свой `objectId`. Неоднозначное совпадение требует дополнительной проверки. Точный допуск по расстоянию предстоит подобрать на данных поставщиков.

Логически запись содержит три части:

- Основные поля объекта — название, адрес, координаты, тип, описание и другие доступные характеристики. Тарифы и цены имеют свою область действия и дату наблюдения.
- `filters` — список подтверждённых стандартных признаков объекта для быстрого подбора. Модель может предложить признак для проверки. В список он попадает после подтверждения по данным. Обязательность, желательность и исключение задаются в запросе пользователя.
- Дополнительные данные — словарь, где ключ обозначает смысл вопроса, а значение содержит ответы по областям действия. Для каждой области сохраняются `true` или `false`, источник и время проверки. Если ответ зависит от тарифа или периода, в словаре могут одновременно храниться разные ответы. При недостатке доказательств подходящего ответа в словаре нет. Незавершённую проверку можно хранить отдельно с коротким сроком повторного использования.

Например, у вопроса «Завтрак включён в цену?» может быть ответ `true` для тарифа с питанием и `false` для тарифа без питания. Для распространённых вопросов сценарий разбора пожеланий выделяет известный признак и область действия. Для разных формулировок редких вопросов можно искать похожие проверки с помощью эмбеддингов. Перед повторным использованием нужно подтвердить совпадение смысла, отрицания, тарифа и периода. Порог сходства и необходимость отдельного вызова модели определятся по результатам испытаний.

При новом запросе Python ищет в каталоге записи, подходящие по месту, фильтрам и актуальности данных. Поставщики пополняют выборку и обновляют цены и характеристики. Одновременные проверки одного и того же факта можно объединять. C# хранит итог бюджета по версии карточки. Python хранит результат бюджетной задачи для доставки и повторной обработки запроса с тем же `taskId`.

## Панель управления и конструктор

Первая версия панели доступна автору проекта. C# использует собственный ключ доступа, а каждый локальный клиент — отдельный отзываемый ключ. Для администратора предусмотрен отдельный вход.

Панель показывает состояние клиентов, версию модели, очередь задач, время до первого варианта, длительность этапов и ошибки. Вкладка «Конструктор карточки» запускает тот же подбор и расчёт бюджета и читает сохранённые события Python. На ней можно задать параметры поездки, посмотреть варианты в порядке поступления, выбрать отель и места и рассчитать бюджет. Эту вкладку можно демонстрировать и тестировать без C# и основного сайта. Тестовые карточки живут в пространстве панели и не попадают в пользовательские карточки.

## Развёртывание и дальнейшее развитие

Render — кандидат для размещения Python API и панели. Инференс выполняется на компьютерах участников. Бесплатный веб-сервис Render засыпает после 15 минут без входящего трафика, а его локальная файловая система не сохраняется после остановки. Бесплатная база Render Postgres истекает через 30 дней. Поэтому место для постоянной БД и срок её доступности нужно выбрать до развёртывания. Пробуждение Render учитывается в таймаутах и повторах. [Ограничения бесплатного Render](https://render.com/docs/free).

До выбора места веб-поиска проверяем с хостинга доступ к поставщикам и источникам, лимиты и время ответа. Обычные HTTP-запросы выполняет Python. Поиск и тяжёлый парсинг можно выдать отдельным локальным заданием, если на хостинге недостаточно ресурсов или источник с него недоступен.

После проверки первого сквозного сценария можно подключать дополнительные компьютеры, автоматический режим доступности, облачные модели с лимитом расходов, эмбеддинги и управление версиями промптов из панели. Переключение локальной модели выполняется из разрешённого списка и с учётом согласия владельца компьютера. Для демонстрации преподавателю или команде можно добавить отдельную роль с доступом к конструктору и результатам.

Перед интеграцией предстоит согласовать хостинг БД, точные схемы запросов и callback, сроки ожидания и повторов, правила сопоставления объектов, сроки актуальности фактов и цен. Первые проверки — выдача варианта до завершения поиска, отключение клиента во время работы, перезапуск Python после `202`, повтор доставки и бюджет с завтраком именно по выбранному тарифу. [Результаты локального эксперимента](experiments/card-preferences/REPORT.md).
