# Инструкции для работы над backend TripFlow

Этот файл дополняет [корневой AGENTS.md](../AGENTS.md) и действует внутри `Backend/`. Корневой файл содержит общий контекст проекта. При работе над backend учитывай более конкретные инструкции этого файла; не считай предварительные идеи утверждёнными требованиями.

## Границы и подход к работе

- Основная рабочая область — `Backend/`. Другие части репозитория используй для чтения и сверки интеграции; изменения за пределами `Backend/` согласовывай с пользователем.
- Backend-разработчик осваивает C# и планирует использовать ASP.NET. Объясняй решения и незнакомые конструкции понятным языком, соразмерно задаче. Предлагай простую поддерживаемую реализацию, подходящую учебному проекту; не усложняй архитектуру без необходимости.
- Первый рабочий вариант использует ASP.NET Core Minimal API на .NET 10, локальный JSON для данных и токены сессий в памяти. [README backend](README.md) описывает запуск и текущие маршруты. Выбор постоянной СУБД, ORM и схемы авторизации для развёртывания остаётся открытым.
- Перед реализацией изучай относящиеся к задаче файлы. Изменения делай в рамках запроса, не переписывай соседние части без необходимости. Добавляй значимые проверки поведения и запускай подходящие тесты; сообщай, что именно проверено и что осталось непроверенным.
- Решения, существенно влияющие на модель данных, пользовательский сценарий, бюджет или границы сервисов, уточняй у пользователя и команды. Независимую работу продолжай. Устойчивые новые договорённости фиксируй в этом файле по мере их появления.

## Контекст продукта и обязанности

TripFlow — курсовой проект трёх студентов: сервис совместного планирования поездок. Участники дашборда сравнивают карточки с вариантами поездки и голосуют за них. Backend предполагается основной системой приложения: он связывает React-клиент с Python API, отвечает за пользователей, доступ и сохранение состояния дашбордов, карточек, вариантов, голосов и предложений. Python API выполняет тестовый подбор и оценку расходов, хранит собственные задачи и аккаунты кабинета интеграции. AI и внешние данные относятся к следующему этапу.

- Автор собирает карточку и выбирает варианты; незавершённые карточки в первой версии предполагается скрывать от остальных. После публикации карточка доступна группе и остаётся редактируемой автором.
- Участники могут голосовать; голос сохраняется при изменении карточки. Предполагается предупреждать проголосовавшего о том, что карточка изменилась, и позволять оставить или снять голос. Механизм версий и подтверждения просмотра пока не определён.
- Рассматриваются предложения изменения элемента чужой карточки с выбором альтернативы и необязательным комментарием; автор принимает или отклоняет предложение. Объём MVP, статусы и история ещё уточняются.
- Предварительно рассматриваются приглашение по ссылке и чтение по ссылке без регистрации. Создание карточек, голосование и предложения требуют входа. Правила вступления, выхода, управления участниками и остальные права владельца и участников требуют согласования. Проверяй права на сервере, не полагайся только на интерфейс.
- Владелец может удалить дашборд целиком, включая карточки других участников и их черновики. Удалить отдельную карточку может её автор. Голоса хранятся вместе с карточкой и удаляются вместе с ней.
- Исходные параметры карточки предварительно включают направление, даты, число путешественников, общий бюджет и свободные предпочтения. Перелёты и точки отправления пока вне рассматриваемого первого объёма.

## Интеграция с Python API

Актуальная схема описана в [контракте](../API/docs/CONTRACT.md), [BACKEND-HANDOFF](../API/docs/BACKEND-HANDOFF.md) и [сценариях](../API/docs/SCENARIOS.md). Маршруты карточек уже реализованы. Текущий клиент C# ожидает callback. При подключении новой Python API переведи его на polling. [Состояние C#](README.md#связь-с-python) · [Кабинет на Render](../API/docs/PORTAL.md)

- Backend предоставляет frontend направления из [общего справочника](../shared/data/destinations.json) и передаёт в Python выбранный `destinationId` в составе параметров поездки. Сейчас в справочнике только Москва.
- Первичный подбор и догенерация используют `POST /v1/recommendations`, смета использует `POST /v1/budget`. Запрос защищён `X-API-Key`. Backend сохраняет `taskId`, версии и снимок входа перед отправкой. Ответ `202 Accepted` подтверждает приём задачи.
- Для нового контракта Backend создаёт отдельную задачу на каждую категорию. `targets` — строка, `count`, `maxTotalRub`, `refinement` и `excludedObjectIds` находятся на верхнем уровне. Оба последних поля обязательны и допускают `null`. Для исключений также подходит `[]`. При расчёте сметы выбранный отель передаётся как `objectId` и `price`.
- Backend читает `GET /v1/tasks/{taskId}` по `Location` с тем же ключом. При `pending` учитывает `Retry-After`, а при `completed` разбирает `result` и применяет его один раз по ID и версии карточки. Ключ хранится в окружении или защищённой конфигурации.
- Backend хранит выбор, накопленные варианты и исключения конкретной карточки. Догенерация добавляет альтернативы в существующую выдачу. Изменение выбора или параметров увеличивает версию карточки. Итог прошлой версии не применяется, а прежняя смета получает статус `stale`.
- `hasMore` трёхзначен: `true` означает дополнительный кандидат, `false` означает исчерпанный поиск, `null` означает неизвестность. Во время поиска и при сбое наружу отдаётся `null`. При сбое прежние варианты сохраняются и клиент получает причину.
- Не сохраняй секреты в репозитории или логах. Разделяй ошибку немедленного запроса и ошибку асинхронной задачи; сохраняй введённые данные при сбое. Форматы ошибок и точное поведение повторов уточняются по мере реализации.

## Бюджет и качество данных

- Целевой бюджет — целые рубли на всю группу и поездку, включая резерв. Backend рассчитывает ориентировочный итог, сумму на человека и разницу с бюджетом. Проценты допуска и условия повторного поиска не согласованы; превышение само по себе не является ошибкой генерации.
- Ночи — разница дат. Цена отеля — целая сумма за проживание всей группы. Цена посещения содержит сумму и единицу за человека или группу. Дополнительные расходы и резерв Python возвращает на всю группу за поездку. Сумма на участника округляется вверх.
- Для посещений `price.kind` различает цену источника и расчётную оценку. `0` означает бесплатность, `null` — неизвестную цену. При ночёвке без отеля или при неизвестной цене смета неполная. Цена «от» и неполная смета дают нижнюю границу.
- Не подменяй неизвестные данные нулём и не выдавай придуманные AI объекты за реальные. Новые рекомендации предлагаются пользователю и не заменяют его выбор молча.
