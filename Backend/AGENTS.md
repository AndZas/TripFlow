# Инструкции для работы над backend TripFlow

Этот файл дополняет [корневой AGENTS.md](../AGENTS.md) и действует внутри `Backend/`. Корневой файл содержит общий контекст проекта. При работе над backend учитывай более конкретные инструкции этого файла; не считай предварительные идеи утверждёнными требованиями.

## Границы и подход к работе

- Основная рабочая область — `Backend/`. Другие части репозитория используй для чтения и сверки интеграции; изменения за пределами `Backend/` согласовывай с пользователем.
- Backend-разработчик осваивает C# и планирует использовать ASP.NET. Объясняй решения и незнакомые конструкции понятным языком, соразмерно задаче. Предлагай простую поддерживаемую реализацию, подходящую учебному проекту; не усложняй архитектуру без необходимости.
- Первый рабочий вариант использует ASP.NET Core Minimal API на .NET 10, локальный JSON для данных и токены сессий в памяти. [README backend](README.md) описывает запуск и текущие маршруты. Выбор постоянной СУБД, ORM и схемы авторизации для развёртывания остаётся открытым.
- Перед реализацией изучай относящиеся к задаче файлы. Изменения делай в рамках запроса, не переписывай соседние части без необходимости. Добавляй значимые проверки поведения и запускай подходящие тесты; сообщай, что именно проверено и что осталось непроверенным.
- Решения, существенно влияющие на модель данных, пользовательский сценарий, бюджет или границы сервисов, уточняй у пользователя и команды. Независимую работу продолжай. Устойчивые новые договорённости фиксируй в этом файле по мере их появления.

## Контекст продукта и обязанности

TripFlow — курсовой проект трёх студентов: сервис совместного планирования поездок. Участники дашборда сравнивают карточки с вариантами поездки и голосуют за них. Backend предполагается основной системой приложения: он связывает React-клиент с Python API, отвечает за пользователей, доступ и сохранение состояния дашбордов, карточек, вариантов, голосов и предложений. Python API получает внешние данные, выполняет AI-подбор и формирует оценки; пользовательское состояние в нём не хранится.

- Автор собирает карточку и выбирает варианты; незавершённые карточки в первой версии предполагается скрывать от остальных. После публикации карточка доступна группе и остаётся редактируемой автором.
- Участники могут голосовать; голос сохраняется при изменении карточки. Предполагается предупреждать проголосовавшего о том, что карточка изменилась, и позволять оставить или снять голос. Механизм версий и подтверждения просмотра пока не определён.
- Рассматриваются предложения изменения элемента чужой карточки с выбором альтернативы и необязательным комментарием; автор принимает или отклоняет предложение. Объём MVP, статусы и история ещё уточняются.
- Предварительно рассматриваются приглашение по ссылке и чтение по ссылке без регистрации. Создание карточек, голосование и предложения требуют входа. Способ вступления, права владельца и участников, удаление и выход требуют согласования. Проверяй права на сервере, не полагайся только на интерфейс.
- Исходные параметры карточки предварительно включают направление, даты, число путешественников, общий бюджет и свободные предпочтения. Перелёты и точки отправления пока вне рассматриваемого первого объёма.

## Интеграция с Python API

Источник деталей — [черновик контракта](../API/CONTRACT.md); [сценарии](../API/SCENARIOS.md) поясняют поведение. Это договорённости для проектирования, а не свидетельство работающей интеграции. Перед реализацией сверяй актуальную версию контракта и согласовывай изменения с автором Python API. Статусы HTTP-ошибок, каталог ошибок и часть правил валидации ещё открыты.

- Backend предоставляет frontend направления из [общего справочника](../shared/data/destinations.json), принимает выбранный `id` и формирует объект направления для Python. Сейчас в справочнике только Москва. Не считай примеры других городов в контракте перечнем поддерживаемых направлений.
- Полная генерация: `POST /v1/generate`; догенерация одного типа: `POST /v1/generate-more`. Формат JSON — `camelCase`; запрос защищён `X-API-Key`. Backend заранее создаёт `taskId` и связывает его с карточкой и её версией. Ответ `202 accepted` подтверждает приём задачи, а не её успешное завершение.
- Результат поступает на callback backend с тем же `taskId`. До обработки проверяется отдельный `X-Callback-Key`; ключи хранятся в окружении или защищённой конфигурации, передача — по HTTPS. Успешный приём подтверждается `200` или `204`. При проектировании обработки учитывай повторную доставку, неизвестные задачи и устаревшие результаты, чтобы не перезаписать актуальный выбор; конкретную политику согласуй с командой.
- Backend хранит выбор, показанные и отклонённые варианты и управляет общей очередью. Догенерация получает актуальный контекст, `target`, лимит и исключения; возвращает альтернативы, не меняя выбор и общие оценки автоматически. Исключение относится к подбору конкретной карточки, а не ко всем карточкам.
- `hasMore` трёхзначен: `true` — есть дополнительный кандидат; `false` — поиск завершён, после исчерпания выдачи не запрашивать догенерацию с теми же параметрами; `null` — поиск не завершён, пользователь может инициировать повторный поиск с новым `taskId`. Пустая выдача может быть успешной. При ошибке догенерации предыдущая выдача и `hasMore` сохраняются.
- Не сохраняй секреты в репозитории или логах. Разделяй ошибку немедленного запроса и ошибку асинхронной задачи; сохраняй введённые данные при сбое. Форматы ошибок и точное поведение повторов уточняются по мере реализации.

## Бюджет и качество данных

- Целевой бюджет — целые рубли на всю группу и поездку, включая резерв. Backend рассчитывает ориентировочный итог, сумму на человека и разницу с бюджетом. Проценты допуска и условия повторного поиска не согласованы; превышение само по себе не является ошибкой генерации.
- Ночи — разница дат; ежедневные расходы включают обе даты. Положительная дробная сумма после приведения к рублям округляется вверх. При расчёте используй единицы, указанные в контракте: цена отеля — на человека за ночь, цена достопримечательности — на человека за посещение; общие расходы и резерв уже рассчитаны на группу и поездку.
- Для кандидата используй `price.amountRub`, если значение не `null`, иначе `price.estimatedRub`. `0` означает подтверждённую бесплатность, `null` — неизвестную цену. Сохраняй различие цены источника и оценки; даже цена источника не гарантирует стоимость бронирования.
- До выбора применяются общие опорные ставки проживания и посещений; после выбора соответствующий расчёт заменяет общую оценку, без двойного учёта. Альтернативные отели не суммируются. Если у выбранной достопримечательности обе цены неизвестны, её стоимость не включается в итог; итог помечается как неполный и соответствие бюджету не считается подтверждённым. Полные формулы и состав обязательных оценок см. в контракте.
- Не подменяй неизвестные данные нулём и не выдавай придуманные AI объекты за реальные. Новые рекомендации предлагаются пользователю и не заменяют его выбор молча.

- [README проекта](../README.md), [обзор источников](../API/EXTERNAL_APIS.md) и исследования в `API/experiments/` дают контекст и ограничения данных, а не готовую реализацию backend.

- `Frontend/TripFlow/` сейчас содержит стартовый шаблон React/Vite, поэтому готового контракта клиентского API из него вывести нельзя. Форматы backend ↔ frontend следует проектировать совместно с frontend-разработчиком.
- До реализации соответствующих частей уточнить: состав MVP и правила публикации; регистрацию и сессии; модель доступа и приглашений; правила голосования и версий; предложения изменений; пересчёт и пороги; технологический стек, развёртывание и контракт клиента. Не превращай этот перечень в обязательную полную проработку до начала независимых задач.
